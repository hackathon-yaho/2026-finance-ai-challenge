## 5-1. `POST /api/draft` (F7-01)

백엔드는 문장을 **생성하지 않는다.** AI-server를 호출하고 결과를 검사해 전달한다.

### 내부 호출

```json
POST /internal/draft
{
  "events": [ /* confirmed=true 카드만 */ ],
  "reason": "goods | service | debt | unclear",
  "readiness": "SUBMISSION_READY | SUPPLEMENT_NEEDED | BANK_CHECK_REQUIRED",
  "intake": { "when": "2026-09-04", "amount": 450000, "kind": "goods", "usage": "main" }
}
```

- [ ] **`confirmed=true` 카드만 전달한다** (F4-06 소명서 반영, TC-11)
- [ ] `reason`·`readiness`는 `ReadinessService`가 이미 결정한 값을 그대로 넘긴다. **AI-server는 이 값을 재해석하지 않는다** — 백엔드도 AI 응답을 근거로 준비도를 다시 계산하지 않는다
- [ ] 타임아웃 15초, 재시도 1회

### `intake` 객체 (2026-08-25 신설) — TC-06이 이것 없이는 불가능하다

자료 0건 경로(TC-06)는 `events`가 빈 배열이다. **문진이 유일한 사실 재료**인데 종전 스키마에는 자리가 없었다. 요청·확정: `../../docs/request/backend/draft-intake-input.md`, `../../docs/response/ai/draft-intake-input.md`.

- [ ] `/api/intake`로 받아 세션에 있는 값 4개(`when`·`amount`·`kind`·`usage`)를 **필드명 그대로** 넘긴다
- [ ] **`history`·`dueNoticeStatus`·`dueNoticeDate`는 넘기지 않는다.** 준비도 판정용 값이고 그 판정은 이미 끝나 `readiness`로 전달된다. 더 중요한 이유는 **과거 지급정지 이력이 사용자에게 불리한 정보**라는 것 — 묻지도 않은 이력을 사용자가 스스로 은행에 제출하는 문서에 넣게 만들면 안 된다
- [ ] `intake.amount`는 **사실 기재 전용**이다. 준비도에 쓰지 않고("입금액은 소명서 사실 기재에만", `reason-type-rules.md`), "소액이라 유리하다" 류의 문장도 만들지 않는다 (PRD §14 OI-01)
- [ ] 문진을 건너뛴 세션은 각 필드가 `null`이거나 `intake`가 통째로 없어도 된다 — AI-server가 `events`만으로 생성한다

### 지급정지일 합성 이벤트를 `events`에 넣지 않는다 (2026-08-25 확정)

F5-01이 타임라인에 삽입하는 "사용자 진술 / 낮은 신뢰도" 지급정지일 이벤트는 **소명서 입력에서 뺀다.**

- [ ] `events` 구성 시 **추출 카드만** 담는다. 합성 이벤트를 필터링한다
- [ ] 이유: 합성 이벤트가 섞이면 AI-server가 `evidence` 근거로 오인해 **"근거 있는 사실"처럼 서술**한다. FR-045의 근거 유형 구분이 존재하는 이유가 무너진다
- [ ] **타임라인 표시(F5-01)와 공백 탐지(F5-03)에서는 합성 이벤트를 그대로 쓴다.** 화면의 타임라인과 `/internal/draft`의 `events`가 완전히 같지 않다는 뜻이다 — 같은 리스트를 재사용하다가 실수하기 쉬운 지점이다

### 사실 검증 실패 처리 (F7-02 / FR-045)

- [ ] 응답의 `factCheckPassed == false`면 **그대로 프론트에 전달하지 않는다**
- [ ] 재생성 **1회로 제한**한다. 재실패 시 해당 문단을 생략한다 (`prd.md` §10.3)
- [ ] **무한 루프 방지** (F7-02 개발 주의)

### 응답 (`api-contract.md`)

```json
{
  "draftText": "...",
  "sentences": [{ "sentenceId": "s1", "text": "...", "evidenceRefs": [{ "type": "evidence", "imageIndex": 2, "bbox": {...} }] }],
  "checklist": [{ "item": "거래 대화 캡처", "have": true }]
}
```

- [ ] `sentences`를 세션의 `sentenceEvidence`에 보관한다 — **참조(imageIndex, bbox)만. 이미지 바이트 금지** (`data-model.md`)
- [ ] **`evidenceRefs.type` 3종을 그대로 통과시킨다** (2026-08-25 확정): `evidence`(+`imageIndex`·`bbox`) / `intake` / `user_text`. 뒤 둘은 `imageIndex`가 **없는 것이 정상**이므로 검증에서 필수로 걸지 않는다. 프론트는 이 둘에 "본인 진술" 배지를 렌더한다 (FR-045 ⑤)
- [ ] **응답의 `checklist`는 백엔드가 자기 값으로 채운다.** `/internal/draft` 응답에도 `checklist`가 들어 있지만 **첨부 서류 체크리스트(F7-03)의 담당은 `A`(백엔드)** 이고 내용이 결정적(사유별 고정 목록 + 보유 여부)이므로, AI가 준 값을 그대로 흘리지 않는다. 두 값이 다르면 사용자는 Stage 3과 Stage 4에서 서로 다른 체크리스트를 보게 된다
- [ ] 프론트는 이 참조로 자기 브라우저 blob에서 원본을 찾는다. **서버에서 원본을 다시 내려주지 않는다** (FR-046)

## 5-2. 재생성 (F7-04)

- [ ] Stage 2 복귀 → 증거 추가 → Stage 4 재진입 시 타임라인 갱신 후 F7-01 재실행
- [ ] 수용 기준: **협박 문자를 추가하면 협박 수신 사실 문단이 새로 생긴다** (발표 데모 `[2:40]`)

> 협박 문단의 문안은 F10-04에 고정되어 있고 **"편취 의도가 없었음을 반증한다", "결백을 증명한다" 같은 결론적 표현은 금지**다. 다만 이 제약은 **AI-server의 프롬프트 제약**이며(`../../docs/00-context/prd.md` §10.2), 백엔드가 문장을 검열하는 역할은 문서에 정의되어 있지 않다. 백엔드의 책임은 `factCheckPassed == false`일 때 재생성 1회로 제한하는 것까지다.

## 5-3. 첨부 서류 체크리스트 (F7-03 / FR-041~042)

- [ ] Phase 4의 사유별 체크리스트 데이터를 재사용한다 (두 벌로 나누지 않는다) — **Stage 3(`/api/readiness`)과 Stage 4(`/api/draft`)가 같은 소스에서 나와야 한다**
- [ ] **Phase 4-3a의 항목 구조를 그대로 쓴다** (`tier`·`fulfillBy`·`whenMissing`·`options`). 평평한 목록으로 눌러 담지 않는다
- [ ] 미보유 항목 표기 **"미보유 — 보완 요청 사유가 될 수 있어요"는 `whenMissing == NOTICE`인 항목에만 붙인다** (2026-08-25 정정 — 층이 아니라 이 필드가 기준). `SILENT`은 **배지 자체를 렌더하지 않는다**
- [ ] **이 문구는 화면 전용이다.** PDF에 나가지 않는다 (5-4 "부족자료 체크리스트를 뺀 이유")
- [ ] 신분증 사본 = `fulfillBy: SELF` + `whenMissing: SILENT` — "서비스 업로드 대상 아님, 제출 시 직접 첨부"
- [ ] 재직증명서·소득금액증명원 등 `supporting.*`도 **`fulfillBy: SELF`로 "직접 첨부" 표시** (업로드받지 않는다)
- [ ] 세금계산서는 필수로 노출하지 않는다 — **`goods.trade_doc` 택일 선택지 중 하나**로만 노출한다

- [ ] 라이브러리: OpenPDF 또는 Apache PDFBox

- [ ] 각 면 하단 고정 표기: **"AI 초안 · 사용자 확인 완료 {시각} · 최종 판단은 금융회사"**. **`{시각}`은 다운로드를 누른 시각**이다 — 초안 생성 시각이 아니다
- [ ] **원본 이미지 페이지는 서버가 만들지 않는다.** 프론트가 자기 blob으로 만들어 `pdf-lib`으로 병합한다 (F7-06 분담)

### 부족자료 체크리스트를 뺀 이유

미보유 항목 중에는 **사용자가 애초에 채울 수 없는 것**이 섞여 있다(개인 중고거래자의 사업자등록증, 차용증 없는 대여의 차용증). 화면에서는 이것들을 `whenMissing: SILENT`로 두어 **표시조차 하지 않는데**(Phase 4-3a), 같은 목록이 PDF가 되면 **화면에서 감춘 항목이 제출본에서 되살아난다.** "이 사람은 사업자등록증도 차용증도 없다"를 사용자가 스스로 정리해 은행에 건네는 셈이다.

**부족자료 체크리스트는 화면에 그대로 있다** — 사용자가 무엇을 더 준비할지 보는 용도다. TC-34가 이걸 검증한다.

### 면별 항목·정렬 기준 (2026-08-25 신설)

**같은 면을 백엔드(PDF)와 프론트(미리보기 S04-2)가 각자 그린다.** 기준이 없으면 사용자가 미리 본 것과 받는 것이 어긋난다. **PDF가 단일 출처**이므로 아래가 기준이다 (`../../docs/00-context/spec.md` F8-01).

| 면 | 항목 | 정렬 |
| --- | --- | --- |
| 표지 | "이 문서에 포함된 것" 1~5 / "신청인이 따로 첨부하는 것"(신분증 사본, 1면 자필 서명) | 고정 |
| 1 | 11필드 | 서식 순서 고정 |
| 2 | 진술서 본문 (제외 문장 빼고) | 문장 생성 순서 |
| 3 | 일시 · 행위 주체 · 요약 · 금액. **`confirmed`인 카드만** (2026-08-26 명시) | `occurred_at` 오름차순, 동시각은 F5-01 tie-break |
| 4 | 순번 · 자료 유형 · 확인된 일시 · 한 줄 요약 · **원본 n번** | **카드 단위, `source_image_index` 오름차순** (2026-08-25 정정, 아래 참조) |

**3면 미확인 카드 제외 (2026-08-26)** — 2면·4면은 이미 제외였는데 3면만 정해진 바 없었다. 3면 항목(일시·행위주체·요약·금액)이 FR-028 게이팅 필드와 겹쳐, 미확인 카드를 표로 올리면 서술문(2면)보다 더 사실처럼 읽힌다. `ReadinessService`/`DraftService`처럼 **`confirmed`(`user_confirmed`/`user_corrected`)인 카드만 3면 입력으로 쓴다.** 근거: `../../docs/request/backend/page3-and-biz-notice.md`, `../../docs/response/backend/page3-and-biz-notice.md`

**4면 정렬 기준 정정 (2026-08-25 ②)** — "5면 이미지 순서와 일치"는 성립하지 않는다: 이미지 1장에서 카드가 여러 개 나오거나(대화 캡처 안 송금 알림), 미확인 카드는 4면엔 없는데 원본은 5면에 남거나, 텍스트 입력 카드(F3-04)는 애초에 이미지가 없다.

- [ ] **카드(사실) 단위로 정렬** — `source_image_index` 오름차순, `null`(텍스트 입력 카드)은 뒤로
- [ ] 각 줄에 **"원본 n번"** 표기. `source_image_index`는 계약상 **0-base**이지만 화면·PDF엔 **1-base로 표시** — **변환은 프론트가 렌더링 시 처리**한다(백엔드 PDF 생성 로직도 동일하게 +1)
- [ ] 텍스트 입력 카드(`source_image_index: null`)는 "원본 n번" 없이 자료 유형 자리에 **"본인 서술"**

근거: `../../docs/response/frontend/page4-ordering.md`

**금지 3가지**

- [ ] **3면에 `gaps`(증거 공백)를 넣지 않는다** — 부족자료 체크리스트를 뺀 것과 같은 이유. 공백은 화면에만 표시한다
- [ ] **4면에 파일명을 넣지 않는다** — 사용자 파일명에 개인정보가 섞일 수 있다(`카톡_김철수_20260901.png`)
- [ ] **4면에 보유/미보유를 표시하지 않는다** — 4면은 목차이지 체크리스트가 아니다

> **프론트는 1면을 HTML로 재현하지 않는다.** 같은 법정 서식을 두 곳에서 구현하면 한쪽만 고쳤을 때 조용히 어긋난다. 미리보기는 **입력값 요약만** 보여주고 서식 렌더는 서버 PDF에 맡긴다.

### 별지 제4호서식 **11개 필드** + `excludedSentenceIds` (요청 바디, 2026-08-25 개정)

PRD §4.4 필드 매핑상 아래 값은 **사용자 직접 입력(서비스 미저장)**이라 `GET` 쿼리에 실을 수 없다. `POST` 바디로 받는다.

```json
{
  "applicant": { "name": "", "birthDate": "", "address": "", "phone": "", "mobile": "", "email": "" },
  "account":   { "bank": "", "branch": "", "depositType": "", "accountNumber": "", "holderName": "" },
  "excludedSentenceIds": ["s3", "s7"]
}
```

- [ ] **`mobile`·`email`·`holderName` 3개가 추가됐다** — 종전 8필드는 서식의 11개 기재란과 맞지 않았다
- [ ] **11개 전부 선택.** 빈 값이어도 `400`을 내지 않는다 — 해당 칸을 **공란으로 둔 PDF**를 만든다
- [ ] `applicant` / `account` 객체가 없거나 `null`이어도 전부 공란과 같게 처리한다
- [ ] 형식 검증은 한다 — 각 필드 **최대 100자**, `birthDate`는 값이 있으면 `YYYY-MM-DD`. 위반 시 `400` + **`INVALID_FORM_FIELD`**
- [ ] **`excludedSentenceIds`의 문장은 2면 생성 시 제외**한다. 선택이며 기본 빈 배열. **세션에 상태를 만들지 않는다** — 다운로드 시점에 한 번 전달되고 끝이다. 존재하지 않는 id는 무시한다
- [ ] 받은 값은 **PDF 생성에만 쓰고 세션·DB·로그 어디에도 남기지 않는다.** 접근 로그 필터에서 **이 경로의 요청 바디를 제외**한다 (`../../docs/03-infra-ops/privacy-and-safety.md`)

> **"선택"인 이유**: 사용자가 계좌번호나 개설점포를 모르는 경우가 실제로 있다. 이 산출물은 제출용 완성본이 아니라 **작성 지원본**(FR-047)이므로, 모르는 값 하나 때문에 패키지 생성이 막히면 서비스가 목적을 잃는다. 프론트도 폼에 필수 표시(`*`)를 붙이지 않는다.
>
> **`holderName`**: 프론트가 "신청인과 동일" 체크박스를 **기본 체크**로 두고 `applicant.name`을 실어 보낸다. 법 제7조 제1항의 이의제기 주체가 명의인이라 둘이 다른 경우가 예외적이다. **체크박스 상태는 계약에 없다** — 바디에는 항상 최종 문자열이 온다.

## 5-4a. `POST /api/draft/revise` — 문장 수정·제외 (2026-08-25 신설)

> **일정: 8/29~8/31.** 프론트가 자유 편집을 이 구간으로 앞당겼고 백엔드가 수용했다. 어려워지면 프론트에 알린다 — 프론트는 읽기 전용 + 문장 제외로 먼저 완성해 두고 자유 편집만 9/1~9/2로 되돌린다.

```json
{ "sentences": [ { "sentenceId": "s3", "excluded": true },
                 { "sentenceId": "s5", "text": "2026년 9월 1일 물품을 발송하였습니다." } ] }
→ { "sentences": [...], "warning": "수정하신 문장은 업로드 자료와 연결되지 않아 '본인 진술'로 표시됩니다." }
```

- [ ] **`text`와 `excluded`를 분리해 받는다.** `text: ""`를 삭제 신호로 쓰지 않는다 — 되돌릴 수 없고, 빈 문자열과 공백 입력을 구분해야 하는 부담이 생긴다
- [ ] **`text`가 바뀐 문장만 F7-02 재검증한다.** `excluded`는 재검증하지 않는다 — 문장을 빼는 것은 새 사실을 만들지 않고, 남은 문장은 이미 검증을 통과했다
- [ ] **⚠️ 재검증에서 매칭이 끊겨도 문장을 삭제하지 않는다.** `evidenceRefs`를 `[{ "type": "user_text" }]`로 바꾸고 `warning`을 함께 내린다. **FR-045 ③의 자동 삭제는 LLM 출력에만 적용**된다 (`prd.md` FR-045 ③ 2026-08-25 개정) — 사람이 자기 사실을 적은 문장에 같은 규칙을 쓰면 성격이 다르고, ⑤가 이미 `user_text`에 "본인 진술" 표기를 규정하고 있다
- [ ] `warning`은 **화면에 그대로 나가는 문자열**이다. 프론트가 순화하지 않는다
- [ ] 수정 결과를 세션의 `sentenceEvidence`에 반영한다 — 이후 `/api/package/text`가 이 값으로 2면을 만든다

| ① | 별지 제4호서식 작성 지원본 | 서버 |
| ② | 사실관계 진술서 | 서버 |
| ③ | 시간순 거래 타임라인 | 서버 |

| ~~⑥~~ | ~~부족한 자료 체크리스트~~ | **제외 (화면에는 유지)** |

**표지(⓪) 내용**

```
제출 서류 목록

이 문서에 포함된 것
  1. 이의제기신청서 (작성 지원본)     4. 증빙자료 목록
  2. 사실관계 진술서                 5. 증빙 원본 이미지
  3. 거래 타임라인

신청인이 따로 첨부하는 것
  · 명의인 신분증 사본
  · 1면 서명란 자필 서명
```

- [ ] **못 갖춘 자료는 표지에 적지 않는다.** 갖춘 것과 따로 낼 것만 적는다 (TC-35)
- [ ] **자필 서명 안내가 PDF 안에 들어가야 한다** — 화면에만 있으면 파일만 받아 그대로 보낸 사용자가 서명 없이 제출한다
- [ ] 수용 기준(TC-13): 중고거래 시나리오(채팅·입금내역·배송자료만)로 패키지가 완성된다
- [ ] **신분증 사본은 패키지에 포함하지 않는다** (민감도 — 서비스에 업로드받지 않음)
- [ ] 접수 경로 표기: 시행령상 제출처는 **해당 계좌를 관리하는 금융회사**다. 금융감독원 민원을 같은 수준의 제출 방법으로 표시하지 않는다

## 완료 기준

- 확인된 카드만으로 소명서가 생성되고, 미확인 카드의 날짜·금액이 본문에 없다 (TC-11)
- 타임라인에 없는 사실이 최종본에 없다 (TC-08)
- 자료 0건이어도 최소 골격이 나오고 전 문장에 "본인 진술" 표기가 붙는다 (TC-06)
- 한글이 정상 렌더되는 PDF가 내려온다 (표지 + 1~4면)
- **제출본 어디에도 "미보유" 목록이 없다** (TC-34·35)
- 문장을 제외하면 2면에서 빠지고, 수정하면 배지가 "본인 진술"로 바뀐다 (TC-32·33)

## 단위 테스트 (Phase 5 범위)

- `factCheckPassed == false` → 재생성 1회 후 문단 생략 (무한 루프 없음)
- `confirmed == false` 카드가 `/internal/draft` 요청 본문에서 제외됨
- 사유별 체크리스트 매핑 (**`fss` 층은 물품·용역 2종만, 나머지는 `common`**)
- `excludedSentenceIds`의 문장이 2면 렌더 결과에서 빠짐 (TC-32)
- `/api/draft/revise`에서 **매칭이 끊겨도 문장이 삭제되지 않고** `user_text` + `warning`으로 나감 (TC-33)
- 서식 11필드가 전부 빈 값이어도 `400`이 나지 않고 공란 PDF가 생성됨 (TC-14)
- **4면에 파일명·보유여부가 없고, 3면에 `gaps`가 없음** (TC-34)
