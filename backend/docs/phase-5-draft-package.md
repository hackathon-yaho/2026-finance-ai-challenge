# Phase 5 — 소명서 생성 · 제출 패키지

> 목표: 확인된 타임라인 + 준비도 결과로 소명서를 받아오고, 제출 패키지 텍스트 5종을 만든다.
>
> 근거: `../../docs/00-context/spec.md` F7-01~06·F8-01, `../../docs/02-architecture/api-contract.md`, `../../docs/02-architecture/internal-api-contract.md`

## 5-1. `POST /api/draft` (F7-01)

백엔드는 문장을 **생성하지 않는다.** AI-server를 호출하고 결과를 검사해 전달한다.

### 내부 호출

```json
POST /internal/draft
{
  "events": [ /* confirmed=true 카드만 */ ],
  "reason": "goods | service | debt | unclear",
  "readiness": "SUBMISSION_READY | SUPPLEMENT_NEEDED | BANK_CHECK_REQUIRED"
}
```

- [ ] **`confirmed=true` 카드만 전달한다** (F4-06 소명서 반영, TC-11)
- [ ] `reason`·`readiness`는 `ReadinessService`가 이미 결정한 값을 그대로 넘긴다. **AI-server는 이 값을 재해석하지 않는다** — 백엔드도 AI 응답을 근거로 준비도를 다시 계산하지 않는다
- [ ] 타임아웃 15초, 재시도 1회

### 사실 검증 실패 처리 (F7-02 / FR-045)

- [ ] 응답의 `factCheckPassed == false`면 **그대로 프론트에 전달하지 않는다**
- [ ] 재생성 **1회로 제한**한다. 재실패 시 해당 문단을 생략한다 (`prd.md` §10.3)
- [ ] **무한 루프 방지** (F7-02 개발 주의)

### 응답 (`api-contract.md`)

```json
{
  "draftText": "...",
  "sentences": [{ "sentenceId": "s1", "text": "...", "evidenceRefs": [{ "type": "evidence", "imageIndex": 2, "bbox": {...} }] }],
  "checklist": [{ "item": "거래 대화 캡처", "have": true }]
}
```

- [ ] `sentences`를 세션의 `sentenceEvidence`에 보관한다 — **참조(imageIndex, bbox)만. 이미지 바이트 금지** (`data-model.md`)
- [ ] **응답의 `checklist`는 백엔드가 자기 값으로 채운다.** `/internal/draft` 응답에도 `checklist`가 들어 있지만 **첨부 서류 체크리스트(F7-03)의 담당은 `A`(백엔드)** 이고 내용이 결정적(사유별 고정 목록 + 보유 여부)이므로, AI가 준 값을 그대로 흘리지 않는다. 두 값이 다르면 사용자는 Stage 3과 Stage 4에서 서로 다른 체크리스트를 보게 된다
- [ ] 프론트는 이 참조로 자기 브라우저 blob에서 원본을 찾는다. **서버에서 원본을 다시 내려주지 않는다** (FR-046)

## 5-2. 재생성 (F7-04)

- [ ] Stage 2 복귀 → 증거 추가 → Stage 4 재진입 시 타임라인 갱신 후 F7-01 재실행
- [ ] 수용 기준: **협박 문자를 추가하면 협박 수신 사실 문단이 새로 생긴다** (발표 데모 `[2:40]`)

> 협박 문단의 문안은 F10-04에 고정되어 있고 **"편취 의도가 없었음을 반증한다", "결백을 증명한다" 같은 결론적 표현은 금지**다. 다만 이 제약은 **AI-server의 프롬프트 제약**이며(`../../docs/00-context/prd.md` §10.2), 백엔드가 문장을 검열하는 역할은 문서에 정의되어 있지 않다. 백엔드의 책임은 `factCheckPassed == false`일 때 재생성 1회로 제한하는 것까지다.

## 5-3. 첨부 서류 체크리스트 (F7-03 / FR-041~042)

- [ ] Phase 4의 사유별 체크리스트 데이터를 재사용한다 (두 벌로 나누지 않는다) — **Stage 3(`/api/readiness`)과 Stage 4(`/api/draft`)가 같은 소스에서 나와야 한다**
- [ ] 미보유 항목 표기: **"미보유 — 보완 요청 사유가 될 수 있습니다"**
- [ ] 신분증 사본 = "서비스 업로드 대상 아님, 제출 시 직접 첨부"
- [ ] 세금계산서는 필수로 노출하지 않는다

## 5-4. `GET /api/package/text` — 텍스트 5종 PDF (F8-01 / FR-043)

> ⚠️ **미확정 — 생성 주체.** `spec.md` 총괄표는 F8-01 담당을 `C`(프론트)로 적었으나, F7-06·F8-01 본문·`api-contract.md`·배포 체크리스트는 모두 서버 생성을 전제한다. 프론트 회신 전까지 착수하지 않는다. 요청: `../../docs/request/frontend/pdf-ownership-and-open-contracts.md`

**서버 생성으로 확정될 경우**의 작업이다.

- [ ] 5면 구성 (F8-01)
  1. 시행령 별지 제4호서식 이의제기신청서 **작성 지원본**
  2. 사실관계 진술서 (F7-01)
  3. 시간순 거래 타임라인 (F5-01)
  4. 증빙자료 목록
  5. 부족자료 체크리스트 (F7-03)
- [ ] 파일명 `이의제기패키지_YYYYMMDD.pdf`
- [ ] 라이브러리: OpenPDF 또는 Apache PDFBox
- [ ] **한글 폰트** — Phase 1에서 넣은 나눔고딕을 사용한다. 없으면 전부 깨진다
- [ ] 각 면 하단 고정 표기: **"AI 초안 · 사용자 확인 완료 {시각} · 최종 판단은 금융회사"**
- [ ] **원본 이미지 페이지는 서버가 만들지 않는다.** 프론트가 자기 blob으로 만들어 `pdf-lib`으로 병합한다 (F7-06 분담)

### 별지 제4호서식의 인적사항 문제 (해결 필요)

PRD §4.4 필드 매핑상 신청인 성명·생년월일·주소·연락처, 금융회사·개설점포·예금종별·계좌번호는 **사용자 직접 입력(서비스 미저장, PDF 생성 시에만 사용)**이다. 그런데 계약상 이 엔드포인트는 `GET`이라 값을 받을 자리가 없다.

- [ ] 서버 생성으로 확정되면 **`POST /api/package/text`로 전환**하고 `api-contract.md`를 개정한다
- [ ] 받은 인적사항은 **PDF 생성에만 쓰고 세션·DB·로그 어디에도 남기지 않는다**

## 5-5. 제출 패키지 6종 (F7-06 / FR-047)

| # | 산출물 | 생성 주체 |
| --- | --- | --- |
| ① | 별지 제4호서식 작성 지원본 | 서버 |
| ② | 사실관계 진술서 | 서버 |
| ③ | 시간순 거래 타임라인 | 서버 |
| ④ | 증빙자료 목록 | 서버 |
| ⑤ | 증빙별 원본 이미지 | **브라우저** |
| ⑥ | 부족한 자료 체크리스트 | 서버 |

- [ ] 수용 기준(TC-13): 중고거래 시나리오(채팅·입금내역·배송자료만)로 6종이 완성된다
- [ ] **신분증 사본은 패키지에 포함하지 않는다** (민감도 — 서비스에 업로드받지 않음)
- [ ] 접수 경로 표기: 시행령상 제출처는 **해당 계좌를 관리하는 금융회사**다. 금융감독원 민원을 같은 수준의 제출 방법으로 표시하지 않는다

## 완료 기준

- 확인된 카드만으로 소명서가 생성되고, 미확인 카드의 날짜·금액이 본문에 없다 (TC-11)
- 타임라인에 없는 사실이 최종본에 없다 (TC-08)
- 자료 0건이어도 최소 골격이 나오고 전 문장에 "본인 진술" 표기가 붙는다 (TC-06)
- (서버 생성 시) 한글이 정상 렌더되는 5면 PDF가 내려온다

## 단위 테스트 (Phase 5 범위)

- `factCheckPassed == false` → 재생성 1회 후 문단 생략 (무한 루프 없음)
- `confirmed == false` 카드가 `/internal/draft` 요청 본문에서 제외됨
- 사유별 체크리스트 4종 매핑
