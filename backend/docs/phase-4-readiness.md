# Phase 4 — 제출 준비도 점검 (결정적 규칙 엔진)

> 목표: `POST /api/readiness`가 세 상태 중 하나를 결정적으로 산출한다.
>
> 근거: `../../docs/01-product/reason-type-rules.md` (단일 출처), `../../docs/00-context/spec.md` F6-01~06, `../../docs/00-context/prd.md` §4.3

## 이 Phase의 절대 원칙

> **제출 준비도 점검은 AI가 하지 않는다.** `ReadinessService`는 결정적 규칙으로 구현한다. LLM 호출 금지, 임의 스코어링 금지, 승인·기각 예측 금지.
> — `../../docs/01-product/reason-type-rules.md` §0, `../../docs/02-architecture/system-architecture.md` 컴포넌트 책임표 "절대 하지 않는 것"

**이 경계가 무너지면 심사 방어 논리 전체가 무너진다.** 구현 중 "여기서 LLM을 한 번 부르면 편할 텐데" 싶은 지점이 나오면, 그게 바로 부르면 안 되는 지점이다.

## 4-1. 사유유형 확정 (F6-01)

문진 응답을 **그대로 매핑**한다. 추론하지 않는다.

| 문진 `kind` | 사유유형 | 응답 `reason` |
| --- | --- | --- |
| 중고 물건 판매 (`goods`) | 재화 거래 대금 | `goods` |
| 용역·알바 대가 (`service`) | 용역 제공 대가 | `service` |
| 빌려준 돈 회수 (`debt`) | 채권 회수 | `debt` |
| 잘 모르겠음 (`unclear`) | 사유 미확정 | `unclear` |

- [ ] 매핑 구현
- [ ] `unclear`이면 F6-02 확인 질문으로 분기

## 4-2. 확인 질문 (F6-02 / FR-031)

- [ ] 트리거: 거래 성격 = '잘 모르겠음'
- [ ] 질문 "돌려받은 돈이 맞나요?" + 4개 선택지
- [ ] **1회만.** 반복 질문 금지 (F6-02 횟수)
- [ ] 응답이 '잘 모르겠습니다'면 **사유 미확정으로 그대로 진행**한다

근거 페르소나 P-05(차용증 없는 채권 회수) — TC-05.

## 4-3. 증빙 충족·누락 점검 (F6-03)

- [ ] **입력은 `user_confirmed` 또는 `user_corrected` 카드뿐이다.** 미확인 카드는 충족 근거로 쓰지 않는다 (F6-03 수용 기준)
- [ ] 점검 대상은 F7-03 사유별 체크리스트 (Phase 5 표와 동일한 데이터를 공유한다)
- [ ] 항목별 출력 3값 — spec 본문의 한글 표기와 계약 필드명의 대응은 다음과 같다

| F6-03 본문 표기 | `api-contract.md` `status` 값 |
| --- | --- |
| 충족 | `met` |
| 보완 필요 | `unmet` |
| 확인 필요 | `unknown` |
- [ ] **금지: 입금액으로 소액 여부를 판정하지 않는다.** 금액은 사실 정보로만 기록

### 사유별 증빙 (F7-03) — 3단 구조

> **2026-08-25 개정.** 종전에는 사유 4종에 각각 "필수 증빙" 목록을 뒀으나, **금감원 표준은 물품 거래·용역/급여 2종뿐**이고 나머지는 근거 없이 만든 목록이었다. 단일 출처는 `../../docs/01-product/reason-type-rules.md` §2다.

**① 법정 첨부서류 (필수 · 전 유형 공통)** — 시행령 제7조

- 사기이용계좌가 아니라는 사실을 증명하는 자료 → **우리 산출물 전체**가 여기 해당
- 신분증 사본 → **서비스 업로드 대상 아님. "제출 시 직접 첨부"로 표시**

**② 금감원 표준 소명자료 (2종만)**

| 사유 | 항목 |
| --- | --- |
| 재화 거래 대금 (`goods`) | 사업자등록증 / 거래상대방 대화내역 / **계약서·세금계산서·거래명세서 중 택일** / 구매자–송금인 일치 여부 |
| 용역 제공 대가 (`service`) | **건강보험자격득실확인서·재직증명서 중 택일** / 급여 입금내역 |
| 채권 회수 (`debt`) · 사유 미확정 (`unclear`) | **표준 없음** → ③ 적용 |

- [ ] **택일 항목은 OR로 구현한다.** 그룹 안에서 하나라도 충족되면 그룹 전체가 `met`. 전부 AND로 묶으면 금감원이 완화한 기준을 되돌리는 것이 된다
- [ ] `필수증빙누락` 신호는 **②에만** 반응한다. ③·④는 이 신호에 넣지 않는다

**③ 공통 최소 자료 (표준 없는 유형 · 참고 안내)**

거래 상대방 대화·연락 기록 / 계좌 거래내역 / 상대–송금인 일치 확인 자료 / (대여 관계라면) 차용증·이체 기록

- [ ] **`status`를 `unmet`으로 내리지 않는다.** 참고 안내이므로 미보유여도 준비도를 깎지 않는다

**④ 보강 자료 (전 유형 공통 · 선택)**

재직증명서 / 소득금액증명원 / 예금거래내역서 — **업로드받지 않고 직접 첨부 안내만.** 준비도 산출 입력에서 제외한다.

> **개발 주의**: **②를 관문으로 만들지 않는다.** 개인 중고거래자는 사업자등록증이 없어 물품 거래 표준을 채울 수 없다. 그렇다고 이의제기가 막히는 게 아니므로(①의 "증명하는 자료"는 자유 형식), 사업자등록증 미보유만으로 `SUPPLEMENT_NEEDED`를 내지 않도록 주의한다.
>
> **세금계산서는 필수 항목이 아니다.** ②의 택일 선택지 중 하나로만 노출한다 (F7-06 제외 항목).

## 4-4. 준비도 산출 (F6-04 / FR-033) — 핵심

`../../docs/01-product/reason-type-rules.md` §3의 의사코드를 **그대로** 옮긴다.

### 네 가지 신호

| 신호 | 정의 |
| --- | --- |
| `hasUnconfirmedFields` | 사용자가 확인하지 않은 카드 또는 낮은 신뢰도 필드가 남아 있음 |
| `hasMissingRequiredEvidence` | 사유별 체크리스트에 미보유 항목이 있음 |
| `hasConflicts` | `signals.quality_flags.amount_mismatch` 또는 날짜·배송상태 불일치 |
| `hasUnknownBankCriteria` | **과거 지급정지 이력 있음** OR 은행 내규 기준을 서비스가 알 수 없는 항목 |

### 산출

```java
if (hasUnconfirmedFields || hasMissingRequiredEvidence) return SUPPLEMENT_NEEDED;
if (hasConflicts || hasUnknownBankCriteria)             return BANK_CHECK_REQUIRED;
return SUBMISSION_READY;
```

- [ ] 4신호 산출 + 3분기 구현
- [ ] **순서를 바꾸지 않는다.** `SUPPLEMENT_NEEDED`가 먼저다
- [ ] 새로운 조건을 추가하지 않는다 — 추가하려면 "금감원 발표 또는 법령의 어느 조항인가"를 먼저 확인한다 (`reason-type-rules.md` §0)

## 4-5. 응답 스키마

```json
{
  "reason": "goods | service | debt | unclear",
  "checklist": [{ "item": "거래 대화 내역", "status": "met | unmet | unknown" }],
  "readiness": "SUBMISSION_READY | SUPPLEMENT_NEEDED | BANK_CHECK_REQUIRED",
  "missingItems": ["물품 발송 증빙"],
  "conflicts": [],
  "notices": ["최종 판단은 은행이 합니다"],
  "smallAmountNotice": "특정 소액 입금 건은 ...",
  "urgentAlert": false
}
```

- [ ] **`notices`에 "최종 판단은 은행이 합니다"를 세 상태 모두에 항상 포함한다** (`api-contract.md`, F6-04)
- [ ] `urgentAlert`는 협박 감지 여부이며 **`readiness`와 독립적으로** 산출한다
- [ ] `hasConflicts`의 입력인 `amount_mismatch`는 **Phase 3의 금액 교차 대조(F4-07)** 가 세운다. 그쪽이 구현되지 않으면 이 분기는 영원히 false다

## 4-6. 금지 문구 (신뢰의 핵심 지점)

`../../docs/01-product/reason-type-rules.md` §4.

- **금지**: "기각될 수 있습니다" / "해제 가능성이 높습니다" / "그래도 해볼 만합니다" / "혹시 모르니 신청해보세요" — 결과 예측·낙관·위로 표현 일체
- **허용(과거 이력 케이스 고정 문구)**: "과거 지급정지 이력이 있어 간소화 절차 대상이 아닐 수 있습니다. 은행 확인이 필요하며, 최종 판단은 은행이 합니다."

- [ ] 위 문구를 상수로 고정한다. 백엔드가 문구를 조합·변형하지 않는다

## 4-7. 업무처리 기간 안내 (F6-05)

- [ ] **상태별 예측값을 만들지 않는다. 세 상태 모두에 동일한 고정 문구를 내려준다.**
- [ ] 고정 문구 (F6-05, 토씨 그대로):

> "이의제기신청서와 소명자료를 충분히 구비하여 제출한 경우 금융회사는 5영업일 내 심사결과를 통보합니다. 자료 보완이 필요한 경우 처리기간이 추가될 수 있으며, 5영업일 내 지급정지 해제를 보장하는 것은 아닙니다."

- [ ] **누락 개수로 연장일수를 자동 예측하지 않는다** (FR-034)

## 4-8. 준비도 근거 설명 (F6-06)

- [ ] **검증된 고정 문구 템플릿만 사용한다. LLM 다듬기를 쓰지 않는다** (문구 변형으로 인한 오안내 방지)
- [ ] 예: "배송 증빙이 확인되지 않아 보완이 필요합니다"

> 총괄표는 담당을 `B`(AI)로 적었으나 본문이 "LLM 사용 안 함"을 명시하므로 **백엔드가 고정 템플릿으로 구현**한다. 스코프 컷 순서 3번이라 밀리면 고정 문구 1종으로 축약한다.

## 4-9. 소액 안내 카드 (판정이 아닌 정보 제공)

- [ ] **`smallAmountNotice` 필드**로 고정 문구만 노출한다 (2026-08-23 계약 추가, PRD §4.3):

> "특정 소액 입금 건은 금융회사 판단에 따라 간소화된 일부지급정지 절차가 적용될 수 있습니다. 정확한 금액 기준과 적용 여부는 해당 금융회사에 확인해야 합니다."

- [ ] **"소액에 해당하니 유리하다"처럼 단정하지 않는다**
- [ ] **입금액에 따라 문구를 바꾸지 않는다.** 항상 같은 고정 문구다 — 소액 여부를 서비스가 판정하지 않기 때문이다 (§14 OI-01)
