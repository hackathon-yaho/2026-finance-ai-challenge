# [프론트 → AI] 실제 전송 이미지의 해상도·포맷 — 회신

- 작성: 프론트엔드 · 2026-08-25
- 원본 요청: `../../request/frontend/image-delivery-spec.md` (AI · 2026-08-25)

**결론 먼저: 장변 1600px 리사이즈는 적용돼 있습니다.** 그리고 AI 담당이 세우신 "본문 약 27px" 추정은 **실측과 거의 일치**합니다(27.3px). 다만 **캔버스 세로 길이는 실전과 다릅니다** — §3을 봐주세요.

## 1. 물어보신 값 3개

세로로 긴 모바일 캡처(1080×2340) 기준입니다.

| 항목 | 값 |
| --- | --- |
| **가로×세로 픽셀** | **738 × 1600** |
| **포맷** | **`image/png`** (JPEG 미사용 — 압축 품질 개념 없음) |
| **파일 크기** | **약 135KB** (대화 캡처 기준) |

`canvas.toBlob(..., "image/png")` 고정입니다. 텍스트가 많은 캡처라 JPEG 링잉이 판독에 불리하다고 보고 PNG로 뒀습니다 (`frontend/src/lib/mask.ts` 주석에 근거를 남겨뒀습니다).

### 입력 해상도가 달라도 전송본은 같습니다

장변만 1600으로 캡하고 비율을 유지하므로, 세로 캡처는 대부분 **가로 700~740 / 세로 1600**으로 수렴합니다.

| 원본 (기종 예) | 전송본 | 크기 |
| --- | --- | --- |
| 1080×2340 (일반 안드로이드) | **738×1600** | 135KB |
| 1179×2556 (iPhone 15 Pro) | **738×1600** | 143KB |
| 720×1180 (장변 1600 미만) | **720×1180** (그대로) | 93KB |

세 번째 줄이 중요합니다 — **확대하지 않습니다.** `Math.min(maxEdge / longEdge, 1)`이라 원본이 작으면 그대로 나갑니다.

### 10MB 상한 여유

대화 캡처는 135KB 안팎이라 여유가 큽니다. **PNG 최악 조건**(캡처 안에 사진·썸네일이 크게 들어가 무손실 압축이 거의 안 되는 경우)을 일부러 만들어 재보니 **약 1.6MB**였습니다. 그래도 상한의 16% 수준이라 계약 10MB는 넉넉합니다.

## 2. 1600px 리사이즈 — **적용됨**

요청 마지막에 확인 요청하신 항목입니다. 코드에 들어가 있습니다.

| 위치 | 내용 |
| --- | --- |
| `frontend/src/lib/upload.ts` | `MAX_IMAGE_EDGE = 1600` (F3-01 처리 ①) |
| `frontend/src/lib/mask.ts` — `exportSizeFor()` | 장변을 1600으로 캡, **확대는 하지 않음** |
| `frontend/src/lib/mask.ts` — `exportMaskedBlob()` | **화면 캔버스를 내보내지 않고 원본 이미지에서 export 해상도로 다시 그립니다** |

말씀하신 **199×431 사고**는 마지막 줄이 원인이었고, 지금은 구조적으로 재발하지 않습니다. 마스킹 시트의 캔버스는 화면 폭(예: 논리 335px)에 맞춰져 있지만 전송본은 그 캔버스가 아니라 원본에서 새로 그린 것이라, **전송 해상도가 보는 사람의 화면 크기·DPR에 좌우되지 않습니다.** 마스킹 박스만 시트 좌표계에서 export 좌표계로 스케일해 옮깁니다.

## 3. ⚠️ 평가 세트 캔버스 — 가로는 맞고 **세로가 짧습니다**

가장 도움이 될 것 같은 부분이라 따로 적습니다.

| | AI 평가 세트 (현재) | 실제 전송본 |
| --- | --- | --- |
| 캔버스 | 720 × **1180** | 738 × **1600** |
| 본문 글자 | 약 27px | **27.3px** |

**글자 크기 추정은 맞았습니다.** 원본 1080폭에서 카카오톡 본문이 약 40px인데, 738폭으로 줄면 `40 × 738/1080 = 27.3px`입니다. 가로도 720 vs 738이라 사실상 같습니다. **이 축으로는 재생성이 필요 없습니다.**

다른 건 **세로**입니다. 실전 전송본은 1600px인데 평가 세트는 1180px이라, **한 장에 담기는 대화량이 실전보다 약 26% 적습니다.** 이게 영향을 주는 지점은 글자 판독이 아니라 **이벤트 분리**입니다 — 실제 캡처 한 장에는 말풍선이 더 많이 들어가고, 그만큼 한 요청에서 뽑아야 할 이벤트 수와 `source_type`이 섞일 확률이 올라갑니다(대화 캡처 안의 송금 알림처럼요). 지금 세트로 재면 그 조건이 실전보다 쉽게 나올 수 있습니다.

**제안**: 캔버스를 **738×1600**으로 바꾸고 글자 크기는 지금(27px)을 유지한 채 **콘텐츠를 세로로 더 채우는** 방향을 권합니다. 글자 크기가 그대로라 판독 난도 자체는 안 바뀌고, 이벤트 밀도만 실전에 맞습니다. 다만 **재생성 비용과 회차 간 비교 가능성이 깨지는 손해**가 있으니 판단은 AI 담당께 맡기겠습니다 — 지표가 이미 목표를 넘고 있으면 굳이 흔들 필요는 없다고 봅니다.

## 4. 측정 방법 (재현 가능하게)

값을 눈으로 읽은 게 아니라 **실제 업로드 코드 경로에 태워서** 뽑았습니다.

1. 개발 서버(`npm run dev`)를 띄우고 브라우저에서 `src/lib/mask.ts`·`src/lib/upload.ts`를 그대로 import
2. 카카오톡 대화 캡처 형태(상태바 · 상대 표시명 · 말풍선 7개 · 입금 알림 카드 · 입력바)를 **1080×2340 캔버스로 합성**
3. 그 PNG를 `File` → `objectURL` → `loadImage()` → **`exportMaskedBlob(image, boxes, logicalSize, MAX_IMAGE_EDGE)`** 로 실제 전송 경로 그대로 통과
4. 나온 blob의 `naturalWidth/Height` · `type` · `size`를 기록

> **개인 캡처는 쓰지 않았습니다.** 요청하신 대로 값만 필요했고, 합성 캡처로 냈습니다. 그래서 **파일 크기(135KB)는 "이런 화면이면 이 정도"라는 대표값**이지 사용자 캡처의 실측 분포는 아닙니다. 해상도·포맷은 콘텐츠와 무관하게 결정적이므로 그대로 믿으셔도 됩니다.

## 5. 프론트가 앞으로 지킬 것

- **전송 포맷·해상도 규칙을 바꾸면 이 문서를 갱신하고 AI 담당께 알리겠습니다.** 평가 세트 조건이 여기에 묶여 있으니 조용히 바꾸면 안 되는 값으로 취급하겠습니다.
