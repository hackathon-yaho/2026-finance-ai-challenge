## 2. 결정이 필요했던 항목의 근거

### 2-1. 서식 8개 필드는 **전부 선택**입니다

"사용자가 계좌번호를 모르는 경우가 실제로 있다"는 지적을 그대로 받았습니다.

- 빈 값이어도 **`400`을 내지 않습니다.** 해당 칸을 **공란으로 둔 PDF**가 나옵니다.
- 공란 항목은 **5면 부족자료 체크리스트에 "직접 채워야 하는 항목"으로 표시**합니다. 사용자가 무엇을 더 채워야 하는지 모른 채 은행에 가는 상황을 막기 위해서입니다.
- `applicant` / `account` 객체 자체를 생략하거나 `null`로 보내도 됩니다. 8개 전부 공란과 같게 처리합니다.

이 산출물은 제출용 완성본이 아니라 **작성 지원본**입니다(FR-047). 모르는 값 하나 때문에 패키지 생성 자체가 막히면 서비스가 목적을 잃습니다.

**다만 형식 검증은 합니다.** "선택"은 *비어도 된다*는 뜻이지 *무엇이든 받는다*는 뜻이 아닙니다.

| 검증 | 위반 시 |
| --- | --- |
| 각 필드 문자열 최대 100자 | `400` + `INVALID_FORM_FIELD` |
| `birthDate`는 값이 있으면 `YYYY-MM-DD` | `400` + `INVALID_FORM_FIELD` |

**프론트 폼 검증은 "빈 값 허용 + 길이/형식만 확인"으로 짜시면 됩니다.** 필수 표시(`*`)는 붙이지 마세요 — 빈 칸을 못 넘어가는 폼이 되면 위 결정이 무의미해집니다.

응답은 **`application/pdf` 바이너리**가 맞습니다. 그대로 `pdf-lib`에 넘기시면 됩니다.

### 2-2. `mergeCandidates` — 제안 그대로 + `reason` 조건 하나

```json
"mergeCandidates": [
  { "groupId": "mg_001", "eventIds": ["evt_003", "evt_007"], "reason": "시각 차 2분 · 금액 700,000원 일치 · actor 동일" }
]
```

`reason`은 **사용자에게 그대로 보여줄 수 있는 문장**으로 내려갑니다. 왜 같은 사건으로 보이는지 설명 없이 병합을 승인받아서는 안 되기 때문입니다(F5-02 "자동 확정하지 않는다"의 취지).

`POST /api/timeline/merge`의 `mergeGroupIds`는 **`groupId`의 배열**입니다(`eventId`가 아닙니다 — 8/23 요청서의 예시가 헷갈리게 적혀 있었습니다. 정정합니다). `approved: false`는 후보 **거절**로 기록해 이후 응답에서 제외하며 이벤트는 그대로 둡니다.

**스코프 컷 처리도 계약에 못 박았습니다.** 컷하면 백엔드는 `mergeCandidates`를 **항상 빈 배열**로 내리고 승인 엔드포인트를 구현하지 않습니다. 프론트는 빈 배열이면 후보 UI를 렌더하지 않으면 됩니다 — 말씀하신 대로 양쪽이 서로를 기다리지 않고 같이 컷됩니다. **컷 결정이 나면 이 폴더에 회신하겠습니다.**

### 2-3. `deadline.notice`는 **어떤 경우에도 `null`이 아닙니다**

`date`/`daysLeft`가 `null`(공고일 미입력)일 때는 "공고일을 모르는 경우"에 해당하는 문구가 `notice`에 대신 들어갑니다. **`notice`가 항상 존재한다는 전제로 화면을 짜셔도 됩니다.**

`src/lib/deadline.ts` 폐기 계획에 동의합니다. 문구는 서버가 단일 소스입니다.

### 2-4. 동시 요청 상한은 **4**입니다

10장이면 **4 → 4 → 2**로 끊어 보내주세요.

- 백엔드 → AI-server 구간이 이미 최대 4 동시라(F4-01), 10장을 한꺼번에 던져도 백엔드에서 큐가 쌓일 뿐 처리량은 늘지 않습니다.
- Render 인스턴스가 **512MB RAM / 0.1 CPU**입니다. 이미지는 서버에 저장되지 않고 메모리로만 통과하므로(F3-01) **동시 개수가 곧 메모리 점유**입니다. 1600px PNG 10장 동시는 OOM 위험이 있습니다.
- 상한을 넘겨 도착해도 **거부하지 않고 큐잉**합니다. 4는 거부선이 아니라 발신 상한입니다.

### 2-5. 프리뷰 도메인 와일드카드는 **허용하지 않습니다**

`*.vercel.app` 류를 열면 임의의 브랜치·포크 배포에서 이 API를 호출할 수 있게 됩니다. **프로덕션 도메인 1개 + `http://localhost:5173`** 으로 갑니다. "후자여도 문제없다"고 하셔서 안전한 쪽을 택했습니다.

`http://localhost:5173`은 **이미 허용 origin에 등록**했습니다. 도메인 확정을 기다리지 말고 로컬 연동 착수하셔도 됩니다.

허용 헤더는 `Content-Type`, `X-Session-Hash`. 허용 메서드는 `GET`, `POST`, `DELETE`, `OPTIONS`입니다.

## 3. 회신에서 새로 알려주신 항목 — 처리 결과

### 3-1. multipart 1MB 기본값 — **고쳤습니다. 알려주셔서 살았습니다**

`spring.servlet.multipart.max-file-size` / `max-request-size`를 **10MB**로 올렸습니다(F3-02 검증 ③에 맞춤). 그대로 뒀으면 1600px 리사이즈된 **정상 이미지가 전부 `400`**으로 떨어졌을 상황입니다. Render 프록시 바디 상한도 배포 체크리스트에 넣었습니다.

전송 해상도가 199×431까지 줄어 있었다는 것도 중요한 정보였습니다. **F4-01 판독 정확도 문제의 원인이 여기였을 가능성이 높습니다** — 그 해상도로는 계좌번호·시각·금액을 사람도 못 읽습니다. `spec.md` F3-01 개발 주의에 이 사례를 실측값과 함께 남겨뒀습니다.

PNG 유지 판단에 동의합니다. 텍스트 캡처에 JPEG 링잉은 판독에 불리합니다.

### 3-2. 매직바이트 서버 검증 — **합니다**

`spec.md` F3-02에 **검증 주체 행을 신설**해 클라이언트·서버 양쪽이 4종(확장자·매직바이트·10MB·10장)을 모두 검증한다고 못 박았습니다. 수용 기준도 "**서버 단독으로도** 거부되어야 한다"로 고쳤습니다. 지적하신 대로 위조 파일을 실제로 막는 건 서버 몫입니다.

### 3-3. 세션당 10장 프론트 구현 — 확인

백엔드도 호출이 나뉘어도 누적 10장을 유지합니다. 11장째는 `400`입니다.
