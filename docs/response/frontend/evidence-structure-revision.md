**후속 10건 전부 처리했습니다.** §8(플랫폼 유형)은 **B안 채택**입니다 — 제 요청서가 틀렸다는 지적이 맞습니다.

## 1. §8 플랫폼 거래 내역 — **B안 채택. 요청서가 틀렸습니다**

> 요청서는 "`EvidenceId`에 유형 추가"를 적으셨는데, **`EvidenceId`는 목 전용 타입입니다.**

**그대로 맞습니다.** 실제 카드 유형은 AI가 내려주는 `source_type` 6종 고정이고, 프론트가 유형을 하나 늘려도 AI가 그 값을 안 내려주면 **어떤 카드에도 안 붙습니다.** 제가 코드를 확인하지 않고 쓴 요청이었습니다.

**B로 갑니다.** 근거를 하나 보탭니다 — A로 가면 어제 AI가 근거를 붙여 확정한 **`threat(3)`·`autopay(4)` tie-break 순서를 다시 흔들게 됩니다**(`../backend/card-source-type.md`). 남은 13일에 3자 계약을 재개정할 값어치가 없고, 말씀대로 **판독 내용 자체는 `chat`으로 분류돼도 그대로 추출**됩니다.

- `spec.md` **F3-07 ①에 "중고거래 앱(당근마켓·번개장터 등) 거래 내역"을 명시**했습니다. 문구 한 줄 더해주시면 됩니다.
- AI에는 요청을 보내지 않습니다.

## 2. §2 자료구조 — **제안하신 형태 그대로 계약에 넣었습니다**

`tier` / `fulfillBy` / `whenMissing` / `status` / `options` 전부 원안대로입니다. **백엔드가 이 모양에 맞춥니다.**

### 2-1. 층과 미보유 효과를 분리한 판단 — 이게 이번 회신에서 제일 중요합니다

TC-21과 TC-02가 같은 ②인데 기대 결과가 반대라는 지적을 보고 제 3단 구조를 다시 봤습니다. **제가 "근거가 어디서 나왔나"와 "못 채우면 어떻게 되나"를 한 축에 뭉쳐놨습니다.** 두 축으로 쪼갠 게 맞습니다.

**요청하신 판정 규칙을 `reason-type-rules.md` §3-1에 넣었습니다.**

> `blocks`는 **이미 존재하거나 즉시 발급받을 수 있는 자료에만** 붙입니다. 사후에 만들어야 하는 자료에 붙이면 서비스가 증거 조작을 유도하는 셈이 됩니다.

**"계약서·세금계산서를 사후에 만들면 증거 조작"** 이라는 지적은 제가 놓친 부분입니다. PRD가 "증거 생성·보정은 원칙적으로 금지"라고 못박은 영역이라, 이건 단순히 "채울 수 없다"보다 강한 이유입니다. 판정 표에 항목별 근거와 함께 적었습니다.

### 2-2. §2-6 `필수증빙누락` 정의 — **좁혔습니다**

지적하신 대로입니다. `reason-type-rules.md` §3을 고쳤습니다.

| | |
| --- | --- |
| 종전 | "사유별 체크리스트(FR-041)에 미보유 항목이 있음" |
| **지금** | **"`whenMissing: "blocks"`인 항목 중 `met`이 아닌 것이 있음"** |

`phase-4-readiness.md` 맨 위에 **착수 전 경고 블록**도 달았습니다 — 이 문서를 열자마자 보이도록. 종전 문장으로 구현하면 TC-21·TC-22가 깨진다는 걸 구현 시점에 놓치면 안 되기 때문입니다.

### 2-3. 카탈로그 소유 — **백엔드가 최종 소유하되, 제안하신 배치를 그대로 씁니다**

§2-7에서 "항목 구성은 백엔드가 최종 소유"라고 하신 것 맞습니다. **다만 제안하신 `whenMissing` 배치를 바꾸지 않았습니다** — §2-1 기준을 그대로 적용한 결과라 제가 다시 판단해도 같은 값이 나옵니다.

`legal.proof`를 **"확인된 업로드 자료 1건이라도 있으면 `met`"** 으로 두신 것도 그대로 갑니다. 자유 형식이라는 법정 요건의 성격과 정확히 맞고, TC-06이 `SUPPLEMENT_NEEDED`가 되면서도 **자료를 올리면 풀리므로** 가두는 요구가 아닙니다.

**신분증 사본을 `silent`로 두고 "눈에 띄는 자리"로 해결하신 것** — 이것도 그대로입니다. `blocks`면 전원이 영원히 보완 필요라는 지적이 맞습니다.

### 2-4. 자가 진술 저장 — **새 엔드포인트로 갑니다**

두 안 중 **`POST /api/checklist/self-held`** 를 택했습니다. 이유는 하나입니다.

체크리스트를 쓰는 화면이 **Stage 3(`/api/readiness`)과 Stage 4(`/api/draft`) 둘**입니다. `/api/readiness` 요청 바디에만 실으면 서버에 안 남아서, 사용자가 Stage 4로 넘어가면 draft는 그 체크를 모릅니다. **두 화면이 서로 다른 체크리스트를 보게 됩니다** — 제가 Phase 5 문서에 "Stage 3·4가 같은 소스에서 나와야 한다"고 못박아둔 바로 그 사고입니다.

```
POST /api/checklist/self-held   { "itemId": "...", "held": true }
→ 200 { "checklist": [ ... ] }     // 갱신된 전체
```

- 제안하신 이름 그대로입니다.
- **전체를 다시 내리는 것**도 그대로 — 택일 그룹은 옵션 하나가 바뀌면 그룹 상태도 바뀌므로 부분 갱신이 안 됩니다.
- **세션에만 두고 PDF·로그에 남기지 않습니다.** 붙여주신 조건 그대로입니다.

> **§2-4 정정("라벨 고정 + 체크 표시")도 반영했습니다.** `spec.md` F7-03에 넣었습니다 — "누를 때마다 글자가 바뀌면 그 글자가 *지금 상태*인지 *누르면 될 일*인지 알 수 없다"는 게 정확한 진단입니다. `blocks` 항목에 "이 항목을 표시해야 제출 준비 완료가 돼요"를 띄우는 것도 함께 명세했습니다.

## 3. §4 직거래 — **A안 확정. 필드명은 제안하신 그대로**

`deliveryMethod: "courier" | "in_person" | "not_applicable" | null` — 이름 바꾸지 않았습니다.

**물품 거래일 때만 묻는 것**도 그대로입니다. "용역·채권 회수에는 배송 개념이 없어 '해당 없음'만 고르게 되는 문항이 하나 생긴다"는 판단이 맞습니다. `spec.md`에 **F2-01a**로 조건부 문항을 신설했습니다.

**백엔드가 반영한 것**

| 문서 | 내용 |
| --- | --- |
| `api-contract.md` | `/api/intake` 요청에 `deliveryMethod` + 값별 처리 표 |
| `spec.md` **F5-03** | 탐지 규칙 ①에 **`deliveryMethod != "in_person"`** 조건 추가. 직거래 예외를 별도 행으로 명시 |
| `spec.md` F2-01a | 조건부 노출, 선택지, 후속 효과 3가지 |
| `test-cases-and-demo.md` | **TC-30** 신설 — 직거래 + 송장 없음에 공백이 안 뜨는지 |

`goods.delivery` 라벨을 `in_person`일 때 바꾸는 것도 F2-01a 후속 효과에 적었습니다. **F3-07 업로드 안내도 같이 바뀝니다** — 업로드 전에 "물품 사진·거래 장소"를 안내해야 하니까요.

## 4. §5 카드 이름 노출 — 확정 사항 수용

설계 5건 전부 그대로입니다. **"상대방" 라벨 폐기**도 동의합니다 — 대화 상대인지 입금자인지 모르면 사용자가 무엇을 정정하는지 알 수 없습니다.

**불일치 안내 문구는 백엔드가 씁니다.** `checklist[].note` 또는 `notices`로 내리겠습니다 — "대조 결과를 아는 쪽이 문구를 쓰는 게 맞다"는 판단 그대로입니다. `api-contract.md` `notices` 절과 `phase-4-readiness.md`에 명시했습니다.

**불일치를 준비도 신호에 넣지 않는 것**도 확정했습니다(`reason-type-rules.md` §2-1, Phase 4-4). 네 신호 어디에도 들어가지 않고 `needs_explanation` 상태로만 반영됩니다. TC-25·26으로 회귀 테스트를 걸었습니다.

## 5. §6·§7 — 반영 확인

- **신원·경제력**: `fulfillBy: "self"`로 해결됐다는 것 확인했습니다. "이걸 내면 통과됩니다" 류를 안 쓰신 것도 좋습니다.
- **수사 자료**: `whenMissing: "silent"`라 해당 없는 사람에게 아무것도 안 뜨는 구조 — 요청서의 의도 그대로입니다. `spec.md` **F9-02에 연결 규칙**을 적었습니다(문진 문항을 만들지 않는다는 조항 포함).

**"올리는 것 / 안 올리는 것" 기준으로 다시 가른 것이 맞습니다.** 업로드 화면인데 여기서 할 일이 먼저 보여야 한다는 게 제 원안보다 낫습니다.

| | 종전 (제 원안) | 지금 |

**§2-7 참조 구현은 백엔드가 `ReadinessService` 짤 때 대조용으로 쓰겠습니다.** TC 8건 실행 결과까지 붙여주신 게 큰 도움이 됩니다 — 제 구현이 다른 결과를 내면 그쪽이 틀린 것으로 보고 먼저 의심하겠습니다.

### ⚠️ 참조 구현을 보다가 하나 — `sources`는 응답에 없습니다

`frontend/src/types.ts`의 `ChecklistItem`이 `ChecklistEntry`를 `extends`해서 **`sources: EvidenceId[]`가 응답 타입에 딸려 들어가 있습니다.**

```ts
export interface ChecklistItem extends Omit<ChecklistEntry, "anyOf"> {
  status: ChecklistStatus
  options?: (ChecklistOption & { status: ChecklistStatus })[]
}
```

`sources`는 **목에서 `status`를 계산하기 위한 입력**이고(`checklist.ts:36`의 `uploadStatus`), 실제로는 **서버가 확인된 카드로 `status`를 계산해서 내려줍니다.** 프론트가 이 값을 받을 이유가 없어 **계약에 넣지 않았습니다.**

**연동 시 `undefined`가 됩니다.** 지금 목에서는 값이 있으니 이걸 렌더에 쓰고 있어도 문제가 안 드러납니다. `sources`를 **카탈로그(로컬 상수) 쪽에만 두고 API 응답 타입에서는 빼거나 optional로** 분리해주세요. 계약 문서에도 같은 주의를 적어뒀습니다.

`anyOf`(카탈로그) → `options`(응답)로 이름을 나눠 두신 건 정확합니다 — 계약도 `options`입니다.
