# [프론트 → 백엔드] Phase 5 회신 — 배열에서 빼는 방식 괜찮습니다. 다만 제외 경로가 둘이라 하나 확인이 필요합니다

> 원본 요청: `../../request/frontend/draft-revise-and-package-notes.md`

## §1. 제외 문장을 배열에서 빼는 것 — 괜찮습니다. 화면은 원래 그렇게 만들어져 있습니다

원본 텍스트를 클라이언트가 들고 있는 방식이 맞고, **이미 그렇게 동작합니다.** 미리보기 2면은 `draftLines`(문장 전체)와 `excludedSentences`(제외한 id 집합)를 따로 들고, 제외한 문장도 화면에서 지우지 않고 **흐리게 남겨 다시 누를 수 있게** 둡니다. 제출본에서만 빠집니다.

**제외를 눈에 보이게 남기는 것이 UX 선택이 아니라 필요조건이라고 봅니다.** 문장이 사라지면 사용자는 자기가 뭘 뺐는지 모른 채 서류를 내게 됩니다. 되돌릴 수 없는 것보다 이쪽이 더 문제입니다.

**연동할 때 저희가 조심할 것도 하나 적어둡니다** — 응답의 `sentences`로 `draftLines`를 **통째로 갈아끼우면 안 됩니다.** 제외한 문장이 배열에 없으니 그대로 덮으면 화면에서도 사라져 되돌릴 수단이 없어집니다. 남아 있는 문장의 갱신분으로만 병합하겠습니다. 계약 타입 주석에 적어뒀습니다.

## §2. ⚠️ 제외를 전달하는 경로가 두 개입니다 — 어느 쪽이 최종인가요?

이게 이번 회신에서 유일하게 확인이 필요한 부분입니다.

| 경로 | 신설 | 성격 |
| --- | --- | --- |
| `POST /api/draft/revise` 의 `excluded: true` | 2026-08-25 (v1.6) | **세션 상태**로 남음 |
| `POST /api/package/text` 의 `excludedSentenceIds` | 2026-08-25 (v1.6) | **요청 단위** 값 |

둘이 어긋날 때 무엇이 최종인지가 계약에 없습니다. 구체적으로:

1. `revise`로 `s3`을 제외한 뒤, `/api/package/text`를 **`excludedSentenceIds: []`** 로 부르면 — `s3`은 PDF에 **들어갑니까, 빠집니까?**
2. 반대로 `revise`를 한 번도 부르지 않고 `excludedSentenceIds: ["s3"]`만 보내면 빠지는 게 맞습니까? (이쪽은 맞다고 보고 있습니다)

**저희가 원하는 동작은 `excludedSentenceIds`가 최종인 것입니다.** 이유는 사용자가 미리보기에서 문장을 뺐다 넣었다 하는 동안 **매번 서버를 부르지 않기 때문**입니다 — 제외는 텍스트를 고치는 게 아니라 체크박스에 가까워서, 토글할 때마다 왕복하면 느리고 실패 처리가 늘어납니다. 지금 화면은 **내려받기 직전에 최종 목록을 한 번 보내는** 구조입니다.

그렇다면 저희는 **순수 제외에는 `/api/draft/revise`를 부르지 않고**, 문장 텍스트를 실제로 고쳤을 때만 부르게 됩니다. 이 사용 방식이 서버 구현과 맞는지 확인 부탁드립니다. 만약 `revise`의 세션 상태가 PDF에 우선한다면, 저희가 토글마다 서버를 불러야 하므로 화면 구조가 달라집니다.

## §3. `DRAFT_FAILED` — 확인했습니다. 클라이언트에 반영해 뒀습니다

오류 코드 목록과 기본 문구를 추가했습니다. `fallback`이 없는 코드라는 것도 반영했습니다.

기본 문구는 이렇게 뒀습니다 — 서버가 `message`를 주면 그걸 그대로 씁니다.

> 소명서를 만들지 못했어요. 잠시 후 다시 시도해주세요. 확인한 자료는 그대로 있어요.

**뒷문장을 붙인 이유**: 여기서 실패하면 사용자는 자료 확인까지 다 끝낸 상태입니다. "다시 시도"만 있으면 **처음부터 다시 해야 하나** 로 읽히고, 그 자리에서 이탈하기 쉽습니다. 세션이 살아 있고 확인한 카드가 남아 있다는 사실이 재시도 버튼보다 중요합니다.

**확인 부탁**: `DRAFT_FAILED` 후에도 세션과 확인된 카드가 그대로 유지되는 것이 맞습니까? 위 문구가 그 전제 위에 있습니다.
