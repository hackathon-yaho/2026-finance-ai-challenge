## 0. 먼저 — 지적하신 문제가 화면에 이미 나와 있습니다

`spec.md` F8-01의 PDF 하단 표기 얘기를 하셨는데, **그 문구가 지금 화면에도 있습니다.**

`DraftStage.tsx:66`
> AI 초안 · **사용자 확인 완료** · 최종 판단은 금융회사

사용자는 이 문장이 뜨기까지 **아무것도 확인하지 않았습니다.** 초안을 생성하면 바로 붙습니다. PDF만의 문제가 아니라 화면에서 이미 사실이 아닌 표기를 하고 있었습니다.

이 프로젝트가 "낙관적으로 순화하지 않는다"를 내세우는 이상, **우리 화면의 표기부터 사실이어야** 합니다. 그래서 읽기 전용 미리보기는 협의 대상이 아니라 **고쳐야 할 것**으로 보고 진행하겠습니다.

## 1. §4-1 근거 미매칭 수정 문장 — **B(경고 + `user_text` 유지)**

동의합니다. 근거도 같습니다 — **자동 삭제는 LLM 출력에 적용하는 규칙**이고, 사람이 자기 사실을 적은 문장에 같은 규칙을 쓰면 성격이 다릅니다. FR-045 ⑤가 이미 `user_text`에 "본인 진술" 표기를 규정하고 있으니, B는 그 규정을 따르는 것이고 A는 오히려 사용자 입력을 `user_text`로 인정하지 않는 셈입니다.

### 1-1. 다만 — **배지가 바뀌는 것을 사용자가 보게 해야 합니다**

제안하신 응답 스키마에 `sourceType`이 있으니 동작은 이미 정해져 있는데, **화면에서 무슨 일이 일어나는지**가 계약에 안 적혀 있어 적어둡니다.

| 편집 전 | 편집 후 | 화면 |
| --- | --- | --- |
| `evidence` (근거 배지 + 원본 이동) | 여전히 매칭됨 (오타 수정 등) | 그대로 |
| `evidence` | **매칭 끊김** | 배지가 **"본인 진술"로 바뀌고 원본 이동 배지가 사라짐** |

**이게 경고보다 중요합니다.** 경고 문구는 읽고 넘기지만, 방금까지 "대화 캡처"라고 적혀 있던 배지가 "본인 진술"로 바뀌는 건 눈에 보입니다. 사용자가 잃은 것이 무엇인지 정확히 알려주는 신호입니다.

프론트는 `warning` 문구와 배지 변화를 **함께** 렌더하겠습니다. `warning`은 받은 문자열을 그대로 씁니다.

## 2. §4-2 수정 범위 — **제안하신 그대로**

| 대상 | 결론 |
| --- | --- |
| 1면 서식 필드 | 자유 입력 (이미 확정) |
| 2면 소명서 문장 | **문장 단위 편집 + 제외** |
| 3면 타임라인 | **편집 불가** |
| 4·5면 증빙목록·부족자료 | **편집 불가** |

3·4·5면을 여는 데 반대하신 이유에 동의합니다. 타임라인만 고치면 소명서·증빙목록과 어긋나고, 4·5면은 규칙 엔진 산출물이라 사람이 고치면 준비도와 불일치합니다.

### 2-1. 다만 "편집 불가"만 두면 막다른 길이 됩니다

미리보기에서 타임라인의 값이 틀린 걸 발견한 사용자는 **고칠 방법을 찾아야** 합니다. 편집이 막혀 있는데 대안이 안 보이면 그냥 틀린 채로 다운로드합니다.

3면 옆에 **"값이 다르면 자료 확인으로 돌아가 고칠 수 있어요"** 안내와 Stage 2 복귀 링크를 두겠습니다. F7-04(재생성)가 이미 있는 경로라 새로 만드는 건 링크뿐입니다.

## 3. §4-3 문장 삭제 — **"제외" 토글 (`excluded: true`)**

세 안 중 **제외 토글**을 고릅니다. `text: ""`는 쓰지 않는 쪽을 권합니다.

| | 문제 |
| --- | --- |
| `text: ""` | **되돌릴 수 없습니다.** 원문이 사라져서 "역시 넣을게요"가 안 됩니다. 빈 문자열과 공백만 입력한 값을 구분해야 하는 것도 부담입니다 |
| `deleted: true` | 동작은 같지만 이름이 파괴적으로 읽힙니다 |
| **제외 토글** | 되돌릴 수 있고, **FR-028의 "미확인 카드는 문서에 포함되지 않습니다"와 같은 개념**입니다. 사용자가 이미 아는 말입니다 |

요청 형태는 `text`와 분리해 주세요 — 한 필드에 두 의미를 넣지 않는 편이 낫습니다.

```json
{ "sentences": [
  { "sentenceId": "s3", "excluded": true },
  { "sentenceId": "s5", "text": "2026년 9월 1일 물품을 발송하였습니다." }
] }
```

## 4. §4-4 미리보기 화면 위치 — **S04-2 동의**

`S04 → [제출 패키지 내보내기] → S04-1 서식 입력 → S04-2 미리보기 → 다운로드` 그대로 갑니다. `spec.md` 화면 정의서에 반영해 주세요.

### 4-1. (2026-08-25 ② 신설) 미리보기와 실제 PDF가 **서로 다른 렌더러**입니다

제안하신 "미리보기는 프론트가 HTML로, PDF는 서버가"를 그대로 수용했는데, 다시 보니 **미리 본 것과 실제로 받는 것이 달라질 수 있는 구조**입니다. 회신을 보낸 뒤 발견해 덧붙입니다.

#### ① 1면(별지 제4호서식)은 HTML로 재현하지 않겠습니다

서버가 원본 레이아웃을 재현하는데(§2 통보 내용) 프론트가 HTML로 같은 표를 다시 그리면 **같은 법정 서식을 두 곳에서 구현**하는 셈입니다. 한쪽만 고치면 조용히 어긋나고, 사용자는 미리보기에서 본 배치와 다른 PDF를 받습니다.

미리보기 1면에는 **"별지 제4호서식 그대로 생성돼요"라는 안내 + 입력한 11필드 값 요약**만 보여주겠습니다. 서식 자체의 렌더는 서버 PDF에 맡깁니다. 사용자가 확인해야 할 것은 **자기가 입력한 값이 맞는지**이지 표 선의 위치가 아닙니다.

#### ② 폰트 깨짐은 미리보기가 구조적으로 못 잡습니다 — 9/6 점검 항목으로 올려주세요

`spec.md` F8-01의 개발 주의에 이 경고가 있습니다.

> **Render 컨테이너에 한글 폰트가 없으면 전부 깨진다.** Dockerfile에 `fonts-nanum` 설치 또는 나눔고딕 ttf를 리소스에 포함할 것

**HTML 미리보기는 브라우저 폰트로 그리므로 화면에서는 멀쩡한데 받은 PDF만 깨집니다.** 미리보기의 목적이 "내가 받을 게 이거다"인데, 가장 흔한 PDF 사고를 못 거르는 셈입니다.

이건 사용자가 잡을 문제가 아니라 **팀이 리허설에서 잡을 문제**입니다. `roadmap.md`의 9/6 최종 점검(전체 플로우 3회 완주)에 **"생성된 PDF를 실제로 열어 한글이 정상 렌더되는지 확인"** 을 명시 항목으로 넣어주세요.

> 실제 서버 PDF를 브라우저에 렌더해 보여주는 안(병합 결과를 그대로 iframe에 띄우기)도 검토했습니다. 이러면 미리보기와 산출물이 **같은 것**이라 어긋날 수 없는데, **iOS 사파리에서 blob PDF 렌더가 불안정**합니다. NFR-05가 모바일 대응을 요구하고 심사위원이 폰으로 열 가능성이 있어 기본 경로로 삼지 않았습니다. 데스크톱 한정 보조 버튼으로는 검토할 만합니다.

#### ③ ⚠️ **4면 "증빙자료 목록"이 무엇인지 확인이 필요합니다**

<!-- 아래 ③·④는 그대로 유효합니다. ②의 해소 내용은 §4-2를 보세요. -->

이게 이번 개정에서 가장 중요합니다.

요청서 §2가 **4면 증빙목록의 출처를 `/api/draft`의 `checklist`** 로 적으셨는데, `checklist`는 F7-03 **첨부 서류 체크리스트**입니다 — 사유별 필요 서류에 **보유/미보유를 표시**하는 그 목록입니다.

그러면 **`legal-form-and-package.md` §3에서 5면을 뺀 이유가 4면에 그대로 남습니다.** 미보유 목록을 은행에 스스로 건네는 문제요. 5면만 빼고 4면을 두면 반쪽입니다.

이름으로 보면 둘은 다른 것 같습니다.

| 해석 | 내용 | 은행 제출본에 |
| --- | --- | --- |
| **A. 올린 자료의 목록** | "① 대화 캡처 2026-09-01 · ② 입금 내역 2026-09-01 · ③ 택배 송장…" — 뒤에 붙는 **원본 이미지 페이지의 목차** | ✅ 무해하고 담당자에게 유용 |
| **B. 사유별 필요 서류 체크리스트** (`/api/draft`의 `checklist`) | 보유/미보유 표시 | ❌ 5면과 같은 문제 |

**A로 읽는 것이 맞다고 봅니다.** `prd.md` §4.4 서식 매핑표가 *"첨부서류 1 = 타임라인 + **증빙목록** + 원본이미지"* 로 셋을 묶어뒀는데, 목록과 실물(이미지)이 짝을 이루는 구조입니다.

**A/B 중 어느 쪽인지 확정해 주세요.** B라면 4면도 화면 전용으로 빼는 것을 권합니다.

#### ④ 각 면의 **항목·정렬 기준**이 어느 문서에도 없습니다

면 이름과 데이터 출처는 있는데(`spec.md` F8-01, F7-06), **무엇을 어떤 형태로 그릴지는 정의된 곳이 없습니다.**

- 3면 타임라인에 `gaps`(증거 공백)를 표시하는가? 표시하면 5면과 같은 "못 갖춘 것" 문제가 또 생깁니다
- 4면에 파일명·유형·일시 중 무엇을 넣는가? (파일명은 개인정보가 섞일 수 있어 권하지 않습니다)
- 표지를 채택하면 무엇을 적는가?

**같은 면을 두 사람이 각자 그리기 때문에** 기준이 필요합니다 — PDF는 백엔드, 미리보기는 프론트입니다. 기준이 없으면 ①과 같은 어긋남이 2~5면에서도 생깁니다.

**백엔드가 `spec.md` F8-01에 면별 항목을 정의해 주시면 프론트가 그대로 따르겠습니다.** 프론트가 먼저 정하면 PDF와 어긋나고, PDF가 단일 출처이므로 그쪽이 기준이 되는 게 맞습니다.

### 4-2. (2026-08-25 ③) "실제 문서" 보기를 넣었습니다

미리보기 화면(S04-2)에 보기를 둘로 나눴습니다.

| 보기 | 무엇을 보여주나 | 왜 |
| --- | --- | --- |
| **정리해서 보기** (기본) | 면별 내용을 HTML로 | 문장 빼기·되돌리기가 즉시 반영된다. 실제 PDF는 서버가 만들므로 편집할 때마다 다시 부르면 느리다 |
| **실제 문서** | **내려받을 파일 그대로** pdf.js 렌더 | 폰트 깨짐·레이아웃 사고를 받기 전에 본다 |

- **미리보기와 다운로드가 같은 함수를 씁니다.** 따로 만들면 보여준 것과 받는 것이 갈립니다
- `<iframe src={blobUrl}>`은 쓰지 않았습니다 — **iOS 사파리에서 blob PDF 렌더가 불안정**합니다(빈 화면·다운로드 튐). NFR-05가 360px 모바일을 요구합니다
- pdf.js는 **지연 로딩**합니다. 첫 화면 번들은 그대로고 별도 청크로 빠집니다
- 지금은 `/api/package/text`가 없어 **증빙 원본 이미지 면만** 보이며, 화면에 그렇게 밝힙니다. 엔드포인트가 열리면 서버 PDF를 첫 인자로 넘기는 한 줄만 바뀝니다

**백엔드가 추가로 할 일은 없습니다.** §6의 후속 작업 목록은 그대로입니다.

## 5. §4-5 일정 — **읽기 전용 · 제외 · 자유 편집 모두 8/29~8/31** (2026-08-25 ② 개정)

> **종전 회신에서는 자유 텍스트 편집을 9/1~9/2로 미루고 "8/29~8/31에는 `/api/draft/revise`가 필요 없다"고 적었습니다. 그 결정을 뒤집습니다.** 백엔드 작업 계획에 영향이 있어 착수 전에 알립니다.

### 5-1. 왜 바꿨나 — 읽기 전용이면 요청서 §1의 문제가 그대로 남습니다

요청서가 든 문제는 **"있는 사실을 틀리게 쓴 문장"**(카드는 맞는데 "발송했습니다"를 "수령했습니다"로 뒤집는 경우)이고, F7-02는 이걸 못 막습니다. 근거와 매칭은 되니까요.

읽기 전용 미리보기만 있으면 사용자는 그 문장을 **발견만 하고 고치지는 못한 채** 다운로드합니다. 발견하게 만들어놓고 고칠 방법을 안 주는 건 절반만 한 것이고, "AI 초안 · 사용자 확인 완료" 표기도 "봤다"까지만 사실이 됩니다.

프론트 쪽 추가 비용을 다시 따져보니 **문장별 입력창 + 검증 결과 배지 갱신** 정도입니다. §1-1에서 정한 배지 변화 렌더가 어차피 필요하고요. 진짜 비용은 `POST /api/draft/revise`이고 그건 제 일정이 아니라 백엔드 일정입니다.

### 5-2. 확정 일정

| 구간 | 범위 | 필요한 백엔드 작업 |
| --- | --- | --- |
| **8/29~8/31** | 읽기 전용 미리보기 · 문장 제외 · **문장 자유 텍스트 편집** | `excludedSentenceIds` **+ `POST /api/draft/revise`** |
| 밀리면 (컷 순서) | ① 자유 편집 컷 → ② 제외 컷 | 아래 §5-3 참조 |

**`/api/draft/revise`가 8/29~8/31에 어렵다면 알려주세요.** 그 경우 종전 회신대로 자유 편집만 9/1~9/2로 미루면 되고, 프론트는 읽기 전용 + 제외로 먼저 완성해 둡니다. 기다리는 동안 막히는 작업은 없습니다.

### 5-3. 컷하더라도 미리보기는 남습니다 — 제외는 엔드포인트가 필요 없기 때문

일정이 밀렸을 때의 안전망이라 종전 회신 내용을 그대로 둡니다.

**문장을 빼는 것은 새 사실을 만들지 않으므로 F7-02 재검증이 필요 없습니다.** 남은 문장은 이미 검증을 통과했고 근거 연결도 그대로입니다. 재검증이 필요한 건 **텍스트가 바뀌었을 때**뿐입니다.

그래서 제외는 `/api/package/text` 요청 바디만으로 됩니다.

```json
{
  "applicant": { ... },
  "account": { ... },
  "excludedSentenceIds": ["s3", "s7"]
}
```

- 서버는 2면 생성 시 이 id들을 빼고 렌더합니다
- 세션에 상태를 더 만들 필요가 없습니다 — 다운로드 시점에 한 번 전달되고 끝입니다
- **자유 편집이 컷돼도 미리보기·제외는 살아남고, F8-01의 "사용자 확인 완료" 표기는 그 범위만으로도 사실이 됩니다**

### 5-4. 표기 문구도 범위에 맞춰 주세요

미리보기를 거친 뒤라면 "사용자 확인 완료"는 정확합니다 — 사용자가 내용을 보고 다운로드를 눌렀으니까요. **다만 지금처럼 초안 생성 직후 붙으면 안 됩니다.**

- 화면(`DraftStage`)의 표기는 **미리보기를 거친 뒤**에만 붙도록 프론트가 고치겠습니다
- PDF 하단 표기의 `{시각}`은 **다운로드를 누른 시각**으로 잡아 주세요. 초안 생성 시각이 아닙니다
