# [프론트 → 백엔드] 정직성 고지 3건 — 회신

- 작성: 프론트엔드 · 2026-08-25
- 원본 요청: `../../request/frontend/honest-disclosure-fixes.md` (백엔드 · 2026-08-24)

**3건 다 반영했습니다.** 문구까지 구현했고, 한 곳에서 **숫자 하나를 일부러 빼뒀습니다**(§2-1) — 확인 부탁드립니다.

## 1. 5영업일 카피 — 대문과 통계 행 둘 다 고쳤습니다

### 대문 카피

| | 문구 |
| --- | --- |
| 종전 | 지급정지된 계좌, **은행이 5영업일 안에** 판단할 수 있게 정리해요 |
| 지금 | 지급정지된 계좌, **은행이 판단할 수 있는 형태로** 정리해드려요 |

지적하신 두 가지가 다 걸려 있었습니다 — **숫자가 약속처럼 읽히는 것**, 그리고 **서비스가 5영업일을 주는 것처럼 읽히는 것**. 우리가 정리한다고 은행이 빨라지지 않으니 후자가 특히 문제였습니다.

숫자를 뺐지만 주장은 약해지지 않았다고 봅니다. **"은행이 판단할 수 있는 형태"** 가 이 서비스가 실제로 하는 일이고, 심사 기간은 그 결과지 우리 기능이 아닙니다.

### 통계 행 (`INTRO_STATS`)

말씀대로 **사실이라 유지**했고, "심사 결과 통보 기준"임이 드러나게 고쳤습니다.

| | 제목 | 설명 | 값 |
| --- | --- | --- | --- |
| 종전 | 표준 심사 기간 | 자료를 충분히 갖춰 낸 경우 | 5영업일 |
| 지금 | **심사 결과 통보** | 자료를 충분히 갖춰 낸 경우 · **해제 시점은 아니에요** | 5영업일 |

구분을 **숫자가 있는 바로 그 자리**에 붙였습니다. 다른 데 적으면 숫자를 본 사람과 설명을 읽는 사람이 갈립니다.

### `ReadinessStage` 문구는 그대로 뒀습니다

"고치지 마세요"라고 하신 부분입니다. 손대지 않았습니다.

### `notices` 고정 문구 — **백엔드가 내려주세요**

물어보신 항목입니다. **백엔드가 `/api/readiness`의 `notices`로 내려주시는 쪽이 맞습니다.**

지금 `ReadinessStage`에 하드코딩된 문구는 API 연동 전 임시값이고, 법 제8조 제2항 같은 조문 근거 문구는 **서버가 단일 소스로 갖는 편**이 낫습니다 — FR-014 `deadline.notice`를 그렇게 정한 것과 같은 이유입니다. 프론트는 받은 문자열을 **순화하지 않고 그대로** 노출하겠습니다.

`spec.md` F6-05를 고치실 때 **"심사 결과 통보"와 "지급정지 해제"를 분리한 문장**으로 써주세요. 지금 문서에는 그 구분이 없습니다.

## 2. 3년 제한 고지 — **S05 배치가 맞습니다. 넣었습니다**

물어보신 배치에 동의합니다. 준비도 화면에 넣으면 "제출 준비 완료" 배지와 정면으로 부딪힙니다. `RoutesStage`(S05)의 접수 경로 아래, 상시 배지 바로 위에 뒀습니다.

### 화면에 나가는 문구

> **지급정지가 풀린 뒤에도 남을 수 있어요**
>
> 사기이용계좌 명의인으로 등록되면 은행연합회를 통해 다른 은행에도 공유되어, 신규 계좌 개설이나 카드 발급이 한동안 제한될 수 있어요. **지급정지 해제와는 별도 절차**이고, 은행 또는 은행연합회에 등록 해제를 따로 신청할 수 있어요.

- 경고색을 쓰지 않았습니다(중립 회색 카드). 겁을 주려는 게 아니라 알려주는 것입니다.
- **해제 경로를 같은 문장에 붙였습니다.** 불이익만 적고 끝내면 "그래서 어쩌라는 건가"가 됩니다.

### 2-1. ⚠️ **"3년"을 일부러 뺐습니다** — 확인 부탁드립니다

요청서의 근거가 **블로그·후기**(`blog.ehyun.co.kr`, `albup.co.kr`)입니다. 제도가 존재한다는 것과 후기의 정황은 신뢰하지만, **"최대 3년"이라는 수치의 1차 출처는 확인되지 않았습니다.**

PRD §2.7이 정한 규칙에 걸립니다.

> **기획서 작성 지침: 위 세 항목은 어떤 형태로도 숫자를 만들어 쓰지 않는다.** 한계를 명시하는 편이 심사위원 신뢰를 얻는다.

이 프로젝트는 **소액 금액 기준을 추정하지 않겠다고 정한 서비스**입니다(OI-01). 같은 기준을 우리 쪽 숫자에도 적용하지 않으면 앞뒤가 안 맞습니다. 그래서 **"최대 3년"** 대신 **"한동안"** 으로 썼습니다.

**1차 출처(은행연합회 규약, 금융위·금감원 자료, 법령)를 찾으시면 알려주세요.** 그때 숫자를 넣겠습니다 — 정확한 기간을 아는 편이 사용자에게 훨씬 유용하니, 빼는 게 목적은 아닙니다.

## 3. 보존 지침 — **둘 다 넣었습니다**

"셋 중 가장 낮은 우선순위, 2번만 해도 충분"이라고 하셨지만 둘 다 문구 렌더라 같이 넣었습니다.

### 위치 — 업로드 화면(S02) 상단, 파일 선택 영역 **위**

두 요청을 **한 블록**으로 합쳤습니다. "지우지 마세요"와 "이미 지웠다면"은 같은 사용자가 연달아 읽어야 하는 내용입니다.

> **가진 자료를 지우지 마세요**
> 정리가 끝날 때까지 대화방을 나가거나 메시지를 지우지 마세요. 남은 기록이 그대로 소명 근거가 돼요.
>
> **이미 지웠다면 여기를 찾아보세요**
> · 메신저 — 대화 백업 기능으로 복원되는 경우가 있어요
> · 중고거래 앱 — 앱 안의 거래 내역에서 다시 캡처할 수 있어요
> · 문자 — 통신사 문자 보관함에 남아 있을 수 있어요
> · 은행 앱 — 입출금 내역은 언제든 다시 캡처할 수 있어요

**복구 안내를 F5-04(대체 증빙 제안) 안에 넣지 않은 이유**: F5-04는 **판독이 끝난 뒤** "이 자료가 없으니 저걸 대신 내보라"고 제안하는 기능입니다. 복구는 그보다 앞, **자료를 모으는 시점**에 필요합니다. 판독 후에 "카톡 백업을 찾아보세요"라고 하면 이미 업로드를 마친 사용자가 다시 처음으로 돌아가야 합니다.

F5-04는 백엔드·AI 소관으로 그대로 두시고, 이 블록은 **그 앞단**으로 봐주세요. 둘은 겹치지 않습니다.

### 화면 부담 — 괜찮습니다

물어보신 부분입니다. 업로드 화면은 원래 **빈 박스 하나**였습니다(F3-07 요청에서 지적하신 그 상태). 안내가 들어가면서 오히려 화면이 채워졌고, 파일 선택 영역은 그대로 스크롤 없이 닿습니다.

**메신저 이름을 특정하지 않았습니다.** "카카오톡 설정 → 채팅 → 대화 백업"처럼 메뉴 경로를 적으면 앱이 업데이트될 때마다 틀린 안내가 되고, 특정 서비스 이름을 쓰는 부담도 있습니다.
