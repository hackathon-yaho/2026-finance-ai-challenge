# [AI → 백엔드] 회신: 소명서 타임아웃 — **원인은 예산이 아니라 `effort`였습니다**

- 원본 요청: `../../request/ai/draft-timeout-needs-headroom.md` (백엔드 · 2026-08-27)
- 회신: AI · 2026-08-27

## 결론 먼저

로그와 재현 조건이 정확했습니다. 다만 **예산만 올리는 것으로는 부족했습니다** — 재보니 `gpt-5.5`의 `medium` reasoning이 12건에서 이미 **17.9초**였습니다. 요청하신 대로 15~20초로 올렸어도 20건(23.4초)에서 다시 걸렸을 겁니다.

**`draft_effort`를 `medium` → `low`로 내리고, 그 위에서 예산을 실측 기준으로 다시 잡았습니다.**

| | 종전 | 변경 |
| --- | --- | --- |
| `draft_effort` | `medium` | **`low`** |
| `llm_timeout_draft` | 10.0 | **25.0** |
| `handler_budget_draft` | 13.0 | **27.0** |

## 1. 실측 — 이벤트 수에 거의 선형입니다

재시도를 끄고 순수 1회 호출만, 조건당 3회씩 쟀습니다.

| 이벤트 수 | `medium` (종전) | **`low` (채택)** |
| --- | --- | --- |
| 3건 | 11.9초 | **5.8초** |
| 12건 | **17.9초** | **10.4초** (최대 10.9) |
| 20건 | **23.4초** | 13.5초 (최대 14.0) |
| 30건 | — | 17.6초 (최대 18.4) |
| 40건 | — | 22.5초 (최대 23.3) |

대략 **이벤트당 0.45초 + 기본 4초**입니다. 보내주신 로그(12건에서 10.0초 컷)와 정확히 맞습니다 — medium이 17.9초를 쓰려는데 10초에서 끊긴 것이었습니다.

## 2. `low`로 내려도 문장 품질은 떨어지지 않습니다

같은 입력(대화·입금·배송 + 문진)으로 두 설정을 나란히 돌려 눈으로 비교했습니다. 둘 다 `factCheckPassed: true`, 7문장으로 같았고 내용도 대등했습니다. 오히려 `low` 쪽이 **"본인은"** 을 쓰고 `medium`이 **"저는"** 을 써서, 은행 제출 문서로는 `low` 표현이 더 적절했습니다.

**이 작업은 깊은 추론이 필요한 종류가 아닙니다.** 사실 목록을 받아 근거를 붙여 문장으로 옮기는 조립 작업이고, **검증은 어차피 결정적 FactChecker가** 합니다. `medium`이 쓰던 추론 시간은 품질로 돌아오지 않고 지연으로만 나타났습니다.

## 3. 요청 3번 답변 — **계약값 15초를 넘습니다. 30초로 올려주세요**

| 항목 | 값 |
| --- | --- |
| AI-server 1회 시도 상한 | **25초** |
| 권장 `draftRestClient` 타임아웃 | **30초** (AI 25초 + 네트워크·직렬화 여유) |
| 계약 문서 `/internal/draft` | 15초 → **30초** 로 갱신 필요 |

**25초로 잡은 근거**: 30건(최대 18.4초)을 여유 있게 덮고 40건(23.3초)도 아슬하게 들어옵니다. 이미지 10장 상한에 `recurrence` 묶기까지 적용되면 30건 안쪽이 현실적인 상한이라고 봅니다.

### 재시도에 대해 — 타임아웃은 AI-server 안에서 재시도하지 않습니다

체감 대기시간을 물으셨는데, 계산에 필요한 사실을 하나 알려드립니다.

**AI-server의 내부 재시도는 타임아웃에 걸리지 않습니다.** 스키마 불일치·5xx 같은 "다시 하면 될 수도 있는" 실패에만 1회 재시도하고, **타임아웃은 즉시 `TIMEOUT`(504)으로 나갑니다** — 같은 입력에 같은 모델이면 다시 해도 같은 시간이 걸리기 때문입니다.

그래서 프론트 체감 대기시간은 이렇게 됩니다.

| 상황 | 대기 |
| --- | --- |
| 정상 (12건) | **약 10초** |
| 정상 (30건) | 약 18초 |
| AI 타임아웃 → 백엔드 재시도 1회 | 25초 + 25초 = **최대 50초** |

**50초는 깁니다.** 다만 위 실측대로라면 30건까지는 25초 안에 들어오므로 타임아웃 자체가 잘 나지 않을 것으로 봅니다. **재시도 정책을 그대로 두실지는 이 수치를 보고 판단해 주세요** — `factCheckPassed: false`로 인한 재생성은 성격이 다르니(내용 문제) 그건 유지하는 게 맞다고 봅니다.

## 4. 제 잘못이었던 부분

`config.py` 주석에 **"소명서: 텍스트만이라 빠르고"** 라고 적어둔 것이 근거 없는 단정이었습니다. 추출 경로는 평가 세트로 이벤트 수까지 바꿔가며 쟀는데, **소명서 경로는 스모크 테스트 1회(11.1초)로 넘겼습니다.** 그 11.1초가 이미 제가 정한 10초 한도를 넘는 값이었는데도 그냥 지나쳤습니다.

지금은 위 표대로 이벤트 수별 실측이 있고, `evals/README.md`에 남겼습니다.

## 5. "소명서에 나온 사유가 mock 데이터였다"에 대해

프론트 쪽에서 나온 이야기로 전해 들었습니다. `DEMO_MODE=true`이면 `/internal/draft`를 호출하지 않고 `demo/draft-tc0*.json` 픽스처를 그대로 돌려주는 것이 **의도된 동작**입니다(F11-03). 실연동을 확인하실 때는 `DEMO_MODE=false`인지 함께 봐주시면 좋겠습니다.

다만 **픽스처가 진짜 생성 결과처럼 보인 것**은 짚어둘 만합니다. 데모 응답에 "데모"임을 알 수 있는 표시가 없어서 생긴 일인데, 필요하시면 픽스처에 표식을 넣는 방향도 검토하겠습니다 — 다만 그 표식이 실제 데모 시연에서 화면에 보이면 안 되니, 넣는다면 응답 필드가 아니라 **로그 쪽**이 맞다고 봅니다. 의견 주세요.
