# [AI → 백엔드] 회신: 추출 카드에 대화 상대명·입금자명 추가 요청

- 원본 요청: `../../request/ai/payer-name-extraction.md` (2026-08-24)
- 회신: AI · 2026-08-25
- 연관: `../../request/frontend/evidence-structure-revision.md` §1 (프론트 회신 대기 중 — 아래 §5에 프론트 안내 문구 관련 요청 1건 있음)

## 1. 필드명·구조 — **제안하신 원안 수용**

```json
{
  "event_id": "evt_0_1",
  "actor": "counterparty",
  "counterparty_name": "김OO",   // 대화 캡처: 화면에 보이는 표시명·닉네임 그대로
  "payer_name": null,             // 입금 내역 캡처: 거래내역의 입금자 표기 그대로
  ...
}
```

- 해당 없으면 `null`. **추측해서 채우지 않습니다** — 프롬프트에 명시적 금지 조항으로 들어갑니다(기존 "확인 불가 값은 null" 원칙과 동일 계열).
- `field_confidence`에 `counterparty_name`, `payer_name` 키를 추가해 신뢰도(high/medium/low)를 함께 내립니다.
- 값이 있는 카드는 F4-06 확인 카드에 노출되어 **사용자가 확인·정정**하게 됩니다(잘못 읽은 이름이 그대로 대조에 쓰이는 것을 사용자 확인 단계가 막아줍니다).

## 2. 부분 마스킹 대조 가능 여부 — **가능하지만 권하지 않습니다. "화면에 보이는 그대로 추출"을 제안합니다**

질문 주신 절충안에 대한 기술 판단입니다.

**부분 마스킹(예: `김O수`) 상태의 대조는 성립은 하지만 판별력이 크게 떨어집니다.**

- 마스킹 후 대조는 "가운데 글자를 뺀 나머지 일치"가 되는데, 한국 성명 구조상 **동성·동돌림자 오탐**(김민수/김영수 → 둘 다 `김O수`)이 흔합니다. 통장협박·삼각사기의 판별 지점이라는 이 기능의 목적에 비해 신호 품질이 낮아집니다.
- 더 근본적인 문제: **마스킹 규칙을 LLM에게 시키면 규칙 자체가 흔들립니다** (2글자 이름·법인명·외국명에서 마스킹 위치가 비결정적). 대조 로직이 결정적이려면 입력이 결정적이어야 합니다.

**제안: 거래 당사자의 표시명은 화면에 보이는 그대로 추출하고, 대신 아래 경계로 개인정보 원칙을 지킵니다.**

| 경계 | 내용 |
| --- | --- |
| 추출 범위 | **거래 당사자**(대화 상대, 입금자)의 화면 표시명만. 거래와 무관한 제3자 이름은 기존대로 추출하지 않음 |
| 근거 논리 | 이 이름은 "거래 사실"의 구성 요소입니다. 금감원이 요구하는 소명자료("구매자와 송금인이 일치하는지 확인할 수 있는 자료")가 바로 이 값이고, 소명서 사실 기재에도 필요합니다. 전화번호·계좌번호 전체·주민번호처럼 "판독 목적에 불필요한 식별자"와는 성격이 다릅니다 |
| 저장 | 기존 원칙 그대로 — 추출 JSON은 서버 세션(30분 TTL)에만 존재, DB·로그 미기록. AI-server는 아무것도 저장하지 않음 |
| 사용자 통제 | F3-06 사전 마스킹으로 사용자가 이름을 가리고 올릴 수 있음(가리면 `null`로 나감) + F4-06 카드에서 확인·수정·삭제 가능 |

즉 **"부분 마스킹으로 절충"이 아니라 "추출 범위를 거래 당사자로 한정"하는 것을 절충안**으로 제안합니다. 백엔드가 검토 중인 "대조 후 판정 결과만 세션에 남기는 방안"과도 호환됩니다 — 다만 소명서 사실 기재("김OO에게 판매" / "입금자 박OO")에 이름이 필요할 수 있으므로, **카드에는 원문 유지 + 소명서 표기 수위는 소명서 생성 단계에서 결정**(기본: 표시명 그대로, 이는 은행에 내는 사용자 본인 문서라 은행이 원문 대조 가능해야 함)을 권합니다.

이 제안이 수용되면 예고하신 문서 6곳(특히 `privacy-and-safety.md` 추출 범위 예외, `spec.md` F4-03 "실명" 항목 예외)을 백엔드가 갱신해 주세요. **수용 여부가 백엔드·프론트 판단과 어긋나면 부분 마스킹 방식으로도 구현은 가능**합니다 — 위 판별력 저하를 감수한다는 팀 결정만 있으면 됩니다.

## 3·4. 실제 추출 정확도 — 부풀리지 않은 판단

아직 평가 세트(F11-05)로 실측 전이므로, 멀티모달 LLM의 일반 성능과 화면 구조에 근거한 **사전 추정**입니다. 8/28까지 합성 캡처로 실측해 이 문서에 수치를 추가하겠습니다.

| 항목 | 추정 | 근거와 한계 |
| --- | --- | --- |
| 대화 상대 표시명 (chat) | **보이면 높음, 자주 안 보임** | 카톡·당근 대화방 상단 이름은 큰 글씨라 판독 자체는 쉽습니다. 문제는 **사용자 캡처 습관** — 상단바를 잘라 찍은 캡처가 많고, 그 경우 값이 아예 없습니다(`null`). 말풍선만으로 상대명을 추정하는 것은 금지 조항에 걸리므로 하지 않습니다 |
| 입금자명 (bank) | **높음** | 은행 앱 거래내역은 "입금 김철수" 형태로 표기가 정형적입니다. 다만 은행별 UI 차이, 법인명 축약("(주)한빛→한빛"), 뒷글자 잘림이 있고, 이 경우 confidence를 `medium/low`로 내립니다 |
| 공통 리스크 | — | 사용자가 F3-06 마스킹으로 이름을 가리면 추출 불가(`null`). 흐림·잘림은 기존 `quality_flags`로 표기됩니다 |

**기능을 접을 수준은 아니라고 판단합니다.** 값이 없으면 `null`로 정직하게 내려가고, 백엔드 대조 로직은 "둘 다 있을 때만 대조"하면 되므로 실패 모드가 안전합니다(없음 ≠ 불일치).

## 5. 판정은 하지 않습니다 — 확약

- `payer_matches` 같은 판정 필드를 만들지 않습니다. 추출만 합니다.
- 닉네임 vs 실명이 다른 것은 정상이라는 점, 불일치가 위험 신호가 아니라 "설명이 필요한 항목"이라는 점 — 소명서 생성(DraftService) 프롬프트에도 같은 원칙을 적용해, **이름 불일치에 대한 해석·평가 문장을 생성하지 않도록** 금지 조항을 둡니다.
- **프론트 쪽 부탁 1건**: F3-06 마스킹 안내가 "거래와 무관한 제3자 이름"을 가리라고 권장하는데, 사용자가 헷갈려 **거래 상대방 이름까지 가리면 이 기능 전체가 무력화**됩니다. 프론트 회신(`evidence-structure-revision.md` §1) 처리 시 "거래 상대방·입금자 이름은 가리지 마세요" 안내 문구를 함께 반영해 주시길 요청합니다 (백엔드가 프론트와 협의 중인 건이라 백엔드 경유로 전달합니다).

## 백엔드가 해야 할 후속 작업

1. §2 제안(거래 당사자 표시명 원문 추출) 수용 여부 결정 → 수용 시 예고하신 문서 6곳 갱신, 미수용 시 부분 마스킹 방식으로 회신 주시면 맞추겠습니다.
2. 카드 스키마에 `counterparty_name` / `payer_name` / `field_confidence` 확장 반영 (`internal-api-contract.md`, `api-contract.md`).
3. 프론트 협의(`evidence-structure-revision.md` §1)에 §5의 마스킹 안내 문구 건 포함.
