## 1. §1-A — F3-06 "가리지 마세요" 문구: **반영 완료**

요청하신 대로 **권장 대상 안내와 같은 크기(13px)로 병기**했습니다. 각주로 줄이지 않았습니다.

### 화면에 나가는 문구

> **거래 상대방·입금자 이름은 가리지 마세요.** 은행이 "구매자와 송금인이 같은 사람인지" 확인하는 데 쓰여요.

`spec.md` F3-06 "가리지 말 것 안내"의 문구를 그대로 쓰되, 화면 존댓말 톤(`~해요`)에만 맞췄습니다. 의미는 바꾸지 않았습니다.

### 배치

마스킹 시트(`MaskingSheet.tsx`)의 안내 영역, **권장 대상 안내 바로 아래**입니다.

```
① 계좌번호 · 주민등록번호 · 전화번호 · 주소 · 관련 없는 제3자 이름 …   (13px, muted)
② 거래 상대방·입금자 이름은 가리지 마세요. …                          (13px, ink) ← 신설
③ "가리기 완료"를 누르면 가린 부분은 되돌릴 수 없어요.                 (13px, warning)
```

②를 **①과 ③ 사이**에 둔 이유는, ①을 읽고 손을 움직이기 **전에** 예외를 보게 하려는 것입니다. ③(되돌릴 수 없음) 뒤로 밀면 이미 마음을 정한 뒤에 읽게 됩니다.

### 시각 처리 — 경고색을 쓰지 않았습니다

②는 옅은 파란 배경 카드(`brand-subtle`) + 본문 잉크색이고, **주황(warning)·빨강(danger)을 쓰지 않았습니다.**

③만 주황입니다. ②까지 경고색으로 칠하면 "이름을 안 가리는 게 위험한 일"처럼 읽히는데, 요청서 §1이 반복해서 강조한 **"서비스가 사용자를 의심하는 톤이 되면 안 된다"** 와 어긋납니다. 배경 카드로 시선만 잡고 톤은 중립으로 뒀습니다.

375px(모바일 최소 폭)에서 두 줄로 떨어지고 이미지 미리보기 영역이 가려지지 않는 것까지 확인했습니다.

### 백엔드가 확인할 것

**없습니다.** `spec.md` F3-06에 이미 명세돼 있고 문구·배치는 프론트 재량이라고 하셨으므로, 공용 문서는 건드리지 않았습니다.

### 1-1. 함께 확인한 것 — 개인정보 경계는 그대로입니다

②를 넣으면서 마스킹 안내가 넓어지는 건 **거래 당사자 이름 둘뿐**임을 코드와 문구 양쪽에서 확인했습니다. 계좌번호·주민등록번호·전화번호·주소는 권장 대상 안내에 그대로 남아 있고, 프론트가 자동으로 무엇을 가리거나 풀어주지 않습니다 — 무엇을 가릴지는 여전히 사용자가 정합니다.

## 2. §2 — 소명자료 3단 구조 + 택일(OR): **자료구조 확정**

요청하신 대로 형태를 정했습니다. **백엔드가 이 모양에 맞춰 주세요.**

### 2-1. 핵심 — 층(tier)과 미보유 효과(whenMissing)는 **독립된 두 축**입니다

가장 중요한 결정이라 먼저 적습니다. 처음엔 "①은 필수, ②는 기준선, ③④는 참고"처럼 **층 하나로 준비도 효과까지 정하려** 했는데, 그러면 테스트 케이스 두 개가 서로 모순됩니다.

| | 층 | 기대 결과 |
| --- | --- | --- |
| TC-21 물품 · **사업자등록증** 없음 | ② 금감원 표준 | `SUPPLEMENT_NEEDED`가 **아니어야** 함 |
| TC-02 용역 · **재직 증빙 계열** 없음 | ② 금감원 표준 | `SUPPLEMENT_NEEDED`가 **맞아야** 함 |

같은 ②인데 반대입니다. 층으로는 이 둘을 가를 수 없습니다.

**가르는 기준은 "사용자가 실제로 채울 수 있는가"입니다.**

- 건강보험 자격득실 확인서·재직증명서 → 근로자면 정부24·건강보험공단에서 **즉시 무료 발급**. 채울 수 있으니 준비도에 반영해도 사용자를 가두지 않습니다
- 사업자등록증 → 개인은 **발급 자체가 불가능**. 반영하면 영원히 "보완 필요"입니다
- 계약서·세금계산서·거래명세서 → 개인 간 거래엔 원래 없고, **사후에 만들면 증거 조작**입니다. PRD가 "증거 생성·보정은 원칙적으로 금지"라고 못박은 영역이라 요구해서는 안 됩니다

그래서 **`whenMissing`을 층과 별개 필드로 뒀습니다.**

> **판정 규칙**: `blocks`는 **이미 존재하거나 즉시 발급받을 수 있는 자료에만** 붙입니다. 사후에 만들어야 하는 자료에 붙이면 서비스가 증거 조작을 유도하는 셈이 됩니다.

이 문장을 `reason-type-rules.md` §2나 §3에 넣어주시면 좋겠습니다 — 나중에 항목을 추가할 때 판단 기준이 없으면 또 흔들립니다.

### 2-2. 타입 (계약 제안)

`/api/readiness`·`/api/draft` 응답의 `checklist` 배열 원소입니다. 현행 계약(`{ item, status }`)을 대체합니다.

```ts
type EvidenceTier  = "legal" | "fss" | "common" | "supporting"   // ① ② ③ ④ — 근거가 어디서 나왔나
type FulfillBy     = "upload" | "self" | "derived"               // 누가 채우나
type MissingEffect = "blocks" | "notice" | "silent"              // 미보유일 때 무슨 일이
type ChecklistStatus = "met" | "unmet" | "unknown" | "needs_explanation"

interface ChecklistItem {
  id: string                 // "goods.trade_doc" — 불투명 문자열
  label: string              // 화면에 그대로 노출
  tier: EvidenceTier
  fulfillBy: FulfillBy
  whenMissing: MissingEffect
  status: ChecklistStatus
  note?: string              // 화면에 그대로 노출하는 보조 문구
  options?: { id: string; label: string; status: ChecklistStatus }[]  // 택일 그룹
}
```

**값의 뜻**

| 필드 | 값 | 뜻 |
| --- | --- | --- |
| `tier` | `legal` | ① 법정 첨부서류 (시행령 제7조) |
| | `fss` | ② 금감원 표준 (**물품·용역 2종에만 존재**) |
| | `common` | ③ 공통 최소 자료 (근거 문서 없음, 참고) |
| | `supporting` | ④ 보강 자료 (실무 관행) |
| `fulfillBy` | `upload` | 서비스에 올리는 캡처 |
| | `self` | 서비스에 올리지 않고 **사용자가 은행에 직접 첨부** (신분증·재직증명서) |
| | `derived` | **올린 자료에서 서버가 뽑아 채운다** (구매자–송금인 대조). 사용자가 갖다 낼 것이 없음 |
| `whenMissing` | `blocks` | 준비도의 `필수증빙누락` 신호에 포함 |
| | `notice` | "미보유 — 보완 요청 사유가 될 수 있어요" 문구만. **준비도를 깎지 않음** |
| | `silent` | 아무 표시도 하지 않음 |
| `status` | `unknown` | **확인 불가** (대조할 값 한쪽이 `null`). **불일치가 아님** (TC-26) |
| | `needs_explanation` | 값은 나왔으나 소명서에 설명이 필요 (구매자–송금인 불일치). **위험 신호가 아니며 준비도를 깎지 않음** (TC-25) |

### 2-3. 택일(OR) 표현

`options` 배열이 있으면 택일 그룹입니다. **하나라도 `met`이면 그룹 전체가 `met`** 입니다 (TC-23).

```json
{
  "id": "service.employment",
  "label": "일한 사실을 보이는 서류",
  "tier": "fss", "fulfillBy": "self", "whenMissing": "blocks",
  "status": "met",
  "note": "이 중 하나만 있으면 돼요. 정부24·건강보험공단에서 바로 뗄 수 있어요.",
  "options": [
    { "id": "service.employment.insurance",   "label": "건강보험 자격득실 확인서", "status": "met" },
    { "id": "service.employment.certificate", "label": "재직증명서",             "status": "unmet" }
  ]
}
```

`anyOf` 대신 `options`로 한 이유는 **응답 원소가 항상 같은 모양이어야** 프론트가 분기 없이 그리기 때문입니다. 단일 항목은 `options`가 없을 뿐입니다.

### 2-4. `fulfillBy: "self"` 항목의 상태는 **사용자가 정합니다**

서비스가 받지 않는 자료라 보유 여부를 알 방법이 없습니다. 그런데 TC-02는 재직 증빙 미보유를 `SUPPLEMENT_NEEDED`로 요구하므로, **누군가는 "없다"고 말해줘야** 합니다.

프론트가 체크리스트 항목마다 **"챙겼어요" 체크박스**를 놓았습니다. 체크하면 `met`, 기본은 `unmet`입니다.

> **2026-08-25 ③ 정정** — 처음에는 누를 때마다 글자가 바뀌는 버튼("있으면 눌러주세요" ↔ "가지고 있어요")이었는데, 그 글자가 **지금 상태**인지 **누르면 될 일**인지 읽는 사람이 알 수 없었습니다. 라벨을 고정하고 체크 표시로 상태를 드러내는 쪽으로 바꿨습니다. **`blocks`인 항목에는 "이 항목을 표시해야 제출 준비 완료가 돼요"를 함께 띄웁니다** — 같은 토글이라도 준비도를 바꾸는 항목(용역의 재직 증빙)과 본인 확인용 항목이 섞여 있어, 무엇이 걸려 있는지 말하지 않으면 왜 눌러야 하는지 알 수 없습니다.

**백엔드에 필요한 것**: 이 표시를 세션에 담을 자리입니다. 계약에 없어서 아래를 제안합니다 — 이름은 바꾸셔도 됩니다.

```
POST /api/checklist/self-held   { "itemId": "service.employment.insurance", "held": true }
→ 200 { "checklist": [ ... ] }     // 갱신된 전체 체크리스트
```

- `itemId`는 단일 항목 또는 **택일 그룹의 옵션 id**입니다
- 이 값은 **사용자 자가 진술**이고 서류 자체가 아닙니다. 세션에만 두고 PDF·로그에 남기지 마세요
- 엔드포인트를 새로 만드는 게 부담이면 `/api/readiness` 요청 바디에 `selfHeld: string[]`로 실어도 됩니다. **판단을 맡기겠습니다** — 프론트는 어느 쪽이든 맞춥니다

### 2-5. ③·④를 준비도에서 제외하는 것 — **동의합니다**

요청서가 물어보신 항목입니다. 동의하고, 한 걸음 더 나갔습니다.

| 층 | 준비도 반영 |
| --- | --- |
| ① legal | `legal.proof`(사기이용계좌가 아니라는 사실을 증명하는 자료)만 `blocks`. **신분증 사본은 `silent`** |
| ② fss | **항목마다 다름** — §2-1 기준으로 `blocks` / `notice` / `silent` |
| ③ common | 전부 `notice` 또는 `silent`. 준비도를 깎지 않음 |
| ④ supporting | 전부 `silent` |

**신분증 사본을 `silent`로 둔 이유**: ①이라서 필수인 건 맞지만, 서비스가 받지 않는 자료라 판정할 수 없습니다. `blocks`로 두면 **전원이 영원히 "보완 필요"** 입니다. 대신 화면에서 "반드시 내야 하는 것" 묶음 맨 앞에 두고 "여기에 올리지 마세요. 은행에 낼 때 직접 첨부해주세요"를 붙였습니다 — 준비도가 아니라 **눈에 띄는 자리**로 해결했습니다.

**`legal.proof`는 자유 형식**이라 확인된 업로드 자료가 **1건이라도 있으면 `met`** 으로 봤습니다. 자료 0건이면 `blocks`가 서서 `SUPPLEMENT_NEEDED`가 됩니다 — 자료를 올리면 풀리므로 가두는 요구가 아닙니다.

### 2-6. ⚠️ 확인 부탁드립니다 — `필수증빙누락`의 정의를 좁혀야 합니다

이 구조를 그대로 쓰면 `reason-type-rules.md` §3의 신호 정의가 지금 문장과 달라집니다.

| | 현재 문서 | 이 구조 |
| --- | --- | --- |
| `필수증빙누락` | "사유별 체크리스트(FR-041)에 **미보유 항목이 있음**" | "**`whenMissing: "blocks"`인 항목** 중 `met`이 아닌 것이 있음" |

현재 문장 그대로 구현하면 ②③④의 모든 미보유가 신호가 되어 TC-21·TC-22가 깨집니다. **§3의 정의를 좁혀 주시고**, §2-1의 판정 규칙(`blocks`는 채울 수 있는 자료에만)을 함께 적어 주세요. 문서 소유가 백엔드라 프론트가 손대지 않았습니다.

목 데이터 기준이지만 **같은 규칙으로 실제로 돌려봤습니다.** 백엔드가 `ReadinessService`를 짤 때 대조용으로 쓰세요.

**카탈로그의 사유별 항목 구성은 백엔드가 최종 소유**라고 봅니다 — `reason-type-rules.md` §2가 단일 출처이므로, 제 카탈로그와 다르게 판단하시면 그쪽을 따르겠습니다. 프론트가 정한 것은 **자료구조의 모양**이고, 어떤 항목이 어느 층·어느 `whenMissing`인지는 §2-1 기준에 따른 **제안**입니다.

### 2-8. 화면에서 지킨 것

- **미보유에 붉은색을 쓰지 않습니다.** `blocks`만 주황(`필요`), 나머지 미보유는 회색(`미보유`)입니다. 채울 수 없는 항목까지 경고로 칠하면 서비스가 사용자를 탓하는 화면이 됩니다
- `whenMissing: "silent"` + 미보유는 **배지 자체가 없습니다** (사업자등록증, 차용증, 협박 메시지)
- `needs_explanation`·`unknown`은 **중립 회색**입니다 — "설명 필요" / "확인 불가"
- 층마다 제목과 한 줄 설명을 달아 무게 차이를 드러냈습니다: "반드시 내야 하는 것" / "은행이 바로 심사할 수 있는 자료 — 없다고 접수가 막히지는 않아요" / "있으면 도움이 되는 자료" / "함께 내면 도움이 되는 자료 — 없어도 불이익은 없어요"

## 3. §7 — 사유별 업로드 안내 (F3-07): **구현 완료**

업로드 패널 상단, **파일 선택 영역 위**에 넣었습니다.

**목록은 `EVIDENCE_CATALOG`를 F7-03 체크리스트와 그대로 공유합니다.** 복사하지 않았습니다 — 요청서가 "목록을 두 곳에 복사하지 않는다"고 못박은 부분이고, 실제로 복사했으면 §2에서 카탈로그를 고칠 때마다 두 곳이 어긋났을 겁니다.

### 3-1. 3단 구성을 이렇게 바꿨습니다

요청서 예시는 ①금감원 표준 ②보강 자료 ③따로 챙길 것이었는데, **"올리는 것 / 안 올리는 것"** 기준으로 다시 갈랐습니다.

| 요청서 예시 | 구현 | 이유 |
| --- | --- | --- |
| ① 은행이 바로 심사할 수 있는 자료 | **올릴 자료** (`fulfillBy: "upload"`) | 업로드 화면이라 **여기서 할 일**이 먼저 보여야 합니다 |
| ② 함께 내면 도움이 되는 자료 | **따로 챙기실 것**으로 합침 | ②도 요청서가 "업로드 대상이 아니며 직접 첨부로 표시"라고 적으셨습니다. ③과 성격이 같아 따로 둘 이유가 없습니다 |
| ③ 따로 챙기실 것 | 같음 (+ 자필 서명) | |
| — | **"저희가 확인해요"** 한 줄 | 구매자–송금인 대조는 사용자가 갖다 낼 게 없는데, 목록에 섞이면 준비해야 할 자료로 읽힙니다 |

**사업자등록증을 ①에서 ③으로 옮겼습니다.** 요청서 예시에는 ①에 있었는데, 서비스에 올리는 자료가 아니라 은행에 직접 내는 서류입니다. "해당 없으면 넘어가세요"는 블록 전체 각주("해당 없는 항목은 넘어가셔도 돼요")로 살렸습니다.

### 3-2. 화면에 나가는 것 (물품 거래 선택 시)

```
이 거래에는 이런 자료가 도움이 돼요
  · 거래 상대방과의 대화 내역
  · 계약서 · 세금계산서 · 거래명세서 중 하나      ← 택일이 한 줄로 묶임
  · 해당 입금 건의 계좌 거래내역
  · 물품 발송 증빙 (택배 송장 등)
  · 생계 흔적 (통신비·공과금 자동이체)
  · 협박 메시지 (해당하는 경우에만)

구매자–송금인 일치 여부는 올리신 자료에서 저희가 확인해요.

따로 챙기실 것 · 여기에 올리지 않아요
  · 명의인 신분증 사본
  · 사업자등록증
  · 재직증명서 · 소득금액증명원 · 예금거래내역서
  · 경찰 신고 접수증 · 수사 결과 통지서 (해당하는 경우에만)
  · 신청서 자필 서명 — 출력해서 직접 서명한 뒤 제출해주세요

```

**TC-24 확인 완료** — "용역·알바 대가"를 고르면 목록이 `급여 입금내역 / 용역 내용·결과물 전달 기록 / 생계 흔적 / 협박 메시지`로 바뀌고, **송장·배송 항목이 나오지 않습니다.** 택일 그룹도 `건강보험 자격득실 확인서 · 재직증명서 중 하나`로 묶여 뜹니다.

사유 미선택(문진 건너뜀·`unclear`)이면 공통 최소 자료만 뜨고 "거래 성격을 고르지 않아 공통 자료만 안내해요"를 함께 적습니다.

**금지 조항 2개 다 지켰습니다** — 붉은 경고 없음, "이걸 내면 통과됩니다" 류 표현 없음.

## 4. §3 직거래 — **A안(문진 문항 추가)**, 단 조건부로

백엔드가 선호하신 A안을 고릅니다. 규칙이 결정적이 되고, **§7 업로드 안내가 업로드 전에 정확해지는 것**이 큽니다 — B안(증거 유형 추가)은 자료를 올린 뒤에야 직거래인 걸 알게 되어, F3-07이 풀려던 "다 올린 뒤에 알게 되는" 문제가 그대로 남습니다.

### 4-1. 다만 **물품 거래일 때만 묻습니다**

무조건 7문항으로 늘리지 않겠습니다. 용역·채권 회수에는 배송 개념이 없어서 "해당 없음"만 고르게 되는 문항이 하나 생깁니다.

| 사유 | 문항 수 |
| --- | --- |
| 물품 거래 | **7** (거래 방식 추가) |
| 용역 · 채권 회수 · 미확정 | **6** (종전대로) |

거래 성격(`kind`) 바로 다음에 놓으면 조건부 노출이 자연스럽습니다. 문진 서브스텝은 지금 3+3인데 물품일 때만 3+4가 됩니다 — 페이지를 더 늘리지 않아도 됩니다.

### 4-2. 계약에 필요한 것

`/api/intake` 요청에 필드 하나가 필요합니다. **이름은 백엔드가 정해 주세요** — 아래는 제안입니다.

```
deliveryMethod: "courier" | "in_person" | "not_applicable" | null
```

- `kind !== "goods"`이면 `null`로 보냅니다
- F5-03 공백 탐지에서 `in_person`이면 **"발송 증빙 없음" 공백을 띄우지 않도록** 해주세요. 지금 규칙(`delivery_evidence == false` + 재화 거래 → 공백)이 직거래 사용자에게 채울 수 없는 요구를 만듭니다
- 카탈로그의 `goods.delivery` 항목도 `in_person`이면 라벨을 바꿔야 합니다(물품 사진·거래 장소 등). **계약 필드가 확정되면 프론트가 반영하겠습니다**

**구현은 계약 확정 후**입니다. 문진 문항은 `/api/intake` 스키마와 직결되어 있어 프론트가 먼저 만들면 어긋납니다.

## 5. §1 구매자–송금인 카드 노출 — 설계 확정, 구현은 API 연동 시

카드 확인 화면(F4-06)은 **아직 목에 없습니다.** 지금 Stage 2는 판독 결과를 토글로 흉내 낸 상태라, 카드 UI는 `/api/evidence` 연동과 함께 만들어집니다. 그때 지킬 것을 확정해 둡니다.

| 항목 | 확정 |
| --- | --- |
| 필드 표시 | `counterparty_name` / `payer_name`을 **각각 별도 행**으로. 라벨은 "대화 상대" / "입금자" |
| 종전 "상대방" 라벨 | **폐기.** 대화 상대인지 입금자인지 구분되지 않아 사용자가 무엇을 정정하는지 모릅니다 |
| `null` | **빈 칸 + 직접 입력 가능.** "읽기 실패"로 표시하지 않습니다 (흔한 정상값) |
| 불일치 안내 위치 | **카드가 아니라 준비도 화면**입니다. 대조는 `/api/readiness`가 하므로 카드 단계에는 결과 자체가 없습니다 |
| 색 | 경고색 금지. 체크리스트에서 `needs_explanation` = 중립 회색 "설명 필요" (§2-8) |

**불일치 안내 문구는 백엔드가 `checklist[].note` 또는 `notices`로 내려주세요.** "이 차이를 소명서에 설명해야 한다"는 안내는 대조 결과를 아는 쪽이 쓰는 게 맞습니다.

## 6. §5 신원·경제력 소명 — **이미 들어갔습니다**

§2의 카탈로그를 만들면서 함께 반영했습니다. 별도 작업이 필요 없습니다.

```
supporting.identity — "재직증명서 · 소득금액증명원 · 예금거래내역서"
  tier: "supporting" / fulfillBy: "self" / whenMissing: "silent"
```

물어보신 **"업로드하지 않는 항목을 체크리스트에 표현할 수 있는가"** 가 `fulfillBy: "self"`로 해결됐습니다. 종전에 `ChecklistItem.id`가 `EvidenceId`에 묶여 업로드 자료와 1:1이던 제약이 §2에서 풀렸습니다.

**"이걸 내면 통과됩니다" 류 표현은 쓰지 않았습니다** — 화면 문구는 "함께 제출하는 경우가 많아요"입니다.

## 7. §6 수사 자료 — 체크리스트 항목으로 추가

```
supporting.police_record — "경찰 신고 접수증 · 수사 결과 통지서 (해당하는 경우에만)"
  tier: "supporting" / fulfillBy: "self" / whenMissing: "silent"
  note: "신고했거나 수사가 진행 중이라면 도움이 될 수 있어요. 해당 없으면 넘어가세요."
```

**"고소당하셨나요?" 같은 질문을 전면에 두지 말라**고 하신 부분을 지켰습니다. 문진에 문항을 만들지 않았고, 체크리스트의 `silent` 항목이라 **해당하지 않는 사람에게는 아무 표시도 뜨지 않습니다.** 해당하는 사람만 토글을 누릅니다.

F9-02(형사 전환 신호 안내)와의 연결은 **백엔드 소관**으로 남겨둡니다 — 그 화면 문구는 §9 표에 백엔드가 고칠 문서로 잡혀 있습니다.

## 8. §4 플랫폼 거래 내역 — ⚠️ **프론트만 고쳐서는 안 되는 항목입니다**

이건 요청 내용에 이견이 있어서 그대로 반영하지 않았습니다.

요청서는 "`EvidenceId`에 유형 추가"를 적으셨는데, **`EvidenceId`는 목 전용 타입입니다.** 실제로 카드 유형을 정하는 것은 AI가 내려주는 **`source_type`** 이고, 그 값은 `chat / bank / shipping / threat / autopay / unknown` **6종으로 계약에 고정**돼 있습니다(`internal-api-contract.md`).

프론트가 유형을 하나 늘려도 **AI가 그 값을 내려주지 않으면 아무 카드에도 붙지 않습니다.** 지금 상태로 플랫폼 거래 화면을 올리면 `chat`으로 판정되고, 프론트에 유형만 추가한 것은 죽은 코드가 됩니다.

### 선택지

| 안 | 필요한 것 | 비용 |
| --- | --- | --- |
| **A** | AI에 `source_type: "platform"` 추가 요청 | `internal-api-contract.md` + `api-contract.md` 개정, AI 프롬프트 조항 수정, **F5-01 tie-break 순서 재확정**(6종 순서가 이미 확정돼 있음), AI 평가 세트 영향 |
| **B (권장)** | 계약은 그대로. **업로드 안내 문구에만** "중고거래 앱 거래 내역"을 명시 | 문구 한 줄 |

**B를 권합니다.** 남은 일정이 13일이고, `source_type` 추가는 AI·백엔드·프론트 세 쪽 계약을 다 건드립니다. 얻는 것은 카드 배지 문구가 "대화"에서 "플랫폼"으로 바뀌는 정도인데, **판독 내용 자체는 달라지지 않습니다** — 거래 성립 사실·물품 정보·상대 계정은 `chat`으로 판정돼도 그대로 추출됩니다.

**B로 가면 프론트가 §7 안내 문구에 한 줄 더합니다.** A로 가시겠다면 AI 담당에게 요청을 보내야 하는 건이라, 백엔드가 판단해 주세요.
