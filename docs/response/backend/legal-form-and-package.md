# [프론트 → 백엔드] 법정 서식 원본 대조 — 회신

- 작성: 프론트엔드 · 2026-08-25
- 원본 요청: `../../request/frontend/legal-form-and-package.md` (백엔드 · 2026-08-24)

> **추가 (2026-08-25 ②)** — §3-2 신설. 5면을 빼기로 한 뒤 면 구성을 다시 훑다가 **4면에 같은 문제가 남아 있을 수 있다**는 것을 발견했습니다. 확인이 필요합니다.

**3건 모두 제안대로 수용합니다.** 서명 안내(§2)는 구현까지 마쳤고, 서식 11필드 폼(§1)은 예정대로 8/29~8/31 구간에서 만듭니다.

## 1. 서식 11필드 — **제안하신 필드명 그대로 씁니다**

```json
{
  "applicant": { "name": "", "birthDate": "", "address": "", "phone": "", "mobile": "", "email": "" },
  "account":   { "bank": "", "branch": "", "depositType": "", "accountNumber": "", "holderName": "" }
}
```

`mobile` / `email` / `holderName` 세 개 신설, 나머지 8개는 그대로입니다. 다른 이름을 제안하지 않겠습니다 — 서식 기재란과 1:1로 읽히고, 이름을 바꿔봐야 양쪽이 한 번 더 맞추는 비용만 듭니다.

**8/24 회신에서 확정한 규칙은 11개 전부에 그대로 적용합니다**: 전부 선택 / 빈 값이면 공란 PDF / 폼에 필수 표시(`*`) 금지 / 길이 100자·`birthDate` 형식만 검증.

### 1-1. "신청인과 동일" 체크박스 — **둡니다. 기본값 체크입니다**

`holderName`은 체크박스로 처리합니다. 체크되어 있으면 입력칸을 숨기고 `applicant.name` 값을 그대로 `account.holderName`에 실어 보냅니다.

**기본값을 체크로 두는 이유**: 법 제7조 제1항의 이의제기 주체가 **명의인**이라 둘이 다른 경우가 예외적입니다. 기본을 해제로 두면 대다수 사용자가 같은 이름을 두 번 칩니다. 체크를 풀면 별도 입력칸이 열려 법정대리인 같은 경우를 담을 수 있습니다.

**백엔드가 받는 값은 달라지지 않습니다** — 체크 여부는 프론트 폼 상태일 뿐이고, 요청 바디에는 항상 `holderName`에 최종 문자열이 들어갑니다. 체크박스 상태를 계약에 넣지 않았습니다.

### 1-2. 폼 자체는 8/29~8/31에 만듭니다

요청서에 "8/29~8/31 서식 폼 착수 전에만 확정되면 된다"고 적어주신 대로, **이 회신은 필드 확정까지입니다.** 폼 화면(S04-1)은 `pdf-lib` 병합·이미지 페이지 생성과 같은 구간에 함께 만듭니다.

`api-contract.md`의 요청 바디를 11필드로 갱신해 주시면, 그때 그 문서를 보고 붙이겠습니다.

## 2. 서명 안내 — **구현 완료**

전자서명이 범위 밖이라 서명란이 공란으로 나가고, 모르고 파일만 보내면 반려될 수 있다는 지적에 동의합니다. 안내를 넣었습니다.

### 배치 — 내보내기 버튼 **바로 위**, 신분증 사본과 한 묶음

제안하신 대로 신분증 사본 안내와 묶었습니다. 다만 종전처럼 체크리스트 아래 각주로 두지 않고, **"따로 챙기실 것"이라는 별도 블록**으로 올렸습니다.

```
[첨부 서류 체크리스트]
        ↓
따로 챙기실 것                                   ← 신설 (brand-subtle 카드)
  · 신청서 자필 서명 — 출력해서 직접 서명한 뒤 제출.
                      이메일·팩스로 낼 때는 서명한 종이를 다시 찍거나 스캔
  · 명의인 신분증 사본 — 여기에 올리지 않아요. 은행에 낼 때 직접 첨부
        ↓
[제출 패키지 내보내기]
```

- **이름을 `spec.md` F3-07 ③의 "따로 챙기실 것"과 맞췄습니다.** 같은 두 항목을 업로드 화면(F3-07)과 소명서 화면에서 다른 이름으로 부르면 사용자가 다른 것으로 읽습니다.
- **재스캔 안내를 함께 적었습니다.** 요청서 §2가 짚은 "출력 → 자필 서명 → (이메일 접수라면) 재스캔"에서 마지막 단계가 빠지면 서명한 종이를 손에 들고 어떻게 보내는지 모르게 됩니다. 인터넷은행이 이메일·팩스 접수라는 §1의 지적과 이어지는 부분입니다.
- 내보내기를 누르는 순간에도 같은 취지의 안내를 한 번 더 띄웁니다.

경고색은 쓰지 않았습니다. 사용자가 뭘 잘못한 게 아니라 절차 안내입니다.

## 3. 5면 부족자료 체크리스트 — **은행 제출본에서 빼는 데 동의합니다**

동의합니다. 근거를 하나 더 보태면, **이번에 확정한 체크리스트 구조 때문에 문제가 더 커집니다.**

`evidence-structure-revision.md` §2 회신에서 항목마다 `whenMissing`(`blocks`/`notice`/`silent`)을 두기로 했는데, 미보유 항목 중에는 **사용자가 애초에 채울 수 없는 것**이 섞여 있습니다 — 개인 중고거래자의 사업자등록증, 차용증 없는 대여의 차용증. 화면에서는 이것들을 `silent`로 두어 **표시조차 하지 않기로** 했습니다.

그런데 이 목록이 그대로 PDF가 되어 은행에 가면, **화면에서는 감춘 항목이 제출본에서 되살아납니다.** "이 사람은 사업자등록증도 차용증도 없다"는 문장을 사용자가 스스로 정리해 건네는 셈입니다. 화면 규칙과 출력 규칙이 어긋나는 상태라, 빼는 쪽이 맞습니다.

### 3-1. ⑥ 자리 — **"제출 서류 목록" 표지를 권합니다**

제안하신 "직접 첨부해야 하는 서류 안내"에 동의하되, 조금 넓혀 **표지 한 장**으로 만드는 쪽을 권합니다.

```
제출 서류 목록

이 문서에 포함된 것
  1. 이의제기신청서 (작성 지원본)
  2. 사실관계 진술서
  3. 거래 타임라인
  4. 증빙자료 목록
  5. 증빙 원본 이미지

신청인이 따로 첨부하는 것
  · 명의인 신분증 사본
  · 1면 서명란 자필 서명
```

- **은행 담당자에게 유용합니다.** 창구·이메일 어느 쪽이든 첫 장에서 구성이 보입니다.
- **사용자에게 불리한 정보가 없습니다.** 갖춘 것과 따로 낼 것만 적히고, 못 갖춘 것은 적히지 않습니다.
- 부족자료 체크리스트는 **화면에 그대로 있습니다.** 지우지 말라고 하신 부분이고, `evidence-structure-revision.md` §2에서 다시 만든 `ChecklistPanel`이 그 역할을 합니다.

표지를 넣으면 장수는 그대로 6면이고 내용만 바뀝니다. **표지 없이 5면으로 가도 프론트는 문제없습니다** — 병합 로직이 장수에 의존하지 않습니다. 판단을 맡기겠습니다.

### 3-2. ⚠️ **4면에 같은 문제가 남아 있을 수 있습니다** (2026-08-25 ② 추가)

5면을 빼기로 한 뒤 면 구성을 다시 훑다가 발견했습니다.

`draft-preview-and-edit.md` §2가 **4면 증빙목록의 데이터 출처를 `/api/draft`의 `checklist`** 로 적어뒀는데, `checklist`는 F7-03 **첨부 서류 체크리스트**입니다 — 보유/미보유를 표시하는 그 목록이요.

**그러면 5면을 빼도 4면으로 미보유 목록이 그대로 은행에 갑니다.** 이 절에서 5면을 뺀 이유가 4면에 똑같이 적용됩니다.

| 해석 | 내용 | 은행 제출본에 |
| --- | --- | --- |
| **A. 올린 자료의 목록** | 뒤에 붙는 원본 이미지 페이지의 **목차** | ✅ 무해 |
| **B. 필요 서류 체크리스트** | 보유/미보유 표시 | ❌ 5면과 같은 문제 |

`prd.md` §4.4 매핑표가 *"첨부서류 1 = 타임라인 + 증빙목록 + 원본이미지"* 로 셋을 묶은 걸 보면 **A**로 읽는 게 맞다고 봅니다. 목록과 실물이 짝을 이루는 구조입니다.

**확정해 주세요.** B라면 4면도 화면 전용으로 빼는 것을 권합니다. 상세는 `draft-preview-and-edit.md` 회신 §4-1 ③에 적었습니다.

### 3-3. 프론트가 고친 것

내보내기 버튼 문구를 **"제출 패키지 6종 내보내기" → "제출 패키지 내보내기"** 로 바꿨습니다. 숫자를 뺀 이유는 구성이 확정되기 전이라서만은 아닙니다 — **버튼에 숫자를 박아두면 구성이 바뀔 때마다 문구가 낡습니다.** 구성은 표지(또는 화면)가 보여주는 게 맞다고 봤습니다.

## 5. 확인이 필요한 것

요청하신 3건에는 모두 답했습니다. **§3-2에서 확인 요청 1건이 생겼습니다** — 4면 증빙목록이 A(올린 자료 목록)인가 B(필요 서류 체크리스트)인가. B라면 5면만 빼는 것으로는 부족합니다.

프론트 쪽 잔여 작업은 서식 11필드 폼(8/29~8/31)이며, 이건 회신 대기 항목이 아니라 예정된 구현입니다.
