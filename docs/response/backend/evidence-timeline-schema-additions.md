# [프론트 → 백엔드] Phase 3 계약 보완 4건 회신 — 전부 수용, 클라이언트에 반영 완료

> 원본 요청: `../../request/frontend/evidence-timeline-schema-additions.md`

**4건 모두 그대로 갑니다.** 다른 가정으로 만들어 둔 것은 없었고, API 클라이언트(`frontend/src/lib/api/`)에 지금 반영했습니다. 화면 연결은 아직이라 지금 붙이면 됩니다.

## §1. `imageIndex` — 반영했습니다. 다만 **배치 순번이 아니라 세션 누적 인덱스**입니다

`uploadEvidence(file, imageIndex)`로 시그니처를 바꿔 필수 인자로 만들었습니다.

**한 가지 짚어둘 것이 있습니다.** 요청서에 "그 파일의 원래 blob 배열 인덱스(0-base)"라고 되어 있는데, 저희 화면은 **한 번에 다 올리지 않습니다.** 2장을 올려 판독하고, 나중에 `[자료 더 올리기]`로 3장을 더 올릴 수 있습니다. 이때 두 번째 배치의 인덱스는 `0,1,2`가 아니라 **`2,3,4`** 입니다.

그래서 배치 함수가 배열 순번을 자동으로 매기지 않도록 시그니처를 바꿨습니다.

```ts
// 종전 — 배치 안에서의 순번이 그대로 나가 두 번째 배치가 0부터 다시 시작한다
uploadEvidenceBatch(files: Blob[])

// 지금 — 호출부가 세션 전체에서의 위치를 명시해야 한다
uploadEvidenceBatch([{ blob, imageIndex: 2 }, { blob, imageIndex: 3 }])
```

**확인 부탁드릴 것**: 같은 세션에서 `imageIndex`가 이어서 증가하는 것(2번째 호출이 2부터 시작)이 백엔드 구현과 맞습니까? 카드의 `source_image_index`가 세션 누적 기준이어야 4면 "원본 n번"이 5면 이미지 순서와 맞습니다. 세션 안에서 같은 `imageIndex`가 두 번 오면 어떻게 되는지도 알려주시면 방어 코드를 어디에 둘지 정할 수 있습니다.

## §2. `gaps` 스키마 — 맞습니다. `no_life_activity`는 제안 영역을 통째로 감춥니다

타입(`EvidenceGap`)을 계약대로 정의했습니다. 화면 요구사항과 어긋나는 곳은 없습니다.

| 필드 | 화면에서 쓰는 방식 |
| --- | --- |
| `type` | **분기용으로만** 씁니다. 문구를 유형별로 따로 갖지 않습니다 |
| `label` | 타임라인 빈 노드의 제목으로 **그대로** 노출합니다 |
| `suggestions` | F5-04 제안 칩. **빈 배열이면 제안 영역 자체를 렌더하지 않습니다** |

`no_life_activity`처럼 제안이 없는 공백은 **"없음"이나 빈 칸을 그리지 않고 블록을 감춥니다.** 빈 상태를 그리면 "제안이 있어야 하는데 못 만들었나" 로 읽히고, 사용자가 할 일이 늘어난 것처럼 보입니다. 공백 자체는 `label`로 이미 전달됩니다.

직거래일 때 `no_delivery_evidence`가 아예 오지 않는다는 것도 확인했습니다 — 프론트에서 따로 거르지 않겠습니다.

## §3. 카드 삭제 — `confirmed: false`가 맞습니다. 다른 방식으로 만든 것 없습니다

별도 엔드포인트나 `DELETE`로 만든 것은 없습니다. 화면의 `[이 자료 빼기]`가 이 호출로 갑니다.

계약 타입을 **유니온으로 나눠** 두었습니다.

```ts
type ConfirmRequest =
  | { cardId: string; confirmed: true; corrections?: Record<string, unknown> }
  | { cardId: string; confirmed: false }
```

`corrections`가 `confirmed: true`일 때만 의미가 있다고 하셔서, **서버가 무시할 값을 실어 보내는 코드가 타입 단계에서 걸리도록** 했습니다. 호출부에는 `deleteCard(cardId)`를 따로 뒀습니다 — `confirmed: false`가 코드에서 "확인 안 함"으로 읽히는데 실제로는 세션에서 지우는 동작이라, 이름으로 구분해 두는 편이 안전합니다.

## §4. 병합 표시 방식 — 확인했습니다

응답의 `events`를 통째로 다시 그리고, 프론트에서 중복 제거를 하지 않습니다. 원본 카드가 세션에 남아 F7-05 근거 연결에 쓰인다는 것도 확인했습니다.
