# Git 운영 규칙

> **수정 기록 (2026-08-23)**
> - **브랜치·PR 절차를 삭제했습니다.** 기존 원칙 2(브랜치명 접두어)와 원칙 3(PR로 main 머지)을 없애고 **main에 직접 커밋·푸시**하는 방식으로 변경했습니다. 팀 논의 결과 3인이 각자 다른 디렉터리를 담당해 충돌 가능성이 낮고, PR 단계가 병목만 만든다고 판단했습니다.
> - 문서 제목을 "Git 브랜치 전략" → "Git 운영 규칙"으로 변경했습니다.

> PRD에는 없는 팀 운영 규칙입니다. 모노레포(`frontend/`, `backend/`, `ai-server/`)를 3인이 각자 독립된 디렉터리·독립 배포로 나눠 담당하므로, 사람 간 코드 충돌 가능성이 낮다는 전제로 가볍게 운영합니다.

## 원칙

1. **`main` 하나만 쓴다.** `develop`, `release` 같은 별도 브랜치를 두지 않는다.
2. **각자 `main`에 직접 커밋·푸시한다.** 작업 브랜치도, PR도, 리뷰도 두지 않는다 — 각자 자신의 디렉터리·서비스를 책임지고 작업하므로 병목 없이 바로 반영한다.
3. **`main`은 항상 동작하는 상태로 유지한다.** 직접 푸시하는 만큼, 깨진 상태를 올리면 다른 두 사람이 바로 영향을 받는다. 푸시 전에 본인 서비스가 뜨는지 확인한다.
4. **푸시 전에 `git pull`을 먼저 한다.** 같은 브랜치를 셋이 공유하므로 원격이 앞서 있는 경우가 잦다.

## 참고

- CI/배포 파이프라인은 서비스별로 담당자가 각자 구성한다 (`../03-infra-ops/deployment-and-uptime.md` 참조).
- API 계약(`../02-architecture/api-contract.md`, `../02-architecture/internal-api-contract.md`)이 걸린 변경은 **푸시 전에 문서를 먼저 고치고** 상대 역할에게 공유한다 (`role-assignment.md`의 "매몰 방지 원칙" 참조). PR 리뷰가 없으므로 이 문서 규칙이 유일한 안전장치다.
- 다른 역할에게 보낼 요청은 `../request/{역할}/`에, 처리 결과 회신은 `../response/{요청한 사람}/`에 문서로 남긴다 (`../README.md` 갱신 규칙).
