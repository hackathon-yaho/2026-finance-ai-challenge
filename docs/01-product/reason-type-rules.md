# 사유유형 & 제출 준비도 점검 규칙 (FE / BE / AI 공통 계약)

> 출처: `../00-context/prd.md` §4.3, `../00-context/spec.md` F6. **이 문서는 세 역할이 동일한 용어와 동일한 로직을 쓰기 위한 단일 출처입니다.** 준비도 로직을 구현·수정할 때는 이 문서와 PRD §4.3을 함께 갱신하세요.

## 0. 절대 원칙

> **제출 준비도 점검은 AI가 하지 않는다.** 아래 로직은 백엔드의 `ReadinessService`가 결정적(deterministic) 규칙으로 구현합니다. AI(LLM)는 증거에서 사실을 추출하고 문장을 생성할 뿐, 준비도를 스스로 판단하지 않습니다.
>
> **이 서비스는 은행의 승인·기각을 예측하지 않는다.** 금융감독원이 안내한 간소화 절차의 조건(소액·이력·생계)은 특정 절차의 적용 조건일 뿐, 전체 이의제기의 승인·기각 기준이 아닙니다. 서비스가 산출하는 것은 "제출 서류가 갖춰졌는가"라는 **준비도**이지, "지급정지가 해제될 것인가"라는 **결과 예측**이 아닙니다.
>
> 새로운 조건을 추가하고 싶다면 먼저 "이게 금감원 발표 또는 법령의 어느 조항에서 나온 것인가"를 확인하세요. 근거 없는 조건은 추가하지 않습니다.

## 1. 사유유형 (4종)

| 사유유형 | 트리거 예시 문구 | 대표 페르소나 | 핵심 증거 |
| --- | --- | --- | --- |
| 재화 거래 대금 | "중고 물건 판매" | P-01, P-04 | 거래 대화, 입금내역, 배송 증빙 |
| 용역 제공 대가 | "용역·알바 대가" | P-02 | 용역 내용 증빙, 입금내역, 결과물 전달 기록 |
| 채권 회수 | "빌려준 돈 회수" | P-05 | 대여 관계를 보이는 대화·송금 기록 |
| 기타/불명 | 위 세 가지에 해당하지 않음 | — | 확인 질문 1회 → 미해결 시 "사유 미확정" |

사유유형은 `F6-01`이 문진 응답(FR-010)을 그대로 매핑해 확정합니다. 확신도가 낮거나 사용자가 "잘 모르겠음"을 선택하면 `F6-02`가 확인 질문을 1회만 노출합니다(반복 금지).

## 2. 제출 준비도 산출 (금감원 2026.5.3 기준 그대로 구현)

준비도는 **소액·이력·생계** 3요건을 서비스가 직접 승인/기각 기준으로 판정하는 것이 아니라, 아래 네 가지 결정적 신호만으로 세 상태 중 하나를 산출합니다(`F6-04`).

| 신호 | 정의 |
| --- | --- |
| 미확인필드 | 사용자가 확인하지 않은 카드(FR-028) 또는 낮은 신뢰도 필드가 남아 있음 |
| 필수증빙누락 | 사유별 체크리스트(FR-041)에 미보유 항목이 있음 |
| 자료충돌 | `signals.quality_flags.amount_mismatch` 또는 날짜·배송상태 불일치 |
| 은행기준미상 | **과거 지급정지 이력 있음** OR 은행 내규 기준을 서비스가 알 수 없는 항목이 있음 |

```
IF 미확인필드 OR 필수증빙누락:
    상태 = "증빙 보완 필요" (SUPPLEMENT_NEEDED)
    안내 = 무엇이 빠졌는지 + 어떻게 보완하는지
ELIF 자료충돌 OR 은행기준미상:
    상태 = "은행 확인 필요" (BANK_CHECK_REQUIRED)
    안내 = 충돌 내용 표시 + 간소화 적용 여부는 금융회사 확인 사항임을 안내
ELSE:
    상태 = "제출 준비 완료" (SUBMISSION_READY)
    안내 = 확인된 자료 요약 + 금융회사 판단이 남아 있음을 명시
```

**세 상태 모두 화면에 "최종 판단은 은행이 합니다"를 함께 표시합니다.**

> **'소액'의 정확한 금액 기준은 은행 내규로 비공개**입니다(PRD §14 OI-01). 입금액은 소명서의 **사실 기재**에만 사용하며, 준비도 산출의 판정 조건으로 쓰지 않습니다. 소액 관련 안내는 §4.3의 "소액 안내 카드"(정보 제공용)로만 노출하고, "소액에 해당하니 유리하다"처럼 단정하지 마세요.

확신도가 낮아 사유유형을 하나로 못 정하면(FR-031), 준비도 산출 전에 확인 질문을 1회 노출하고 응답에 따라 위 로직으로 분기합니다.

## 3. 금지 문구 원칙

**은행 확인 필요(BANK_CHECK_REQUIRED)** 케이스, 특히 과거 지급정지 이력이 있는 경우는 **이 서비스의 신뢰를 결정하는 지점**입니다.

- 금지: "기각될 수 있습니다", "해제 가능성이 높습니다", "그래도 해볼 만합니다", "혹시 모르니 신청해보세요" 등 결과 예측·낙관·위로 표현 일체
- 허용: "과거 지급정지 이력이 있어 간소화 절차 대상이 아닐 수 있습니다. 은행 확인이 필요하며, 최종 판단은 은행이 합니다."

프론트엔드는 이 문구를 그대로 노출하고 임의로 순화하지 않습니다. AI(소명서 생성 프롬프트)도 이 케이스에서 결론적·낙관적 어휘를 생성하지 않도록 프롬프트에 명시적으로 금지 조항을 둡니다(`../00-context/prd.md` §10.2 참조).
