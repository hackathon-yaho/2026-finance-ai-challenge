## 0. 절대 원칙

> **제출 준비도 점검은 AI가 하지 않는다.** 아래 로직은 백엔드의 `ReadinessService`가 결정적(deterministic) 규칙으로 구현합니다. AI(LLM)는 증거에서 사실을 추출하고 문장을 생성할 뿐, 준비도를 스스로 판단하지 않습니다.
>
> **이 서비스는 은행의 승인·기각을 예측하지 않는다.** 금융감독원이 안내한 간소화 절차의 조건(소액·이력·생계)은 특정 절차의 적용 조건일 뿐, 전체 이의제기의 승인·기각 기준이 아닙니다. 서비스가 산출하는 것은 "제출 서류가 갖춰졌는가"라는 **준비도**이지, "지급정지가 해제될 것인가"라는 **결과 예측**이 아닙니다.
>
> 새로운 조건을 추가하고 싶다면 먼저 "이게 금감원 발표 또는 법령의 어느 조항에서 나온 것인가"를 확인하세요. 근거 없는 조건은 추가하지 않습니다.

| 사유유형 | 트리거 예시 문구 | 대표 페르소나 | 금감원 표준 소명자료 |
| --- | --- | --- | --- |
| 재화 거래 대금 | "중고 물건 판매" | P-01, P-04 | **있음** — §2-1 물품 거래 |
| 용역 제공 대가 | "용역·알바 대가" | P-02 | **있음** — §2-1 용역·급여 |
| 채권 회수 | "빌려준 돈 회수" | P-05 | **없음** — 공통 최소 자료 적용 (§2-2) |
| 기타/불명 | 위 세 가지에 해당하지 않음 | — | **없음** — 공통 최소 자료 적용 (§2-2). 확인 질문 1회 → 미해결 시 "사유 미확정" |

사유유형은 `F6-01`이 문진 응답(FR-010)을 그대로 매핑해 확정합니다. 확신도가 낮거나 사용자가 "잘 모르겠음"을 선택하면 `F6-02`가 확인 질문을 1회만 노출합니다(반복 금지).

> **금감원 표준은 4종이 아니라 2종뿐입니다** (2026-08-25 조사 확인). 물품 거래와 용역·급여 두 유형만 표준화됐고, **채권 회수·기타에 대한 표준 목록은 존재하지 않습니다.** 종전에 이 문서와 `spec.md` F7-03이 4유형 모두에 목록을 두고 근거를 "금감원 2026.5.3"으로 표기했으나, 뒤 두 유형은 근거 없이 우리가 만든 것이었습니다 — §0의 "근거 없는 조건은 추가하지 않는다" 원칙 위반이라 아래 §2 구조로 정정했습니다.

## 2. 소명자료의 세 층 — 성격이 다릅니다

체크리스트를 만들 때 이 셋을 **같은 무게로 표시하면 안 됩니다.**

| 층 | 성격 | 근거 | 갖추지 못하면 |
| --- | --- | --- | --- |
| **① 법정 첨부서류** | **필수** | 시행령 제7조 (별지 제4호서식에 인쇄돼 있음) | 접수 요건 미충족 |
| **② 금감원 표준 소명자료** | **기준선** | 금감원 2026.5 업무처리 표준화 | 반려가 아니라, 금융회사가 추가 자료를 요구할 수 있음 |
| **③ 보강 자료** | **선택 · 가점** | 실무 관행 (법령·금감원 근거 아님) | 불이익 없음 |

> **②를 관문으로 만들지 마세요.** 금감원 표준은 *"이 정도만 받아 수용 여부를 결정한다"* 는 **부담 경감** 기준이지, *"이게 없으면 안 된다"* 는 요건이 아닙니다. 실제로 개인 중고거래자는 사업자등록증이 없어 물품 거래 표준을 채울 수 없지만, 법정 요건인 "사기이용계좌가 아니라는 사실을 증명하는 자료"는 **자유 형식**이므로 이의제기 자체가 막히지 않습니다.

### 2-1. 금감원 표준 소명자료 (물품 거래 · 용역/급여만)

| 유형 | 표준 소명자료 |
| --- | --- |
| **물품 거래** | 사업자등록증 / 거래상대방 대화내역 / **계약서·세금계산서·거래명세서 중 택일** / 구매자–송금인 일치 여부 |
| **용역·급여** | **건강보험자격득실확인서·재직증명서 중 택일** / 급여 입금내역 |

**택일 항목은 하나만 있으면 충족입니다.** 전부 요구하면 금감원이 완화한 기준을 되돌리는 것이 됩니다.

#### "구매자–송금인 일치 여부"를 서비스가 채우는 방식 (2026-08-25 확정)

이 항목만은 사용자가 별도 서류를 떼 오는 것이 아니라, **이미 올린 자료에서 서비스가 뽑아 대조**합니다.

| 재료 | 출처 |
| --- | --- |
| 구매자 이름 | 대화 캡처의 대화 상대 표시명 → 추출 카드의 `counterparty_name` |
| 송금인 이름 | 입금 내역 캡처의 입금자 표기 → 추출 카드의 `payer_name` |

- **대조는 결정적 규칙 엔진(백엔드)이 합니다.** AI는 두 값을 추출만 하고 일치 판정을 하지 않습니다 (§0 원칙).
- **둘 다 값이 있을 때만 대조합니다.** 한쪽이라도 `null`이면 "확인 불가"이지 "불일치"가 아닙니다 — 상단바를 자른 캡처, 사용자가 F3-06으로 가린 경우가 흔합니다.
- **불일치를 준비도 하향 신호로 쓰지 않습니다.** 닉네임과 실명이 다른 것은 정상이고, 삼각사기 피해자는 **원래 불일치합니다.** 결과는 "설명이 필요한 항목"으로만 안내하며, 이 값이 §3의 네 가지 결정적 신호에 들어가지 않는다는 뜻입니다.
- 이름 추출의 개인정보 경계는 `../03-infra-ops/privacy-and-safety.md` "추출 범위 예외 — 거래 당사자 표시명" 절이 단일 출처입니다.

### 2-2. 공통 최소 자료 (채권 회수 · 기타/불명)

표준이 없는 유형은 아래를 **참고 안내**로 제시합니다. **"필수"로 표시하지 않습니다.**

- 거래 상대방과의 대화·연락 기록
- 해당 입금 건의 계좌 거래내역
- 구매자–송금인(대여 상대–송금인) 일치 여부를 확인할 수 있는 자료
- 대여 관계라면 차용증·이체 기록 등 관계를 보이는 자료 (있는 경우)

> 채권 회수 유형은 근거 문서가 없으므로 **화면 문구에서 "필수" 표현을 쓰지 않습니다.** "이런 자료가 있으면 도움이 됩니다" 수준으로만 안내합니다. P-05(차용증 없는 채권 회수)처럼 자료가 원래 부족한 사용자에게 채울 수 없는 요구를 하면 안 됩니다.

### 2-3. 보강 자료 (전 유형 공통 · 선택)

재직증명서 · 소득금액증명원 · 예금거래내역서 등 **본인의 신원·경제력을 보이는 자료**입니다. 실무상 인용률을 높이는 것으로 알려져 있으나 **법령·금감원 근거는 없습니다.** 서비스에 업로드받지 않고, 제출 단계에서 직접 첨부하도록 안내만 합니다.

**"이걸 내면 통과됩니다"라고 말하지 마세요.** 승인·기각 예측 금지 원칙(§4)에 걸립니다. "함께 제출하는 경우가 많습니다" 수준으로 적습니다.

## 3. 제출 준비도 산출 (금감원 2026.5.3 기준 그대로 구현)

준비도는 **소액·이력·생계** 3요건을 서비스가 직접 승인/기각 기준으로 판정하는 것이 아니라, 아래 네 가지 결정적 신호만으로 세 상태 중 하나를 산출합니다(`F6-04`).

| 신호 | 정의 |
| --- | --- |
| 미확인필드 | 사용자가 확인하지 않은 카드(FR-028) 또는 낮은 신뢰도 필드가 남아 있음 |
| 필수증빙누락 | 체크리스트에서 **`whenMissing: "blocks"`인 항목** 중 `met`이 아닌 것이 있음 (2026-08-25 정정 — 아래 §3-1) |
| 자료충돌 | `signals.quality_flags.amount_mismatch` 또는 날짜·배송상태 불일치 |
| 은행기준미상 | **과거 지급정지 이력 있음** OR 은행 내규 기준을 서비스가 알 수 없는 항목이 있음 |

> **구매자–송금인 이름 불일치는 이 네 신호 어디에도 들어가지 않습니다** (§2-1). 체크리스트 항목 상태(`needs_explanation`)로만 반영합니다.

```
IF 미확인필드 OR 필수증빙누락:
    상태 = "증빙 보완 필요" (SUPPLEMENT_NEEDED)
    안내 = 무엇이 빠졌는지 + 어떻게 보완하는지
ELIF 자료충돌 OR 은행기준미상:
    상태 = "은행 확인 필요" (BANK_CHECK_REQUIRED)
    안내 = 충돌 내용 표시 + 간소화 적용 여부는 금융회사 확인 사항임을 안내
ELSE:
    상태 = "제출 준비 완료" (SUBMISSION_READY)
    안내 = 확인된 자료 요약 + 금융회사 판단이 남아 있음을 명시
```

**세 상태 모두 화면에 "최종 판단은 은행이 합니다"를 함께 표시합니다.**

> **'소액'의 정확한 금액 기준은 은행 내규로 비공개**입니다(PRD §14 OI-01). 입금액은 소명서의 **사실 기재**에만 사용하며, 준비도 산출의 판정 조건으로 쓰지 않습니다. 소액 관련 안내는 §4.3의 "소액 안내 카드"(정보 제공용)로만 노출하고, "소액에 해당하니 유리하다"처럼 단정하지 마세요.

확신도가 낮아 사유유형을 하나로 못 정하면(FR-031), 준비도 산출 전에 확인 질문을 1회 노출하고 응답에 따라 위 로직으로 분기합니다.

### 3-1. `필수증빙누락`을 좁힌 이유 (2026-08-25 정정)

**종전 정의는 "체크리스트에 미보유 항목이 있음"이었습니다.** 그대로 구현하면 TC-21·TC-22가 깨집니다 — ②③④의 모든 미보유가 신호가 되어, **채울 방법이 없는 항목 때문에 사용자가 영원히 "보완 필요"에 갇힙니다.**

그런데 §2의 층(tier)만으로는 이걸 가를 수 없습니다. **같은 ② 금감원 표준인데 기대 결과가 반대인 케이스가 있기 때문입니다.**

| | 층 | 기대 결과 |
| --- | --- | --- |
| TC-21 물품 · **사업자등록증** 없음 | ② fss | `SUPPLEMENT_NEEDED`가 **아니어야** 함 |
| TC-02 용역 · **재직 증빙 계열** 없음 | ② fss | `SUPPLEMENT_NEEDED`가 **맞아야** 함 |

**층(근거가 어디서 나왔나)과 미보유 효과(못 채우면 어떻게 되나)는 독립된 두 축**입니다. 그래서 체크리스트 항목마다 `whenMissing`을 따로 둡니다.

| `whenMissing` | 효과 |
| --- | --- |
| `blocks` | `필수증빙누락` 신호에 포함 — 준비도를 깎음 |
| `notice` | "미보유 — 보완 요청 사유가 될 수 있어요" 문구만. **준비도를 깎지 않음** |
| `silent` | 아무 표시도 하지 않음 |

#### `blocks`를 붙이는 기준 — **사용자가 실제로 채울 수 있는가**

> **`blocks`는 이미 존재하거나 즉시 발급받을 수 있는 자료에만 붙입니다.**

| 자료 | `blocks`? | 이유 |
| --- | --- | --- |
| 건강보험 자격득실 확인서 · 재직증명서 | **가능** | 근로자면 정부24·건강보험공단에서 **즉시 무료 발급**. 채울 수 있으니 가두지 않음 |
| 사업자등록증 | **불가** | 개인은 **발급 자체가 불가능** |
| 계약서 · 세금계산서 · 거래명세서 | **불가** | 개인 간 거래엔 원래 없고, **사후에 만들면 증거 조작**입니다. PRD가 "증거 생성·보정은 원칙적으로 금지"라고 못박은 영역이라 요구해서는 안 됩니다 |
| 신분증 사본 | **불가** | ①이라 필수인 건 맞지만 서비스가 받지 않아 판정할 수 없습니다. `blocks`로 두면 **전원이 영원히 보완 필요**입니다. 화면에서 "반드시 내야 하는 것" 맨 앞에 두는 것으로 해결합니다 |
| `legal.proof` (사기이용계좌가 아니라는 사실을 증명하는 자료) | **가능** | **자유 형식**이라 확인된 업로드 자료가 1건이라도 있으면 `met`. 자료 0건이면 `blocks`가 서서 TC-06이 `SUPPLEMENT_NEEDED`가 됩니다 — 자료를 올리면 풀리므로 가두는 요구가 아닙니다 |

**항목을 새로 추가할 때 이 기준으로 판단하세요.** 기준 없이 늘리면 또 흔들립니다. 근거: `../response/backend/evidence-structure-revision.md` §2-1.

### 3-2. 체크리스트 항목 구조 (2026-08-25 확정)

`/api/readiness`·`/api/draft` 응답의 `checklist` 배열 원소입니다. 스키마 본문은 `../02-architecture/api-contract.md`가 단일 출처이고, 여기서는 **판정에 쓰이는 의미**만 정의합니다.

| 축 | 값 | 뜻 |
| --- | --- | --- |
| `tier` | `legal` / `fss` / `common` / `supporting` | ①②③④ — **근거가 어디서 나왔나** (§2) |
| `fulfillBy` | `upload` | 서비스에 올리는 캡처 |
| | `self` | 서비스에 올리지 않고 **사용자가 은행에 직접 첨부** |
| | `derived` | **올린 자료에서 서버가 뽑아 채움** (구매자–송금인 대조). 사용자가 갖다 낼 것이 없음 |
| `whenMissing` | `blocks` / `notice` / `silent` | **못 채우면 어떻게 되나** (§3-1) |
| `status` | `met` / `unmet` | 보유 / 미보유 |
| | `unknown` | **확인 불가** (대조할 값 한쪽이 `null`). **불일치가 아님** (TC-26) |
| | `needs_explanation` | 값은 나왔으나 소명서에 설명이 필요 (구매자–송금인 불일치). **위험 신호가 아니며 준비도를 깎지 않음** (TC-25) |

- **택일(OR)은 `options` 배열**로 표현합니다. **하나라도 `met`이면 그룹 전체가 `met`** (TC-23).
- `fulfillBy: "self"` 항목은 서비스가 보유 여부를 알 수 없어 **사용자 자가 진술**로 받습니다 (`POST /api/checklist/self-held`). 이 값은 서류 자체가 아니므로 **세션에만 두고 PDF·로그에 남기지 않습니다.**

## 4. 금지 문구 원칙

**은행 확인 필요(BANK_CHECK_REQUIRED)** 케이스, 특히 과거 지급정지 이력이 있는 경우는 **이 서비스의 신뢰를 결정하는 지점**입니다.

- 금지: "기각될 수 있습니다", "해제 가능성이 높습니다", "그래도 해볼 만합니다", "혹시 모르니 신청해보세요" 등 결과 예측·낙관·위로 표현 일체
- 허용: "과거 지급정지 이력이 있어 간소화 절차 대상이 아닐 수 있습니다. 은행 확인이 필요하며, 최종 판단은 은행이 합니다."

### 4-1. 시간·후속 불이익도 같은 원칙을 따릅니다 (2026-08-25 추가)

결과 예측만 금지 대상이 아닙니다. **서비스가 보장할 수 없는 시간**과 **근거 없는 기간 수치**도 같습니다.

| 대상 | 금지 | 허용 |
| --- | --- | --- |
| **심사 기간** | "은행이 **5영업일 안에** 판단할 수 있게 정리해요" — 숫자가 약속처럼 읽히고, **서비스가 5영업일을 주는 것처럼** 읽힙니다 | "은행이 **판단할 수 있는 형태로** 정리해드려요" / 통계 표기는 "심사 결과 통보 · **해제 시점은 아니에요**" |
| **심사 결과 ≠ 해제** | 둘을 같은 문장에 뭉뚱그리기 | 통보와 해제를 **분리해 서술** (법 제8조 제2항 — 피해자 통보일로부터 2개월 제한이 별도로 작동) |
| **후속 불이익 기간** | "**최대 3년**" 처럼 **1차 출처 없는 수치** | "**한동안** 제한될 수 있어요" + 해제 경로 안내 |

> **PRD §2.7의 "숫자를 만들어 쓰지 않는다"가 우리 쪽 숫자에도 적용됩니다.** 소액 금액 기준을 추정하지 않기로 한 서비스(OI-01)가 후속 불이익 기간만 블로그·후기 근거로 단정하면 앞뒤가 맞지 않습니다. **1차 출처(은행연합회 규약, 금융위·금감원 자료, 법령)를 확보하면 그때 숫자를 넣습니다.**
>
> **불이익만 적고 끝내지 않습니다.** 등록 제한을 안내하면 **해제 경로를 같은 문장에 붙입니다** — 안 그러면 "그래서 어쩌라는 건가"가 됩니다. 근거: `../response/backend/honest-disclosure-fixes.md` §2.

프론트엔드는 이 문구를 그대로 노출하고 임의로 순화하지 않습니다. AI(소명서 생성 프롬프트)도 이 케이스에서 결론적·낙관적 어휘를 생성하지 않도록 프롬프트에 명시적으로 금지 조항을 둡니다(`../00-context/prd.md` §10.2 참조).
