| 서브스텝 표기 | 단계 인디케이터(F1-04)의 5단계는 그대로 두고, 서브스텝은 S01 화면 안에서만 표시한다. 상단 인디케이터를 6칸으로 늘리지 않는다 |
| 뒤로 가기 | 2쪽에서 뒤로 가면 S00이 아니라 1쪽으로 간다. 서브스텝을 먼저 소진한 뒤 이전 단계로 나간다 |
| 처리 | 입력 즉시 `POST /api/intake` 증분 저장. 쪽 분할은 화면 표현이며 계약(단일 요청)에 영향을 주지 않는다 |
| 수용 기준 | **현재 쪽의 문항**이 모두 입력 또는 "확인 불가" 선택되면 다음 버튼 활성화 |

### F2-01a 거래 방식 문항 (2026-08-25 신설 · 조건부)

| 항목 | 내용 |
| --- | --- |
| **노출 조건** | **`kind == "goods"`(중고 물건 판매)일 때만.** 거래 성격 바로 다음에 놓는다 |
| 선택지 | 택배로 보냈어요(`courier`) / 직접 만나서 건넸어요(`in_person`) / 해당 없어요(`not_applicable`) |
| 계약 필드 | `/api/intake`의 `deliveryMethod`. `kind !== "goods"`면 `null`로 보낸다 |
| **왜 필요한가** | **직거래는 송장이 원래 없다.** F5-03 ①이 이걸 모르면 직거래 사용자에게 **채울 방법이 없는 "발송 증빙 없음" 공백**을 영원히 띄우고 준비도를 깎는다. 실제 사례: 순금 팔찌를 직거래로 판 사용자가 증빙이 없어 거래 장소 CCTV를 찾아다녀야 했던 건 |
| 후속 효과 | `in_person`이면 ① **F5-03 ① 공백 판정 제외** ② 체크리스트 `goods.delivery` 라벨이 물품 사진·거래 장소·대면 인도 정황으로 바뀜 ③ **F3-07 업로드 안내도 같이 바뀜** |
| **용역·채권 회수에 묻지 않는 이유** | 배송 개념이 없어 "해당 없음"만 고르게 되는 문항이 하나 생긴다. 무조건 7문항으로 늘리지 않는다 |

**문항별 선택지 및 용도**

| 문항 | 선택지 | 용도 |
| --- | --- | --- |
| 지급정지일 | 날짜 직접 선택 (모르면 "확인 불가") | **기한 계산 (FR-014)** |
| 채권소멸절차 개시 공고 | 통지받음(공고일 입력) / 아직 없음 / 모름 | **기한 계산 (FR-014)** |
| 문제 입금액 | 금액 직접 입력 (모르면 "확인 불가") | **소명서 사실 기재 전용** |
| 거래 성격 | 중고 물건 판매 / 용역·알바 대가 / 빌려준 돈 회수 / 잘 모르겠음 | **거래 유형 분류 (F6-01)** |
| **거래 방식** (물품일 때만) | 택배로 보냈어요 / 직접 만나서 건넸어요 / 해당 없어요 | **F5-03 ① 직거래 예외 (F2-01a)** |
| 과거 이력 | 없음 / 있음 | **은행 확인 필요 분기 (F6-04)** |
| 계좌 사용 목적 | 주 거래 계좌다 / 가끔 쓴다 / 거의 안 쓴다 | **생계 흔적 증빙 점검 보조 (F5-03)** |

> **과거 이력(`history`)과 공고 관련 문항은 소명서 생성 입력으로 전달하지 않는다** (2026-08-25 확정). 준비도 판정에만 쓰이는 값이고, **사용자에게 불리한 정보를 본인이 은행에 내는 문서에 스스로 적어 넣게 만들지 않기** 위해서다. 상세: `../02-architecture/internal-api-contract.md` `intake` 객체 절.

> **입금액은 사실 정보로만 기록한다.** 소액 여부는 서비스가 판정하지 않으며, 간소화 절차 적용 여부는 금융회사 확인 사항으로 안내한다. (F6-03 금지 조항)

### F3-01 이미지 다중 업로드

| 항목 | 내용 |

| 제한 | 파일당 10MB, 총 10장 |
| 처리 | ① 클라이언트에서 장변 1600px 리사이즈 ② 마스킹 적용 (F3-06) ③ 결과 blob을 브라우저 메모리 배열에 보관 ④ multipart로 서버 전송 (**Storage 미사용**) |

| **개발 주의** | 처리 ①(1600px 리사이즈)을 빠뜨리면 전송 해상도가 **사용자 화면 크기와 DPR에 좌우된다.** 데스크톱 1x에서 세로 캡처가 199×431까지 줄어 계좌번호·시각·금액을 사람도 못 읽는 사례가 실제로 있었다(2026-08-24 수정). F4-01 판독 정확도가 낮으면 여기부터 확인할 것 |
| **개발 주의** | 리사이즈 적용 후 장당 300KB~1MB가 된다. **Spring Boot 기본 `spring.servlet.multipart.max-file-size`는 1MB**라 그대로 두면 정상 이미지가 `400`으로 떨어진다 — 10MB로 올릴 것 |
| 수용 기준 | 4장 동시 업로드 시 전부 처리 |

### F3-03 업로드 진행 표시

| 항목 | 내용 |
| --- | --- |
| 설명 | 파일별 처리 상태를 순차 표시해 대기 이탈을 방지한다 |
| 상태 | 대기 → 읽는 중 → 읽음 / 실패 |
| 표시 | 진행 바 + 파일명 목록 + `n/총개수` |
| 수용 기준 | 총 8~14초 구간 동안 화면이 비지 않음 |
| 구현 방식 | **이미지 1장당 1요청, 동시 4개까지**(2026-08-24 확정). 응답이 도착하는 순서대로 파일별 "읽음 / 실패"를 칠한다 — **SSE·폴링 인프라를 만들지 않는다** |
| 개발 주의 | **이 구간이 비면 사용자가 이탈한다.** 일괄 응답을 기다리는 구현으로 되돌리지 말 것 |

| 건너뛰기 | 허용. 단 "가리지 않고 보내시겠습니까?" 1회 확인 |
| 수용 기준 | 마스킹 후 전송된 이미지에서 가린 영역이 복원되지 않음 |

| 연관 | F4-03 (서버단 2차 마스킹), 개인정보보호위원회 생성형 AI 안내 |

### F3-07 사유별 업로드 안내 (업로드 전 "무엇을 올릴지" 제시)

| 항목 | 내용 |
| --- | --- |
| 설명 | **업로드 화면에서** 문진에서 고른 사유유형에 맞는 자료 목록을 먼저 보여준다. 빈 업로드 박스만 두지 않는다 |
| 배경 | F7-03 체크리스트는 **Stage 4(소명서)** 에 있어, 사용자가 **자료를 다 올린 뒤에야** 무엇이 필요했는지 알게 된다. 그러면 Stage 2로 되돌아가야 하고, 이미 캡처를 지웠다면 되돌릴 수도 없다 |
| 위치 | S02 업로드 패널 상단 (파일 선택 영역보다 **위**) |
| 데이터 출처 | `../01-product/reason-type-rules.md` §2 — **F7-03과 같은 데이터를 공유한다.** 목록을 두 곳에 복사하지 않는다 |
| 표시 구조 (2026-08-25 개정) | **"올리는 것 / 안 올리는 것"** 기준으로 가른다. 업로드 화면이므로 **여기서 할 일**이 먼저 보여야 한다 |
| ① 올릴 자료 | `fulfillBy: "upload"`인 항목 — **택일은 "이 중 하나만 있으면 돼요"로 한 줄에 묶어 표시.** 중고거래 앱(당근마켓·번개장터 등) 거래 내역도 여기에 명시한다 |
| ② 저희가 확인해요 | `fulfillBy: "derived"` — **구매자–송금인 일치 여부.** 사용자가 갖다 낼 게 없는데 목록에 섞이면 준비해야 할 자료로 읽힌다. 한 줄로 분리 |
| ③ 따로 챙기실 것 | `fulfillBy: "self"` 전부 — 신분증 사본, 사업자등록증, 재직증명서·소득금액증명원, 경찰 신고 접수증, 신청서 자필 서명. **"여기에 올리지 않아요"** |
| **②를 ③에 합친 이유** | 종전 구성의 "함께 내면 도움이 되는 자료"(보강 자료)도 **업로드 대상이 아니라 직접 첨부**다. ③과 성격이 같아 따로 둘 이유가 없다 |
| **사업자등록증 위치** | ①이 아니라 **③**이다. 서비스에 올리는 자료가 아니라 은행에 직접 내는 서류다 |
| 직거래 반영 | `deliveryMethod == "in_person"`이면 ①의 송장·배송 항목이 **물품 사진·거래 장소·대면 인도 정황**으로 바뀐다 (F2-01a) |
| **이름 통일** | ③의 이름을 **F7-07의 "따로 챙기실 것"과 맞춘다.** 같은 항목을 화면마다 다르게 부르면 사용자가 다른 것으로 읽는다 |
| **금지** | **해당 없는 항목을 붉은 경고로 표시하지 않는다.** 개인 중고거래자의 사업자등록증처럼 **애초에 발급받을 수 없는 항목**은 "해당 없으면 넘어가세요"로 안내한다 (TC-21) |
| **금지** | **"이걸 내면 통과됩니다" 류의 표현을 쓰지 않는다.** 허용: "이 자료를 갖추면 금융회사가 5영업일 내 심사합니다" (`reason-type-rules.md` §4 금지 문구 원칙) |
| 사유 미선택 시 | 문진을 건너뛰었거나 `unclear`이면 §2-2 공통 최소 자료를 안내한다 |
| 수용 기준 | 문진에서 "용역·알바 대가"를 고른 사용자에게 **송장·배송 관련 안내가 노출되지 않는다** |
| 연관 | F3-05(캡처 방법 안내), F6-03, F7-03 |

> **F3-05와 다른 기능이다.** F3-05는 *"어떻게 캡처하나"*(기종별 키 조합)이고, F3-07은 *"무엇을 올려야 하나"*(사유별 자료 목록)다. 둘 다 업로드 화면에 필요하다.

#### 거래 당사자 표시명 예외 (2026-08-25 확정)

금감원 표준 소명자료에 **"구매자와 송금인이 일치하는지 확인할 수 있는 자료"** 가 있습니다(`../01-product/reason-type-rules.md` §2-1). 이 대조를 하려면 두 이름이 필요합니다.

| 구분 | 처리 |
| --- | --- |
| **거래 당사자**(대화 상대, 입금자)의 화면 표시명 | **원문 추출** — `counterparty_name` / `payer_name` |
| 그 외 모든 이름 (제3자, 대화에 언급된 사람) | **기존대로 추출하지 않음** |

- **부분 마스킹(`김O수`)은 채택하지 않았습니다.** ① 동성·동돌림자 오탐(김민수/김영수 → 둘 다 `김O수`)으로 판별력이 떨어지고 ② 마스킹 규칙 자체를 LLM에 시키면 2글자 이름·법인명·외국명에서 **비결정적**이 되어, 결정적 대조 로직의 전제가 깨집니다. 판단 근거: `../response/backend/payer-name-extraction.md` §2.
- **소명서 본문에도 원문 그대로 씁니다.** 이 문서는 사용자 본인이 은행에 제출하는 서류이므로, 은행이 원본과 대조할 수 있어야 목적을 달성합니다. 소명서에서만 가리면 문서의 쓸모가 반감됩니다.
- **경계는 그대로입니다** — 전화번호·계좌번호 전체·주민등록번호·주소는 여전히 추출 금지입니다. 이 예외는 "판독 목적에 불필요한 식별자"가 아니라 **거래 사실 그 자체**인 값에만 적용됩니다.
- 저장 원칙 불변: 추출 JSON은 서버 세션(30분 TTL)에만 존재하고 DB·로그에 남지 않습니다. AI-server는 아무것도 저장하지 않습니다.
- 사용자 통제 2단: **F3-06**으로 미리 가릴 수 있고(가리면 `null`), **F4-06** 확인 카드에서 확인·수정·삭제할 수 있습니다.

> **F3-06 안내 문구 주의**: 마스킹 안내가 "제3자 이름을 가리세요"라고만 하면 사용자가 **거래 상대방 이름까지 가려 이 기능이 무력화**됩니다. F3-06 안내에 **"거래 상대방·입금자 이름은 가리지 마세요"** 를 함께 노출해야 합니다 (프론트 요청 `../request/frontend/evidence-structure-revision.md` 참조).

### F4-06 추출 결과 사용자 확인 카드

| 항목 | 내용 |
| --- | --- |
| 설명 | AI가 읽어낸 내용을 사건 카드로 보여주고 사용자가 맞는지 확인·수정한다 |

| 카드 항목 | 날짜 / 금액 / 상대방 / 거래 내용 / 배송 여부 / 원본 화면 썸네일 |
| 처리 | ① 이벤트별 카드 생성 ② 각 항목 인라인 수정 가능 ③ `[맞습니다]` 클릭 시 confirmed=true ④ 카드 삭제 가능 |
| 게이팅 | **날짜 또는 금액이 low 신뢰도인 카드가 미확인 상태면 S03 진입 차단.** 그 외 미확인 카드는 진행 허용하되 "확인하지 않은 자료 n건은 문서에 포함되지 않습니다" 경고 |
| 소명서 반영 | **confirmed=true 카드만 F7-01 입력으로 전달한다** |
| 수용 기준 | 미확인 카드의 날짜·금액이 소명서 본문에 나타나지 않음 |
| 연관 | F7-01, F7-02, F7-05 |
| 표시 | 필드별 신뢰도 배지(높음 / 확인 필요) + 원본 위치 하이라이트 + 사용자 수정 시 "사용자 수정" 배지 |
| 미상처리 | 확인 불가한 값은 임의로 채우지 않고 **미상**으로 유지 |

### F4-07 증빙 품질 검사

| 항목 | 내용 |
| --- | --- |
| 설명 | 읽는 것을 넘어 "이 자료로는 부족하다"를 알려준다 |
| 검사 항목 | ① 이미지가 흐려 금액 판독 불가 ② 채팅 상대방 이름 잘림 ③ 거래 날짜 미표시 ④ 택배 송장번호 가려짐 ⑤ 대화 앞뒤 맥락 부족 ⑥ 거래금액이 자료마다 다름 |
| 처리 | LLM이 quality_flags 산출 → 서버에서 자료 간 금액 교차 대조 → 문제 유형별 안내 문구 매핑 |

### F5-02 중복 이벤트 병합

| 항목 | 내용 |
| --- | --- |
| 설명 | 같은 사건이 여러 캡처에 걸쳐 나올 때 하나로 합친다 |
| 판단 | 시각 차 5분 이내 + 금액 일치 + `actor` 동일 |
| 처리 | **자동 확정하지 않는다.** 병합 후보로 사용자에게 제시하고 승인받은 경우에만 병합한다. 출처는 둘 다 기록 |
| 후보 전달 | `GET /api/timeline` 응답의 `mergeCandidates: [{ groupId, eventIds, reason }]`. `reason`은 사용자에게 그대로 보여줄 수 있는 문장이어야 한다 — 왜 같은 사건으로 보이는지 설명 없이 승인받지 않는다 |
| 승인 | `POST /api/timeline/merge` — `{ mergeGroupIds, approved }`, 응답은 갱신된 타임라인 전체 (2026-08-24 확정, `../02-architecture/api-contract.md`) |
| 거절 | `approved: false`면 후보를 거절로 기록하고 이후 `mergeCandidates`에서 제외한다. 이벤트는 그대로 둔다 |
| **스코프 컷 시** | 백엔드는 `mergeCandidates`를 **항상 빈 배열로** 내리고 승인 엔드포인트를 구현하지 않는다. 프론트는 빈 배열이면 후보 UI를 렌더하지 않는다 — **양쪽이 서로를 기다리지 않고 같이 컷된다.** 컷 결정이 나면 `../response/frontend/`에 회신한다 |

### F5-03 증거 공백 탐지

| 항목 | 내용 |
| --- | --- |
| 설명 | 소명에 필요한데 없는 자료를 지목한다 |
| 탐지 규칙 | ① `delivery_evidence == false` + 사유가 재화 거래 **+ `deliveryMethod != "in_person"`** → 발송 증빙 없음 ② `life_activity == false` + 계좌 사용이 '주 거래'가 아님 → 생계 흔적 없음 ③ 대화 내역 없음(`source_type == "chat"` 카드 부재) → 거래 합의 증빙 없음 |
| **직거래 예외 (2026-08-25 신설)** | **`deliveryMethod == "in_person"`이면 규칙 ①을 적용하지 않는다.** 직거래는 송장이 원래 없어서, 그대로 두면 사용자에게 **채울 방법이 없는 공백**을 띄우고 준비도를 깎는다 |

| 수용 기준 | 송장을 빼고 업로드 → 발송 증빙 공백 표시. **단 직거래를 고른 사용자에게는 표시되지 않음** |
| 발표 활용 | **데모에서 자료를 빼고 눌러 공백이 나타나는 장면을 보여준다** |

## F6 · 제출 준비도 점검

> **원칙: 이 그룹은 확인 완료 여부, 필수 증빙 누락, 자료 간 충돌만을 결정적 규칙으로 점검한다. LLM을 사용하지 않는다.** 금융당국이 안내한 간소화 조건을 전체 이의제기 승인·기각 기준으로 사용하지 않으며, 지급정지 해제 가능성과 은행 심사 결과를 예측하지 않는다.

| 점검 대상 | F7-03 체크리스트의 사유별 필수 항목 |

### F6-04 제출 준비도 산출

| 항목 | 내용 |
| --- | --- |
| 설명 | 확인 완료 여부·필수 증빙 누락·자료 간 충돌을 종합해 세 상태 중 하나를 산출한다 |

```jsx
if (hasUnconfirmedFields || hasMissingRequiredEvidence) {
  return SUPPLEMENT_NEEDED;
}
if (hasConflicts || hasUnknownBankCriteria) {
  return BANK_CHECK_REQUIRED;
}
return SUBMISSION_READY;
```

| 값 | 화면 문구 | 화면 처리 |
| --- | --- | --- |
| SUBMISSION_READY | 제출 준비 완료 | 확인된 자료 요약 + 금융회사 판단 안내 |
| SUPPLEMENT_NEEDED | 증빙 보완 필요 | 누락 자료와 보완 방법 강조 |
| BANK_CHECK_REQUIRED | 은행 확인 필요 | 충돌 내용 표시 + 간소화·일반심사 여부는 금융회사 확인 안내 |

> **세 상태 모두 화면 하단에 "최종 판단은 은행이 합니다"를 병기한다.**
> **금지 문구:** "기각될 수 있습니다" / "해제 가능성이 높습니다" / "그래도 해볼 만합니다" 등 결과 예측·낙관·위로 표현 일체.
> `hasUnknownBankCriteria`에는 과거 지급정지 이력 있음이 포함된다.

### F6-05 업무처리 기간 안내

| 항목 | 내용 |
| --- | --- |
| 설명 | 판정에 따라 예상 소요를 표시한다 |
| 산출 | **상태별 예측값을 만들지 않는다.** 세 상태 모두에 동일한 고정 안내를 표시한다 |
| 근거 | 금감원 2026.5.3 — 기본 5영업일, 보완 +5영업일, 재보완 +3영업일 |
| 표기 | "예상"임을 명시. 보장 표현 금지 |
| 고정 문구 | "이의제기신청서와 소명자료를 충분히 구비하여 제출한 경우 금융회사는 5영업일 내 **심사 결과를 통보**합니다. 자료 보완이 필요한 경우 처리기간이 추가될 수 있습니다.<br>**심사 결과 통보와 지급정지 해제는 다릅니다.** 통신사기피해환급법 제8조 제2항에 따라, 피해자에게 통보한 날부터 2개월이 지나기 전에는 지급정지를 종료할 수 없습니다. **5영업일 내 해제를 뜻하지 않습니다.**" |
| 전달 경로 | 이 문구는 **백엔드가 `/api/readiness`의 `notices`로 내려주고**, 프론트는 순화 없이 그대로 노출한다 (2026-08-25 확정) |

> **"심사 결과 통보"와 "지급정지 해제"를 반드시 분리해 쓴다** (2026-08-25 정정). 종전 문구는 "5영업일 내 해제를 보장하지 않는다"까지만 적어, **왜 5영업일이 지나도 안 풀리는지**를 설명하지 못했습니다. 법 제8조 제2항의 2개월 제한이 별도로 작동한다는 사실이 빠지면 사용자는 "심사가 끝났는데 왜 계좌가 그대로냐"에서 서비스를 불신하게 됩니다.
>
> **화면 카피에도 같은 원칙이 적용됩니다** — "은행이 5영업일 안에 판단할 수 있게 정리해요" 같은 문구는 금지입니다. 숫자가 약속처럼 읽히고, 서비스가 5영업일을 주는 것처럼 읽힙니다. 상세: `../01-product/reason-type-rules.md` §4-1.

## F7 · 소명서 생성

### F7-01 소명서 초안 생성

| 항목 | 내용 |
| --- | --- |
| 설명 | 타임라인과 판정 결과로 은행 제출용 사실 진술서를 생성한다 |
| 입력 | 타임라인 이벤트 + 사유 + 3요건 결과 |
| 처리 | LLM 호출 (프롬프트 제약: 타임라인에 없는 사실 금지, 법률 주장 금지, 감정 호소 금지) |
| 출력 | 제목 / 메타정보 / 본문 3~5문단 / 서명란 |
| 수용 기준 | 3문단 이상. 모든 날짜·금액이 타임라인과 일치 |

### F7-02 사실 일치 검증

| 항목 | 내용 |
| --- | --- |
| 설명 | 생성된 문장에 타임라인에 없는 사실이 들어갔는지 검증한다 |
| 처리 | ① 소명서를 문장 단위로 분리 ② 각 문장을 근거와 매칭 (근거 유형: evidence / intake / user_text) ③ 어느 근거와도 매칭되지 않는 문장 자동 삭제 ④ 원본에 없는 결론적 서술("배송 완료", "정상 판매", "피해자와 무관하다") 생성 차단 ⑤ intake·user_text 근거 문장에 "본인 진술" 표기 ⑥ 1회 재생성 ⑦ 재실패 시 해당 문단 생략 |
| 수용 기준 | **타임라인에 없는 "9월 4일 수령 확인" 같은 문장이 최종본에 없음** |
| 개발 주의 | 재생성은 1회로 제한. 무한 루프 방지 |
| **재실행 경로 (2026-08-25 신설)** | `POST /api/draft/revise`로 문장 `text`가 바뀌면 **그 문장만 재검증**한다. `excluded: true`는 재검증하지 않는다 — 문장을 빼는 것은 새 사실을 만들지 않고, 남은 문장은 이미 검증을 통과했기 때문이다 |

> **③의 "자동 삭제"는 LLM 출력에만 적용됩니다** (2026-08-25 확정). 사용자가 직접 고친 문장이 근거와 매칭되지 않으면 **삭제하지 않고 `user_text`로 유지**하고 경고만 띄웁니다. 사람이 자기 사실을 적은 문장에 LLM용 규칙을 쓰면 성격이 달라지고, ⑤가 이미 `user_text`에 "본인 진술" 표기를 규정하고 있으므로 살리는 쪽이 그 규정을 따르는 것입니다. 근거: `prd.md` FR-045 ③, `../02-architecture/api-contract.md` `/api/draft/revise` 절.

### F7-03 첨부 서류 체크리스트

| 항목 | 내용 |

| 항목 | 처리 |
| --- | --- |

| 사유 | 표준 소명자료 |
| --- | --- |

거래 상대방과의 대화·연락 기록 / 해당 입금 건의 계좌 거래내역 / 상대–송금인 일치 여부 확인 자료 / (대여 관계라면) 차용증·이체 기록 등

**"필수"로 표시하지 않는다.** 근거 문서가 없는 항목이다.

**④ 보강 자료 (전 유형 공통 · 선택)**

재직증명서 · 소득금액증명원 · 예금거래내역서 등 본인의 신원·경제력을 보이는 자료. 서비스에 업로드받지 않고 직접 첨부 안내만 한다. **법령·금감원 근거가 없으므로 "이걸 내면 통과된다"는 표현을 쓰지 않는다.**

| 항목 | 내용 |
| --- | --- |
| 미보유 표시 | **`whenMissing`으로 결정한다** (2026-08-25 정정 — 층이 아니라 이 필드다). `notice`인 항목에만 "미보유 — 보완 요청 사유가 될 수 있어요", `silent`은 **배지 자체를 렌더하지 않는다**, `blocks`만 주의색 |
| **화면 전용** | **이 문구는 화면에만 나가고 PDF에 포함되지 않는다.** 부족자료 체크리스트를 제출본에서 뺀 것과 같은 이유 (F8-01) |
| 시각 처리 | **미보유에 붉은색을 쓰지 않는다.** `blocks`만 주의색, 나머지 미보유는 중립색. 채울 수 없는 항목까지 경고로 칠하면 서비스가 사용자를 탓하는 화면이 된다. `needs_explanation`·`unknown`도 중립색 |
| 자가 진술 | `fulfillBy: "self"` 항목은 서비스가 보유 여부를 알 수 없어 **항목마다 "챙겼어요" 체크박스**를 둔다. **라벨은 고정하고 체크 표시로 상태를 드러낸다** — 누를 때마다 글자가 바뀌면 그 글자가 *지금 상태*인지 *누르면 될 일*인지 알 수 없다. `blocks`인 항목에는 **"이 항목을 표시해야 제출 준비 완료가 돼요"** 를 함께 띄운다 |
| 세금계산서 | **필수 아님.** ②의 택일 선택지 중 하나로만 노출하며, 모든 사용자에게 필수로 노출하지 않는다 |
| 근거 | ① 시행령 제7조 / ② 금감원 2026.5 업무처리 표준화 / ③·④ 근거 없음(참고) |
| **개발 주의** | **②를 관문으로 만들지 않는다.** 개인 중고거래자는 사업자등록증이 없어 물품 거래 표준을 채울 수 없지만, 법정 요건인 ①의 "증명하는 자료"는 자유 형식이라 이의제기 자체가 막히지 않는다 |

### F7-06 제출 패키지 구성 (2026-08-25 개정)

| 항목 | 내용 |
| --- | --- |
| 설명 | 은행에 그대로 낼 수 있는 형태로 산출물을 묶는다 |
| 구성 | ⓪ **제출 서류 목록 표지** ① **시행령 별지 제4호서식 이의제기신청서 작성 지원본** ② 사실관계 진술서(F7-01) ③ 시간순 거래 타임라인(F5-01) ④ 증빙자료 목록(**올린 자료의 목차**) ⑤ 증빙별 원본 이미지 |
| **제외** | **부족한 자료 체크리스트는 제출본에 넣지 않는다** (F8-01 참조). 화면에는 그대로 있다 |
| **분담** | **⓪~④ = 서버 PDF 생성(F8-01, 담당 `A`) / ⑤ = 브라우저가 자기 blob으로 이미지 페이지 생성(담당 `C`)** |
| 병합 | 클라이언트에서 `pdf-lib`으로 서버 PDF + 이미지 페이지를 병합해 단일 PDF 다운로드 |
| 서식 입력 | ①에 필요한 별지 제4호서식 **11개 필드**(신청인 성명·생년월일·주소·연락처·**휴대전화번호·전자우편주소** / 계좌 금융회사·개설점포·예금종별·계좌번호·**명의인**)는 **사용자가 직접 입력**하며 `POST /api/package/text` 요청 바디로 전달한다. **11개 모두 선택이며 빈 값이면 해당 칸을 공란으로 둔 PDF가 나온다** — 사용자가 계좌번호를 모른다는 이유로 패키지 생성이 막혀서는 안 된다. **폼에 필수 표시(`*`)를 붙이지 않는다** |
| 명의인 필드 | 법 제7조 제1항의 이의제기 주체가 **명의인**이라 신청인과 다른 경우가 예외적이다. 프론트는 **"신청인과 동일" 체크박스를 기본 체크**로 두고 `applicant.name`을 그대로 실어 보낸다. 체크박스 상태는 계약에 넣지 않는다 |
| **미저장** | 위 11개 값은 **PDF 생성에만 사용하고 세션·DB·로그 어디에도 남기지 않는다** (PRD §4.4, `../03-infra-ops/privacy-and-safety.md`). 요청 바디를 로깅하지 않도록 주의 |
| 폴백 | 병합 실패 시 텍스트 PDF 다운로드 + 원본 이미지 개별 저장 안내 |
| 제외 | **세금계산서는 필수 항목이 아니다.** 사업자의 보조 증빙으로만 취급하며, 중고거래 이용자는 채팅·입금내역·배송자료만으로 패키지를 완성할 수 있어야 한다. **신분증 사본은 패키지에 포함하지 않는다.** 민감도가 높아 서비스에 업로드받지 않으며, 제출 단계에서 직접 첨부하도록 안내 |
| 접수 경로 표기 | 시행령상 이의제기는 **해당 계좌를 관리하는 금융회사**에 신청서와 객관적 자료를 제출하는 절차다. 금융감독원 민원을 같은 수준의 제출 방법으로 표시하지 않는다 |
| 수용 기준 | **⓪~⑤가 포함된 단일 PDF**가 다운로드됨. 중고거래 시나리오(TC-13)에서 완성 확인 |
| 연관 | F7-01, F7-03, F8-01, F5-01, **F7-07** |

### F7-07 따로 챙길 것 안내 (2026-08-25 신설)

| 항목 | 내용 |
| --- | --- |
| 설명 | 서비스가 만들어주지 않는 것을 사용자가 챙기도록 안내한다 |
| 위치 | **내보내기 버튼 바로 위**, 별도 블록 |
| 내용 | ① **신청서 자필 서명** — 출력해서 직접 서명한 뒤 제출. 이메일·팩스로 낼 때는 **서명한 종이를 다시 찍거나 스캔** ② **명의인 신분증 사본** — 여기에 올리지 않음, 은행에 낼 때 직접 첨부 |

| 재확인 | 내보내기를 누르는 순간에도 같은 취지의 안내를 한 번 더 띄운다 |
| **금지** | **경고색을 쓰지 않는다.** 사용자가 뭘 잘못한 게 아니라 절차 안내다 |
| 배경 | 전자서명이 범위 밖이라 서명란이 공란으로 나간다. 모르고 파일만 보내면 반려될 수 있고, 인터넷은행은 이메일·팩스 접수라 재스캔 단계가 빠지면 서명한 종이를 어떻게 보내는지 모르게 된다 |
| 근거 | 시행령 제7조 — 별지 제4호서식 + 증명자료 + 신분증 사본을 사기이용계좌 관리 금융회사에 제출 |

### F7-08 다운로드 전 미리보기·수정 (2026-08-25 신설 · S04-2)

| 항목 | 내용 |
| --- | --- |
| 설명 | 내려받기 전에 산출물을 보여주고, 틀린 문장을 사용자가 고칠 수 있게 한다 |
| **왜 필요한가** | 소명서 문장은 대부분 **LLM이 생성한 값**이다. **"있는 사실을 틀리게 쓴 문장"**("발송했습니다"↔"수령했습니다")은 근거와 매칭되므로 **F7-02가 잡지 못한다.** 읽기 전용만 두면 사용자는 발견만 하고 고치지 못한 채 다운로드한다 |
| 흐름 | `S04 → [제출 패키지 내보내기] → S04-1 서식 입력 → S04-2 미리보기 → 다운로드` |
| 보기 2종 | **① 정리해서 보기**(기본) — 면별 내용을 HTML로. 문장 빼기·되돌리기가 즉시 반영된다<br>**② 실제 문서** — **내려받을 파일 그대로** pdf.js로 렌더. 폰트 깨짐·레이아웃 사고를 받기 전에 본다 |
| 편집 범위 | 1면 서식 필드(자유 입력) / **2면 문장 수정·제외** / 3·4면 **편집 불가** |
| 편집 경로 | `POST /api/draft/revise` (수정·제외), `excludedSentenceIds` (다운로드 시 제외 반영) |
| 3면 막다른 길 방지 | 3면 옆에 **"값이 다르면 자료 확인으로 돌아가 고칠 수 있어요" 안내 + Stage 2 복귀 링크**. 편집을 막아놓고 대안을 안 주면 사용자는 틀린 채로 다운로드한다 |
| **미리보기와 다운로드는 같은 함수를 쓴다** | 따로 만들면 보여준 것과 받는 것이 갈린다 |
| 개발 주의 | **`<iframe src={blobUrl}>`을 쓰지 않는다** — iOS 사파리에서 blob PDF 렌더가 불안정하다(빈 화면·다운로드 튐). NFR-05가 360px 모바일을 요구한다. pdf.js는 지연 로딩해 첫 화면 번들을 늘리지 않는다 |
| **표기 시점** | **"사용자 확인 완료" 표기는 미리보기를 거친 뒤에만 붙인다.** 초안 생성 직후 붙이면 사용자는 아무것도 확인하지 않은 상태다 — 이 서비스가 "낙관적으로 순화하지 않는다"를 내세우는 이상 우리 화면의 표기부터 사실이어야 한다 |
| 수용 기준 | 문장을 제외하고 다운로드하면 **2면에서 그 문장이 빠진다.** 수정한 문장의 배지가 "본인 진술"로 바뀐다 |

> **폰트 깨짐은 미리보기가 구조적으로 못 잡습니다.** HTML 미리보기는 브라우저 폰트로 그리므로 화면에서는 멀쩡한데 받은 PDF만 깨집니다. "실제 문서" 보기가 이걸 잡지만, 사용자가 건너뛰고 바로 내려받을 수 있으므로 **9/6 최종 점검에 "생성된 PDF를 실제로 열어 한글이 정상 렌더되는지 확인"을 명시 항목으로 둡니다**(`../05-planning/roadmap.md`). 팀이 리허설에서 잡을 문제이지 사용자가 잡을 문제가 아닙니다.

#### 부족자료 체크리스트를 제출본에서 뺀 이유 (2026-08-25 확정)

미보유 항목 중에는 **사용자가 애초에 채울 수 없는 것**이 섞여 있습니다 — 개인 중고거래자의 사업자등록증, 차용증 없는 대여의 차용증. 화면에서는 이것들을 `whenMissing: "silent"`로 두어 **표시조차 하지 않기로** 했는데(F7-03), 같은 목록이 PDF가 되면 **화면에서 감춘 항목이 제출본에서 되살아납니다.** "이 사람은 사업자등록증도 차용증도 없다"는 문장을 사용자가 스스로 정리해 은행에 건네는 셈입니다.

**부족자료 체크리스트는 화면에 그대로 둡니다** — 사용자가 무엇을 더 준비할지 보는 용도입니다. `spec.md` F7-03의 **"미보유 — 보완 요청 사유가 될 수 있습니다"** 문구는 **화면 전용**이며 PDF에 나가지 않습니다.

#### 면별 항목·정렬 기준 (2026-08-25 신설)

**같은 면을 두 사람이 각자 그립니다** — PDF는 백엔드, 미리보기(S04-2)는 프론트. 기준이 없으면 사용자가 미리 본 것과 실제로 받는 것이 어긋납니다. **PDF가 단일 출처이고, 프론트는 이 표를 따릅니다.**

| 면 | 항목 | 정렬 |
| --- | --- | --- |
| **표지** | "이 문서에 포함된 것" 1~5 목록 / "신청인이 따로 첨부하는 것"(명의인 신분증 사본, 1면 서명란 자필 서명) | 고정 |
| **1면** | 별지 제4호서식 11필드 (아래 재현 규칙) | 서식 순서 고정 |
| **2면** | 사실관계 진술서 본문. `excludedSentenceIds`의 문장은 제외 | 문장 생성 순서 |
| **3면** | 일시 · 행위 주체 · 요약 · 금액 | `occurred_at` 오름차순, 동시각은 F5-01 tie-break |
| **4면** | 순번 · 자료 유형(`source_type` 한글 라벨) · 확인된 일시 · 한 줄 요약 | **5면 이미지 페이지 순서와 일치** |

**금지 3가지**

- **3면에 `gaps`(증거 공백)를 표시하지 않는다.** 부족자료 체크리스트를 뺀 것과 같은 이유 — "못 갖춘 것"을 제출본에 적지 않는다. 공백은 화면에만 표시한다
- **4면에 파일명을 넣지 않는다.** 사용자 파일명에 개인정보가 섞일 수 있다(`카톡_김철수_20260901.png`)
- **4면에 보유/미보유를 표시하지 않는다.** 4면은 **올린 자료의 목차**이지 필요 서류 체크리스트가 아니다 — 뒤에 붙는 5면 원본 이미지와 짝을 이룬다 (`prd.md` §4.4가 "타임라인 + 증빙목록 + 원본이미지"를 한 묶음으로 둔 구조)

#### 1면 재현 규칙 (2026-08-25 신설)

| 항목 | 규칙 |
| --- | --- |
| 레이아웃 | **원본 서식의 표 구조를 유지**한다 (`00-context/법정서식-별지제4호서식-이의제기신청서.pdf`) |
| 접수번호 · 접수일자 | **공란 + 음영.** 금융회사가 채우는 칸이다 |
| 수신처 | `○○○ 금융회사 귀하`의 `○○○` 자리에 **`account.bank` 값**을 넣는다. 값이 없으면 원본대로 공란 |
| 작성일자 | **서버 생성 시각**(다운로드 시점)의 날짜 |
| 서명란 | **공란으로 둔다.** 전자서명은 범위 밖이며, 사용자가 출력해 자필 서명한다 |
| 빈 필드 | 11필드 중 값이 없는 것은 **공란**으로 두고 오류를 내지 않는다 (작성 지원본) |

> **프론트는 1면을 HTML로 재현하지 않습니다.** 같은 법정 서식을 두 곳에서 구현하면 한쪽만 고쳤을 때 조용히 어긋납니다. 미리보기 1면에는 **"별지 제4호서식 그대로 생성돼요" 안내 + 입력한 11필드 값 요약**만 보여주고, 서식 렌더는 서버 PDF에 맡깁니다. 사용자가 확인해야 할 것은 **자기가 입력한 값이 맞는지**이지 표 선의 위치가 아닙니다.

| 문구 ① 보존 | **"가진 자료를 지우지 마세요"** — 정리가 끝날 때까지 대화방을 나가거나 메시지를 지우지 마세요. 남은 기록이 그대로 소명 근거가 돼요 |
| 문구 ② 복구 | **"이미 지웠다면 여기를 찾아보세요"** — 메신저(대화 백업 기능) / 중고거래 앱(앱 안의 거래 내역) / 문자(통신사 문자 보관함) / 은행 앱(입출금 내역은 언제든 다시 캡처 가능) |
| **F5-04와 다르다** | F5-04(대체 증빙 제안)는 **판독이 끝난 뒤** "이 자료가 없으니 저걸 대신 내라"고 제안한다. **복구는 그보다 앞, 자료를 모으는 시점**에 필요하다 — 판독 후에 "대화 백업을 찾아보세요"라고 하면 이미 업로드를 마친 사용자가 처음으로 돌아가야 한다. 둘은 겹치지 않는다 |
| **금지** | **메신저·앱 이름과 메뉴 경로를 특정하지 않는다.** ("설정 → 채팅 → 대화 백업" 식) 앱이 업데이트될 때마다 틀린 안내가 된다 |
| 연관 | F3-07(사유별 업로드 안내)과 같은 화면에 온다 |

## 5-2. 휘발성 데이터 (인메모리 세션)

| 항목 | 타입 | TTL |
| --- | --- | --- |
| 문진 응답 | `Map<String,String>` | 30분 |
| 추출 이벤트 | `List<ExtractedEvent>` | 30분 |
| 신호 플래그 | `Signals` | 30분 |
| 준비도 결과 | `Readiness` | 30분 |
| 소명서 텍스트 | `String` | 30분 |
| 카드 확인 상태 | `Map<String,Boolean>` | 30분 |
| **직접 첨부 자가 진술** | `Map<String,Boolean>` (`itemId` → 보유 여부) | 30분 |
| 문장-근거 참조 | `List<SentenceEvidence>` (imageIndex, bbox) | 30분 |
| 품질 플래그 | `Map<String,QualityFlags>` | 30분 |

> **원본 이미지는 이 표에 없다.** 서버 세션은 이미지 바이트를 보관하지 않으며, 근거 참조는 이미지의 **순번과 영역 좌표**만 담는다.

> **별지 제4호서식 11개 필드(신청인 성명·생년월일·주소·연락처·휴대전화번호·전자우편주소 / 계좌 금융회사·개설점포·예금종별·계좌번호·명의인)도 이 표에 없다.** `POST /api/package/text` 요청 바디로 받아 **PDF 생성에만 쓰고 세션에 넣지 않으며 로그에도 남기지 않는다** (PRD §4.4 "서비스 미저장", `../03-infra-ops/privacy-and-safety.md`).

> **`excludedSentenceIds`도 세션에 담지 않는다.** 다운로드 시점에 한 번 전달되고 끝이다.

## 5-3. 원본 이미지 (서버 미보관)

| 항목 | 위치 | 수명 |
| --- | --- | --- |
| 업로드 이미지 | **브라우저 메모리 (blob)** | 탭 종료 또는 세션 종료 시 revoke |
| 서버 측 사본 | **없음** | LLM 호출 시 메모리 통과, 응답 후 즉시 참조 해제 |

> **A안 설계 근거:** 원본이 서버에 존재하지 않으므로 유출·보관 리스크 자체가 없다. 대가로 브라우저 새로고침 시 원본이 소실되며, 이때는 재업로드가 필요하다 (F1-02).

# 7. 보안 · 개인정보 처리

## 7-1. 처리 흐름

```
[동의]    외부 LLM API 전송 · 학습 미사용 · 서버 미저장 고지 후 동의
              ↓
[리사이즈] 브라우저에서 장변 1600px 축소 (F3-01)
              ↓
[마스킹]  브라우저에서 사용자가 가릴 영역 지정 (F3-06)
              ↓
[보관]    마스킹된 blob을 브라우저 메모리에 유지  ← 원본의 유일한 소재지
              ↓
[전송]    Spring Boot (메모리) → LLM API 호출
              ↓
[해제]    응답 수신 즉시 서버 메모리에서 이미지 참조 해제
              ↓
[세션]    추출 JSON + 근거 참조만 보관  ← 서버단 2차 마스킹 (F4-03)
              ↓
        사용자 카드 확인 (F4-06) → 소명서 생성 (F7-01)
              ↓
[패키지]  서버 텍스트 PDF + 브라우저 이미지 페이지 병합 (F7-06)
              ↓
[종료]  서버 세션 삭제 + 브라우저 blob revoke → 익명 통계만 적재
```

## 7-2. 원칙

| 원칙 | 구현 |
| --- | --- |
| 회원가입 없음 | 익명 세션 해시만 사용 |
| 무저장 | 이미지·대화 내용·소명서를 DB·Storage·디스크에 저장하지 않음 |
| 최소 수집 | 판정에 필요한 문항 외 수집 없음 |
| 즉시 폐기 | 서버는 원본을 보관하지 않는다. LLM 호출 후 메모리 참조 즉시 해제, 세션 30분 TTL |
| 로그 제한 | 개인정보 미포함 로그만 (F11-04) |
| AI 처리 고지 | 동의 화면에 외부 LLM API 전송 사실·보관 기간·학습 이용 여부 명시 |
| 원본 소재 | **원본 이미지는 사용자 브라우저 메모리에만 존재한다.** 서버는 LLM 호출 시 메모리로 통과시킬 뿐 보관하지 않는다 |

## 7-3. 악용 방지

| 위험 | 대응 |
| --- | --- |
| 실제 범죄자의 악용 | ① 자료를 **정리**만 하고 생성하지 않음 (F7-02) ② 허위 진술 시 형사 책임 고지 ③ 금감원도 AI 위·변조 대비 추가 자료 요청 절차 마련 |
| 증거 조작 | 사실 검증으로 타임라인에 없는 내용 차단 |
| 프롬프트 인젝션 | 업로드 콘텐츠를 데이터로만 취급, 고정 JSON 스키마 출력(F4-01) |
| 외부 AI 개인정보 처리 | 사전 고지·동의, 전송 전 사용자 마스킹(F3-06), 비학습·최소 보관 설정, 서버 미저장(A안) |
