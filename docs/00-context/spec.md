# 3. 기능별 상세 명세

## F1 · 공통 · 세션 관리

### F1-01 세션 생성

| 항목 | 내용 |
| --- | --- |
| 설명 | 진입 시 익명 세션을 발급한다. 회원가입·로그인 없음 |
| 트리거 | `[시작하기]` 클릭 또는 최초 페이지 로드 |
| 입력 | 없음 |
| 처리 | ① 16자 랜덤 해시 생성 (SecureRandom) ② 인메모리 세션 저장소에 등록 ③ TTL 30분 설정 ④ 응답 본문으로 해시 반환 — 이후 클라이언트가 **커스텀 헤더 `X-Session-Hash`** 로 전달 (2026-08-23 확정, 쿠키 미사용) |
| 출력 | `{sessionHash, expiresAt, demoMode}` |
| 예외 | 세션 저장소 포화 시 가장 오래된 만료 세션 강제 정리 |
| 수용 기준 | 해시가 매번 다르고 사용자 식별 정보를 포함하지 않음 |
| 연관 | F1-02, F1-03 |

### F1-02 세션 상태 유지

| 항목 | 내용 |
| --- | --- |
| 설명 | 문진 응답·타임라인·판정·소명서를 세션에 보관하고 단계 이동 시 복원한다 |
| 처리 | 인메모리 `Map<String, Session>`. DB 미저장 |
| 보관 항목 | 문진 6문항, 추출 이벤트 리스트, 신호 플래그, 판정 결과, 소명서 텍스트 |
| 예외 | 세션 만료 후 API 호출 시 `410 Gone` + 재시작 안내 |
| 수용 기준 | 5단계 왕복 이동 시 입력값 전부 유지 |
| 개발 주의 | **Render 무료 티어는 파일시스템이 휘발성이다. 세션을 디스크에 쓰지 않는다** |
| 개발 주의 2 | **원본 이미지는 서버 세션에 없다.** 새로고침 시 추출 결과·소명서는 살아 있으나 원본만 사라진다. 이 상태를 감지해 "원본이 필요합니다. 다시 올려주세요" 안내를 띄운다 |

### F1-03 세션 만료·파기

| 항목 | 내용 |
| --- | --- |
| 설명 | 30분 무활동 또는 완료 시 세션 데이터를 즉시 삭제한다 |
| 트리거 | ① 30분 무활동 ② `DELETE /api/session` ③ 5단계 완료 |
| 처리 | 세션 객체 제거 + 클라이언트에 blob revoke 신호 전달 (Storage 미사용) |
| 수용 기준 | 파기 후 동일 해시로 조회 시 데이터 없음 |
| 연관 | F11-02 (파기 전 익명 통계만 적재) |

### F1-04 단계 이동 제어

| 항목 | 내용 |
| --- | --- |
| 설명 | 하단 인디케이터로 완료한 단계에 자유롭게 이동한다 |
| 규칙 | 미완료 단계로는 건너뛰기 불가. 완료 단계로는 자유 이동 |
| 무효화 | S01 복귀 후 문항 변경 → S03 이후 전부 초기화 (F2-03) |
| 수용 기준 | **발표 시연 중 특정 단계로 즉시 점프 가능** |

### F1-05 진행 상태 요약

| 항목 | 내용 |
| --- | --- |
| 설명 | 완료한 단계를 시각적으로 요약해 보여준다 (PRD FR-053 대응) |
| 처리 | 클라이언트 상태 기반. 서버 왕복 불필요 |
| 우선순위 | P2 — 없어도 5단계 완주 가능 |
| 수용 기준 | 완료 단계마다 체크 표시 |

| **화면 구성** | 6문항을 **3문항씩 2개 서브스텝**으로 나눠 제시한다. 1쪽 = ①②③(기한 계산 입력), 2쪽 = ④⑤⑥(거래 맥락). 문항 번호는 쪽이 나뉘어도 ①~⑥을 유지한다 |
| 서브스텝 표기 | 단계 인디케이터(F1-04)의 5단계는 그대로 두고, 서브스텝은 S01 화면 안에서만 표시한다. 상단 인디케이터를 6칸으로 늘리지 않는다 |
| 뒤로 가기 | 2쪽에서 뒤로 가면 S00이 아니라 1쪽으로 간다. 서브스텝을 먼저 소진한 뒤 이전 단계로 나간다 |
| 처리 | 입력 즉시 `POST /api/intake` 증분 저장. 쪽 분할은 화면 표현이며 계약(6필드 단일 요청)에 영향을 주지 않는다 |
| 수용 기준 | **현재 쪽의 3문항**이 모두 입력 또는 "확인 불가" 선택되면 다음 버튼 활성화 |

**문항별 선택지 및 용도**

| 문항 | 선택지 | 용도 |
| --- | --- | --- |
| 지급정지일 | 날짜 직접 선택 (모르면 "확인 불가") | **기한 계산 (FR-014)** |
| 채권소멸절차 개시 공고 | 통지받음(공고일 입력) / 아직 없음 / 모름 | **기한 계산 (FR-014)** |
| 문제 입금액 | 금액 직접 입력 (모르면 "확인 불가") | **소명서 사실 기재 전용** |
| 거래 성격 | 중고 물건 판매 / 용역·알바 대가 / 빌려준 돈 회수 / 잘 모르겠음 | **거래 유형 분류 (F6-01)** |
| 과거 이력 | 없음 / 있음 | **은행 확인 필요 분기 (F6-04)** |
| 계좌 사용 목적 | 주 거래 계좌다 / 가끔 쓴다 / 거의 안 쓴다 | **생계 흔적 증빙 점검 보조 (F5-03)** |

> **입금액은 사실 정보로만 기록한다.** 소액 여부는 서비스가 판정하지 않으며, 간소화 절차 적용 여부는 금융회사 확인 사항으로 안내한다. (F6-03 금지 조항)

## F3 · 증거 수집

### F3-01 이미지 다중 업로드

| 항목 | 내용 |
| --- | --- |
| 설명 | 드래그앤드롭 또는 파일 선택으로 최대 10장을 한 번에 올린다 |
| 입력 | `multipart/form-data`, JPG/PNG — **전송 포맷은 PNG**. 텍스트가 많은 캡처라 JPEG 링잉이 판독(F4-01)에 불리하다 |
| 제한 | 파일당 10MB, 총 10장 |
| 처리 | ① 클라이언트에서 장변 1600px 리사이즈 ② 마스킹 적용 (F3-06) ③ 결과 blob을 브라우저 메모리 배열에 보관 ④ multipart로 서버 전송 (**Storage 미사용**) |
| 전송 방식 | **이미지 1장당 1요청, 동시 4개까지**(2026-08-24 확정, `../02-architecture/api-contract.md`). 10장이면 4 → 4 → 2로 끊어 보낸다 |
| 개발 주의 | **Supabase Storage를 사용하지 않는다.** 서버는 이미지를 메모리로만 받아 LLM에 전달하고 즉시 참조를 해제한다 |
| **개발 주의** | 처리 ①(1600px 리사이즈)을 빠뜨리면 전송 해상도가 **사용자 화면 크기와 DPR에 좌우된다.** 데스크톱 1x에서 세로 캡처가 199×431까지 줄어 계좌번호·시각·금액을 사람도 못 읽는 사례가 실제로 있었다(2026-08-24 수정). F4-01 판독 정확도가 낮으면 여기부터 확인할 것 |
| **개발 주의** | 리사이즈 적용 후 장당 300KB~1MB가 된다. **Spring Boot 기본 `spring.servlet.multipart.max-file-size`는 1MB**라 그대로 두면 정상 이미지가 `400`으로 떨어진다 — 10MB로 올릴 것 |
| 수용 기준 | 4장 동시 업로드 시 전부 처리 |

| 항목 | 내용 |

### F4-06 추출 결과 사용자 확인 카드

| 항목 | 내용 |
| --- | --- |
| 설명 | AI가 읽어낸 내용을 사건 카드로 보여주고 사용자가 맞는지 확인·수정한다 |
| 필요성 | **AI가 "70만 원"을 "10만 원"으로 읽거나 날짜를 잘못 읽을 수 있다.** 확인 없이 소명서를 만들면 잘못된 서류가 은행에 제출된다 |
| 카드 항목 | 날짜 / 금액 / 상대방 / 거래 내용 / 배송 여부 / 원본 화면 썸네일 |
| 처리 | ① 이벤트별 카드 생성 ② 각 항목 인라인 수정 가능 ③ `[맞습니다]` 클릭 시 confirmed=true ④ 카드 삭제 가능 |
| 게이팅 | **날짜 또는 금액이 low 신뢰도인 카드가 미확인 상태면 S03 진입 차단.** 그 외 미확인 카드는 진행 허용하되 "확인하지 않은 자료 n건은 문서에 포함되지 않습니다" 경고 |
| 소명서 반영 | **confirmed=true 카드만 F7-01 입력으로 전달한다** |
| 수용 기준 | 미확인 카드의 날짜·금액이 소명서 본문에 나타나지 않음 |
| 연관 | F7-01, F7-02, F7-05 |
| 표시 | 필드별 신뢰도 배지(높음 / 확인 필요) + 원본 위치 하이라이트 + 사용자 수정 시 "사용자 수정" 배지 |
| 미상처리 | 확인 불가한 값은 임의로 채우지 않고 **미상**으로 유지 |

### F4-07 증빙 품질 검사

| 항목 | 내용 |
| --- | --- |
| 설명 | 읽는 것을 넘어 "이 자료로는 부족하다"를 알려준다 |
| 검사 항목 | ① 이미지가 흐려 금액 판독 불가 ② 채팅 상대방 이름 잘림 ③ 거래 날짜 미표시 ④ 택배 송장번호 가려짐 ⑤ 대화 앞뒤 맥락 부족 ⑥ 거래금액이 자료마다 다름 |
| 처리 | LLM이 quality_flags 산출 → 서버에서 자료 간 금액 교차 대조 → 문제 유형별 안내 문구 매핑 |
| 안내 문구 예 | "화면 상단의 날짜가 보이도록 다시 캡처해 주세요" / "대화 상대 이름이 잘렸습니다. 대화방 상단까지 포함해 캡처해 주세요" |

| 우선순위 | P1 — 컷될 경우 quality_flags 산출까지만 유지하고 안내 문구는 고정 문구 1종으로 대체 |
| 수용 기준 | 흐린 이미지 업로드 시 재캡처 안내 노출 |

## F5 · 타임라인 재구성

### F5-01 시간순 정렬

| 항목 | 내용 |
| --- | --- |
| 설명 | 모든 이미지에서 추출한 이벤트를 하나의 시간축에 배열한다 |
| 처리 | `occurred_at` 오름차순. 동시각은 `source_type` 우선순위로 (chat → bank → shipping) |
| 추가 | 사용자가 입력한 지급정지일만 이벤트로 삽입하며, **사용자 진술 / 낮은 신뢰도**로 표시한다 |
| 수용 기준 | 이벤트 5건 이상 시 시각 순서 보장 |
| 금지 | **문진 응답에서 날짜를 역산해 생성하지 않는다.** 없는 사실을 만드는 행위에 해당 |

### F5-02 중복 이벤트 병합

| 항목 | 내용 |
| --- | --- |
| 설명 | 같은 사건이 여러 캡처에 걸쳐 나올 때 하나로 합친다 |
| 판단 | 시각 차 5분 이내 + 금액 일치 + `actor` 동일 |
| 처리 | **자동 확정하지 않는다.** 병합 후보로 사용자에게 제시하고 승인받은 경우에만 병합한다. 출처는 둘 다 기록 |
| 후보 전달 | `GET /api/timeline` 응답의 `mergeCandidates: [{ groupId, eventIds, reason }]`. `reason`은 사용자에게 그대로 보여줄 수 있는 문장이어야 한다 — 왜 같은 사건으로 보이는지 설명 없이 승인받지 않는다 |
| 승인 | `POST /api/timeline/merge` — `{ mergeGroupIds, approved }`, 응답은 갱신된 타임라인 전체 (2026-08-24 확정, `../02-architecture/api-contract.md`) |
| 거절 | `approved: false`면 후보를 거절로 기록하고 이후 `mergeCandidates`에서 제외한다. 이벤트는 그대로 둔다 |
| **스코프 컷 시** | 백엔드는 `mergeCandidates`를 **항상 빈 배열로** 내리고 승인 엔드포인트를 구현하지 않는다. 프론트는 빈 배열이면 후보 UI를 렌더하지 않는다 — **양쪽이 서로를 기다리지 않고 같이 컷된다.** 컷 결정이 나면 `../response/frontend/`에 회신한다 |

### F5-03 증거 공백 탐지

| 항목 | 내용 |
| --- | --- |
| 설명 | 소명에 필요한데 없는 자료를 지목한다 |
| 탐지 규칙 | ① `delivery_evidence == false` + 사유가 재화 거래 → 발송 증빙 없음 ② `life_activity == false` + 계좌 사용이 '주 거래'가 아님 → 생계 흔적 없음 ③ 대화 내역 없음 → 거래 합의 증빙 없음 |

| 수용 기준 | 송장을 빼고 업로드 → 발송 증빙 공백 표시 |
| 발표 활용 | **데모에서 자료를 빼고 눌러 공백이 나타나는 장면을 보여준다** |

## F6 · 제출 준비도 점검

> **원칙: 이 그룹은 확인 완료 여부, 필수 증빙 누락, 자료 간 충돌만을 결정적 규칙으로 점검한다. LLM을 사용하지 않는다.** 금융당국이 안내한 간소화 조건을 전체 이의제기 승인·기각 기준으로 사용하지 않으며, 지급정지 해제 가능성과 은행 심사 결과를 예측하지 않는다.

### F6-01 거래 유형 분류 및 사용자 확인

| 항목 | 내용 |
| --- | --- |
| 설명 | 거래 성격을 이의제기 사유로 매핑한다 |
| 매핑 | 중고 물건 판매 → 재화 거래 대금 / 용역·알바 대가 → 용역 제공 대가 / 빌려준 돈 회수 → 채권 회수 / 잘 모르겠음 → 사유 미확정 |
| 영향 | 사유가 F7-03 첨부 서류 목록을 결정한다 |
| 수용 기준 | 4개 유형 중 하나로 확정되거나 F6-02로 분기 |

### F6-02 미확정 사실 확인 질문

| 항목 | 내용 |
| --- | --- |
| 설명 | 사유가 불명확하면 조용히 오분류하지 않고 1회 되묻는다 |
| 트리거 | 거래 성격 = '잘 모르겠음' |
| 질문 | "돌려받은 돈이 맞나요?" + 4개 선택지 |
| 처리 | 응답에 따라 사유 확정. '잘 모르겠습니다' → 사유 미확정으로 진행 |
| 횟수 | **1회만.** 반복 질문 금지 |
| 근거 페르소나 | P-05 장수연 (차용증 없는 채권 회수) |

### F6-03 증빙 충족·누락 점검

| 항목 | 내용 |
| --- | --- |
| 설명 | 확인 완료된 사건만으로 사유별 필수 증빙의 상태를 점검한다 |
| 입력 | confirmation_status == user_confirmed 또는 user_corrected 인 사건만 |
| 점검 대상 | F7-03 체크리스트의 사유별 필수 항목 |
| 출력 | 항목별 충족 / 보완 필요 / 확인 필요 |
| **금지** | **입금액으로 소액 여부를 판정하지 않는다.** 금액은 사실 정보로만 기록 |
| 수용 기준 | 미확인 사건은 충족 근거로 사용되지 않음 |

### F6-04 제출 준비도 산출

| 항목 | 내용 |
| --- | --- |
| 설명 | 확인 완료 여부·필수 증빙 누락·자료 간 충돌을 종합해 세 상태 중 하나를 산출한다 |

```jsx
if (hasUnconfirmedFields || hasMissingRequiredEvidence) {
  return SUPPLEMENT_NEEDED;
}
if (hasConflicts || hasUnknownBankCriteria) {
  return BANK_CHECK_REQUIRED;
}
return SUBMISSION_READY;
```

| 값 | 화면 문구 | 화면 처리 |
| --- | --- | --- |
| SUBMISSION_READY | 제출 준비 완료 | 확인된 자료 요약 + 금융회사 판단 안내 |
| SUPPLEMENT_NEEDED | 증빙 보완 필요 | 누락 자료와 보완 방법 강조 |
| BANK_CHECK_REQUIRED | 은행 확인 필요 | 충돌 내용 표시 + 간소화·일반심사 여부는 금융회사 확인 안내 |

> **세 상태 모두 화면 하단에 "최종 판단은 은행이 합니다"를 병기한다.**
> **금지 문구:** "기각될 수 있습니다" / "해제 가능성이 높습니다" / "그래도 해볼 만합니다" 등 결과 예측·낙관·위로 표현 일체.
> `hasUnknownBankCriteria`에는 과거 지급정지 이력 있음이 포함된다.

### F6-05 업무처리 기간 안내

| 항목 | 내용 |
| --- | --- |
| 설명 | 판정에 따라 예상 소요를 표시한다 |
| 산출 | **상태별 예측값을 만들지 않는다.** 세 상태 모두에 동일한 고정 안내를 표시한다 |
| 근거 | 금감원 2026.5.3 — 기본 5영업일, 보완 +5영업일, 재보완 +3영업일 |
| 표기 | "예상"임을 명시. 보장 표현 금지 |
| 고정 문구 | "이의제기신청서와 소명자료를 충분히 구비하여 제출한 경우 금융회사는 5영업일 내 심사결과를 통보합니다. 자료 보완이 필요한 경우 처리기간이 추가될 수 있으며, 5영업일 내 지급정지 해제를 보장하는 것은 아닙니다." |

| 처리 | **검증된 고정 문구 템플릿만 사용한다. LLM 다듬기를 사용하지 않는다** (문구 변형으로 인한 오안내 방지) |

| 서버 반환 | `sentences: [{ sentenceId, text, evidenceRefs: [{ type, imageIndex, bbox }] }]` — **이미지 파일이 아니라 참조만 반환한다** |
| 클라이언트 처리 | `imageIndex`로 자기 메모리의 blob 배열에서 해당 이미지를 찾아 표시. `bbox`가 있으면 해당 영역으로 스크롤 |
| 표시 | 문장 아래 근거 배지 (예: "거래내역 2번 · 카카오톡 4번") |
| 상호작용 | 문장 클릭 → 원본 이미지 모달이 열리고 해당 위치로 이동 |
| 우선순위 | P0 — 단 bbox 정밀 하이라이트는 P1로 분리. **P0 범위는 이미지 열기 + 스크롤 이동까지** |
| 예외 | 원본이 메모리에 없으면(새로고침 등) 배지를 회색 처리하고 "원본을 다시 올리면 확인할 수 있습니다" 표시 |
| 수용 기준 | 모든 사실 서술 문장에 근거 배지가 표시되고, 클릭 시 해당 원본이 열림 |
| 연관 | F7-02, F4-06, F1-02 |

### F7-06 제출 패키지 구성 (6종)

| 항목 | 내용 |
| --- | --- |
| 설명 | 은행에 그대로 낼 수 있는 형태로 산출물을 묶는다 |
| 구성 | ① **시행령 별지 제4호서식 이의제기신청서 작성 지원본** ② 사실관계 진술서(F7-01) ③ 시간순 거래 타임라인(F5-01) ④ 증빙자료 목록 ⑤ 증빙별 원본 이미지 ⑥ 부족한 자료 체크리스트(F7-03) |
| **분담** | **①~④,⑥ = 서버 PDF 생성(F8-01, 담당 `A`) / ⑤ = 브라우저가 자기 blob으로 이미지 페이지 생성(담당 `C`)** — 2026-08-24 프론트 회신으로 확정 |
| 병합 | 클라이언트에서 `pdf-lib`으로 서버 PDF + 이미지 페이지를 병합해 단일 PDF 다운로드 |
| 서식 입력 | ①에 필요한 별지 제4호서식 8개 필드(신청인 성명·생년월일·주소·연락처 / 계좌 금융회사·개설점포·예금종별·계좌번호)는 **사용자가 직접 입력**하며 `POST /api/package/text` 요청 바디로 전달한다. **8개 모두 선택이며 빈 값이면 해당 칸을 공란으로 둔 PDF가 나온다** — 사용자가 계좌번호를 모른다는 이유로 패키지 생성이 막혀서는 안 된다. 공란 항목은 ⑥ 부족자료 체크리스트에 "직접 채워야 하는 항목"으로 표시한다 |
| **미저장** | 위 8개 값은 **PDF 생성에만 사용하고 세션·DB·로그 어디에도 남기지 않는다** (PRD §4.4, `../03-infra-ops/privacy-and-safety.md`). 요청 바디를 로깅하지 않도록 주의 |
| 폴백 | 병합 실패 시 텍스트 PDF 다운로드 + 원본 이미지 개별 저장 안내 |
| 제외 | **세금계산서는 필수 항목이 아니다.** 사업자의 보조 증빙으로만 취급하며, 중고거래 이용자는 채팅·입금내역·배송자료만으로 6종을 완성할 수 있어야 한다. **신분증 사본은 패키지에 포함하지 않는다.** 민감도가 높아 서비스에 업로드받지 않으며, 제출 단계에서 직접 첨부하도록 안내 |
| 접수 경로 표기 | 시행령상 이의제기는 **해당 계좌를 관리하는 금융회사**에 신청서와 객관적 자료를 제출하는 절차다. 금융감독원 민원을 같은 수준의 제출 방법으로 표시하지 않는다 |
| 수용 기준 | 6종이 모두 포함된 단일 PDF가 다운로드됨. 중고거래 시나리오(TC-13)에서 완성 확인 |
| 연관 | F7-01, F7-03, F8-01, F5-01 |
| 근거 | 시행령 제7조 — 별지 제4호서식 + 증명자료 + 신분증 사본을 사기이용계좌 관리 금융회사에 제출 |

## 5-2. 휘발성 데이터 (인메모리 세션)

| 항목 | 타입 | TTL |
| --- | --- | --- |
| 문진 응답 | `Map<String,String>` | 30분 |
| 추출 이벤트 | `List<ExtractedEvent>` | 30분 |
| 신호 플래그 | `Signals` | 30분 |
| 준비도 결과 | `Readiness` | 30분 |
| 소명서 텍스트 | `String` | 30분 |
| 카드 확인 상태 | `Map<String,Boolean>` | 30분 |
| 문장-근거 참조 | `List<SentenceEvidence>` (imageIndex, bbox) | 30분 |
| 품질 플래그 | `Map<String,QualityFlags>` | 30분 |

> **원본 이미지는 이 표에 없다.** 서버 세션은 이미지 바이트를 보관하지 않으며, 근거 참조는 이미지의 **순번과 영역 좌표**만 담는다.

> **별지 제4호서식 8개 필드(신청인 성명·생년월일·주소·연락처 / 계좌 금융회사·개설점포·예금종별·계좌번호)도 이 표에 없다.** `POST /api/package/text` 요청 바디로 받아 **PDF 생성에만 쓰고 세션에 넣지 않으며 로그에도 남기지 않는다** (PRD §4.4 "서비스 미저장", `../03-infra-ops/privacy-and-safety.md`).

## 5-3. 원본 이미지 (서버 미보관)

| 항목 | 위치 | 수명 |
| --- | --- | --- |
| 업로드 이미지 | **브라우저 메모리 (blob)** | 탭 종료 또는 세션 종료 시 revoke |
| 서버 측 사본 | **없음** | LLM 호출 시 메모리 통과, 응답 후 즉시 참조 해제 |
| Supabase Storage | **사용하지 않음** | — |

> **A안 설계 근거:** 원본이 서버에 존재하지 않으므로 유출·보관 리스크 자체가 없다. 대가로 브라우저 새로고침 시 원본이 소실되며, 이때는 재업로드가 필요하다 (F1-02).

# 7. 보안 · 개인정보 처리

## 7-1. 처리 흐름

```
[동의]    외부 LLM API 전송 · 학습 미사용 · 서버 미저장 고지 후 동의
              ↓
[리사이즈] 브라우저에서 장변 1600px 축소 (F3-01)
              ↓
[마스킹]  브라우저에서 사용자가 가릴 영역 지정 (F3-06)
              ↓
[보관]    마스킹된 blob을 브라우저 메모리에 유지  ← 원본의 유일한 소재지
              ↓
[전송]    Spring Boot (메모리) → LLM API 호출
              ↓
[해제]    응답 수신 즉시 서버 메모리에서 이미지 참조 해제
              ↓
[세션]    추출 JSON + 근거 참조만 보관  ← 서버단 2차 마스킹 (F4-03)
              ↓
        사용자 카드 확인 (F4-06) → 소명서 생성 (F7-01)
              ↓
[패키지]  서버 텍스트 PDF + 브라우저 이미지 페이지 병합 (F7-06)
              ↓
[종료]  서버 세션 삭제 + 브라우저 blob revoke → 익명 통계만 적재
```

## 7-2. 원칙

| 원칙 | 구현 |
| --- | --- |
| 회원가입 없음 | 익명 세션 해시만 사용 |
| 무저장 | 이미지·대화 내용·소명서를 DB·Storage·디스크에 저장하지 않음 |
| 최소 수집 | 판정에 필요한 문항 외 수집 없음 |
| 즉시 폐기 | 서버는 원본을 보관하지 않는다. LLM 호출 후 메모리 참조 즉시 해제, 세션 30분 TTL |
| 로그 제한 | 개인정보 미포함 로그만 (F11-04) |
| AI 처리 고지 | 동의 화면에 외부 LLM API 전송 사실·보관 기간·학습 이용 여부 명시 |
| 원본 소재 | **원본 이미지는 사용자 브라우저 메모리에만 존재한다.** 서버는 LLM 호출 시 메모리로 통과시킬 뿐 보관하지 않는다 |

## 7-3. 악용 방지

| 위험 | 대응 |
| --- | --- |
| 실제 범죄자의 악용 | ① 자료를 **정리**만 하고 생성하지 않음 (F7-02) ② 허위 진술 시 형사 책임 고지 ③ 금감원도 AI 위·변조 대비 추가 자료 요청 절차 마련 |
| 증거 조작 | 사실 검증으로 타임라인에 없는 내용 차단 |
| 프롬프트 인젝션 | 업로드 콘텐츠를 데이터로만 취급, 고정 JSON 스키마 출력(F4-01) |
| 외부 AI 개인정보 처리 | 사전 고지·동의, 전송 전 사용자 마스킹(F3-06), 비학습·최소 보관 설정, 서버 미저장(A안) |
