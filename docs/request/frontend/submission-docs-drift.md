# A. 치명 — 제출 전 반드시 고쳐야 합니다

## A-1. 제출본이 약속한 출력값이, 코드에서는 하드코딩된 **금지어**입니다

**기능명세서 현재 문구**

> 주요 기능 목록: 「**소명 판정** | … **지급정지 해제 가능성을 판정한다**. 해제가 어려운 경우에도 사실대로 안내한다 | 소명 판정 화면 | 완료」
>
> 이용 흐름: 「판정 화면에서 3요건(소액·이력·생계) 대조 결과와 **도장(일부 해제 가능 / 추가 소명 필요 / 기각 가능)** 을 확인」

**실제 (확인)**

기능명은 **제출 준비도 점검**이고 산출값은 **제출 준비 완료 / 증빙 보완 필요 / 은행 확인 필요** 입니다 (`ReadinessResponse.java:16-18`, `frontend/src/lib/readiness.ts:38-44`).

제출본이 약속한 세 문자열(`일부 해제 가능` / `추가 소명 필요` / `기각 가능`)을 저장소 전체에서 grep하면 **일치하는 곳은 금지어 목록 두 곳뿐입니다**:

- `NoticeTexts.java:39-43` — `BANNED_PHRASES`에 "기각될 수 있습니다", "해제 가능성이 높습니다" 등재. 회귀 테스트로 강제 (`ReadinessServiceImplTest.java:219-221`)
- `ai-server/app/services/factcheck.py:15-40` — `FORBIDDEN_PHRASES`에 "기각", "해제 가능", "가능성이 높" 포함. **해당 표현이 든 LLM 문장은 소명서에서 자동 삭제됩니다**

**도장 자체는 실재합니다** — 틀린 건 도장의 존재가 아니라 **그 안의 글자**입니다. 실제 값은 `완료 / 보완 / 확인` 입니다 (`ReadinessStage.tsx:29-33`, 제가 직접 확인). 같은 화면의 부제가 이미 **"승인 여부는 점치지 않아요"** 입니다 (`ReadinessStage.tsx:40`).

**제안 문구**

> 제출 준비도 점검 | 확인 완료 여부·필수 증빙 누락·자료 간 충돌을 결정적 규칙으로 점검해 **제출 준비 완료 / 증빙 보완 필요 / 은행 확인 필요** 중 하나를 산출한다. **승인·기각을 예측하지 않으며, 세 상태 모두에 "최종 판단은 은행이 합니다"를 병기한다** | 준비도 화면 | 완료

> ㅡ 준비도 화면에서 세 항목(**자료 확인 · 필수 증빙 · 은행 확인 사항**) 대조 결과와 도장(**완료 / 보완 / 확인**), 그리고 "최종 판단은 은행이 합니다" 안내를 확인

MVP 구현 범위의 「소명 판정」도 **「제출 준비도 점검」** 으로 바꿔 주세요.

## A-2. 검증 시나리오대로 하면 **약속한 화면이 나오지 않습니다**

**기능명세서 현재 문구**

> 「샘플 입력값 및 예상 결과 ㅡ 입금액 "**50만원 미만**" + 거래성격 "중고 물건 판매" + 과거이력을 "있음"으로 변경하면 → "**기각 가능**" 판정으로 즉시 전환」

**실제 (확인)** — 세 가지가 모두 틀립니다.

1. **"50만원 미만" 같은 구간 선택지가 없습니다.** 금액을 직접 입력합니다 (`frontend/src/data.ts:42` `input: "amount"`, `IntakeRequest.java:12` `Long amount`)
2. **입금액은 준비도 산출에 아예 쓰이지 않습니다.** `ReadinessServiceImpl.java:33-45`의 입력 4개에 `amount`가 없습니다. 문진 화면에도 그렇게 적혀 있습니다 — `data.ts:46` **"금액으로 준비도를 판정하지 않아요"**
3. **과거 이력 "있음"의 실제 결과는 `BANK_CHECK_REQUIRED`(은행 확인 필요)** 입니다 (`ReadinessServiceImpl.java:36,41-42`). 이 케이스는 TC-04로 테스트되며 **수용 기준이 "기각 단정 없음"** 입니다 (`test-cases-and-demo.md:34`)

**심사위원이 제출본대로 재현하면 "기각 가능" 화면은 나오지 않습니다.**

**제안** — 교정된 절차를 팀이 이미 `../../04-testing/test-cases-and-demo.md:70-82`에 **"기능명세서 제출본 기준 검증 절차"** 로 써 두었습니다. 그대로 옮기시면 됩니다. 예상 결과만 옮겨 적으면:

> ㅡ 샘플 입력값 및 예상 결과: 입금액 "**450,000원**" + 거래성격 "중고 물건 판매" + 과거이력을 "**있어요**"로 변경하면 → "**은행 확인 필요**" 상태로 즉시 전환. **입금액은 준비도 산출에 쓰이지 않으므로 상태를 바꾸는 값은 과거 이력 하나다**

## A-3. 대표 차별성 "3요건을 그대로 구현한 규칙엔진"이 사실이 아닙니다

**기획서 §4 차별성 ② / 기능명세서 「판정 자체는 … 심사 기준을 그대로 구현해」**

**실제 (확인 — 제가 직접 열어봤습니다)** — `ReadinessServiceImpl.java:33-45`가 읽는 입력은 넷뿐입니다.

```java
boolean hasUnconfirmedFields       = evidenceService.hasAnyPendingCard(session);
boolean hasMissingRequiredEvidence = hasBlockingGap(checklist);
boolean hasConflicts               = hasAmountMismatch(session);
boolean hasUnknownBankCriteria     = "true".equals(session.getIntake().get("history"));
```

- **소액** — 판정하지 않습니다. `SMALL_AMOUNT_NOTICE`는 55행에서 **조건 없이 그대로 넘기는 상수 안내문**이고, `NoticeTexts.java:20-22`에 "소액 여부를 서비스가 판정하지 않는다"고 적혀 있습니다
- **생계** — 준비도에 영향이 없습니다. `ChecklistCatalog.java:31-32`에서 `life_activity`는 `whenMissing: "silent"`(누락해도 등급 불변)입니다
- **이력**만 쓰이고, 그것도 "요건 충족"이 아니라 "은행 기준 미상 → 은행 확인 필요" 분기입니다

그리고 이건 **의도된 설계**입니다 — `../../00-context/prd.md:164-166`이 "이 표의 '일부 지급정지 요건'은 … **전체 이의신청의 승인·기각 기준과 동일하지 않다**", "**이 표는 … 준비도 산출 로직의 근거가 아니다**"라고 명시적으로 분리해 뒀습니다. 소액 기준이 은행 내규라 비공개이기 때문입니다.

**제안 문구 (기획서 §4 차별성 ②)**

> ② 판정 로직이 임의 스코어링이 아니라 ① 사용자 확인 완료 여부 ② 사유별 필수 증빙 누락 ③ 자료 간 금액 충돌 ④ 은행 내규로 알 수 없는 항목 — 이 **네 가지만 보는 결정적 규칙엔진**. **공개되지 않은 소액 금액 기준을 서비스가 임의로 수치화하지 않는 것**이 설계 원칙

## A-4. 기획서가 자기 자신과 모순됩니다

§2는 "규칙 엔진이 **지급정지 해제 요건을 판정**", §4는 "**부적격으로 판정**되는 경우에도"라고 쓰는데, **§7 마지막 문단은 "이 서비스는 지급정지 해제 여부를 판정하지 않고"** 라고 정반대로 씁니다. 심사위원이 같은 문서 안에서 대조하면 바로 드러납니다. **§7이 맞고 §2·§4를 고쳐야 합니다.**

부적격 판정은 존재하지 않습니다 — 이력이 있으면 `BANK_CHECK_REQUIRED`로만 표시되고 고정 문구는 `NoticeTexts.java:25-26` "…은행 확인이 필요하며, **최종 판단은 은행이 합니다**"입니다.

> ③ 과거 지급정지 이력이 있는 경우에도 **기각을 단정하지 않고 "은행 확인 필요"로만 표시**한다. "그래도 해볼 만합니다" 같은 낙관·예측 문구는 다짐이 아니라 **코드의 금지어 목록으로 차단**되어 출력 자체가 불가능하다

# B. 실제보다 약하게 쓴 곳 — 심사 배점을 스스로 깎고 있습니다

## B-1. 소명서 안전장치를 "프롬프트 단"으로 축소 (AI 소관)

**현재**: 기획서 §5 "**프롬프트 단에서** … 금지하도록 강제", 기능명세서 "**AI 생성 규칙으로** 금지함"

**실제**: 프롬프트는 1차 방어일 뿐이고, **강제는 LLM을 전혀 호출하지 않는 결정적 검증기**가 합니다 (`ai-server/app/services/factcheck.py:1` — "LLM을 사용하지 않는 순수 함수만 둔다"). 실측이 `ai-server/evals/README.md:157`에 있습니다 — **위반 문장 차단 15/15 (100%), 근거 없는 문장 비율 0%**.

"프롬프트 단"이라고만 쓰면 확률적 방어로 읽힙니다. **이 프로젝트에서 가장 강한 심사 방어 논리를 문서가 스스로 지우고 있습니다.**

> ㅡ 프롬프트로 1차 금지하고, **LLM을 호출하지 않는 결정적 검증기**가 후처리에서 이를 다시 강제한다 — 문장마다 근거가 된 사실의 id를 붙이고, **근거와 대조되지 않는 날짜·시각·금액·반복 횟수가 든 문장과 결과 예측·법률 주장·감정 호소가 든 문장을 자동 삭제**한다. 적대적 문장 15종 주입 실측에서 **차단률 100%(15/15)**, 근거 없는 문장 비율 **0%**

## B-2. 사실 검증 대조 항목이 실제와 다름 (AI 소관)

**현재**: "모든 날짜·금액·**식별자**를 … 후처리 대조"

**실제** (`factcheck.py:194-245`): 날짜 · **시각** · 금액 · **반복 횟수("N회")** + 금지 표현 40여 종. **식별자(운송장·계좌 뒷 4자리)는 대조 대상이 아니며 애초에 소명서 본문에 실리지 않습니다.** "제거 후 재생성"은 맞습니다 — 백엔드가 1회 재호출합니다 (`DraftServiceImpl.java:52-58`).

## B-3. 개인정보 방어가 3중인데 1중으로 서술, 주소 누락

**현재**: "전화번호·계좌번호 전체·주민번호는 추출 단계에서 **마스킹**"

**실제**: 세 겹이고, 어느 겹도 "마스킹"이 아닙니다.

1. **브라우저 전송 전** — 사용자가 직접 가린 이미지만 전송 (`frontend/src/lib/mask.ts:81-117`, "the unmasked original never leaves this function"). 텍스트 경로는 브라우저가 정규식 자동 마스킹 (`textEntry.ts:28-51`)
2. **미추출** — LLM이 애초에 추출하지 않음 (`ai-server/app/llm/prompts.py:17`). **주소가 빠져 있습니다** — 명세에 있던 항목이라 8/25에 프롬프트에 반영했습니다
3. **후처리 제거** — 부분 가림이 아니라 **전체 치환·삭제** (`pii.py:14` `REDACTED = "[가려짐]"`). `김O수` 식 부분 마스킹은 동성·동돌림자 오탐 때문에 **명시적으로 기각**됐습니다 (`privacy-and-safety.md:69-74`)

그리고 **의도적 예외가 빠졌습니다** — **거래 상대방·입금자 표시명은 일부러 가리지 않습니다.** 금감원 표준의 "구매자–송금인 일치 확인"에 필요하기 때문이고, 마스킹 UI가 사용자에게 직접 안내합니다 (`MaskingSheet.tsx:205-208` "거래 상대방·입금자 이름은 가리지 마세요"). **심사에서 설계 깊이를 보여주는 항목이라 빠진 게 아깝습니다.**

또 "이미지 원본은 추출 완료 후 **즉시 삭제**"는 실제보다 약합니다. **저장된 적이 없습니다** — 멀티파트 파서의 디스크 스풀링을 구조적으로 배제하려고 raw body로 전달하고 (`internal-api-contract.md:97-99`), base64 인코딩 직후 원본 참조를 지웁니다 (`extraction.py:212-219` `del data`). "삭제"는 한 번 저장했다는 뜻으로 읽힙니다.

## B-4. 타임라인 재구성 주체가 뒤집혀 있습니다
