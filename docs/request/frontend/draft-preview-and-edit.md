## 1. 배경 — 지금 계약에 구멍이 있습니다

소명서 본문은 대부분 **LLM이 생성한 문장**입니다. 그런데 LLM의 오류는 두 가지인데, **지금 하나만 막고 있습니다.**

| 오류 유형 | 예시 | 현재 대응 |
| --- | --- | --- |
| 없는 사실을 **지어냄** | 타임라인에 없는 "9월 4일 수령 확인" | ✅ F7-02가 근거 미매칭 문장을 자동 삭제 |
| 있는 사실을 **틀리게 씀** | 카드는 맞는데 "물품을 발송했습니다"를 "수령했습니다"로 뒤집음 | ❌ **막지 못합니다** |

F4-06(카드 확인)은 **필드 단위**(날짜·금액·`actor`)를 확인시키므로, 문장 표현 단계에서 생긴 오류는 걸러지지 않습니다. 근거와 매칭은 되는데 서술이 틀린 문장이 그대로 PDF에 들어갑니다.

**이건 은행에 제출되는 문서입니다.** 틀린 서술이 들어가면 보완 요청이 오거나, 최악의 경우 사용자가 하지 않은 진술을 한 것이 됩니다.

### 지금 구조가 이미 이 단계를 전제하고 있습니다

- `spec.md` **F8-01**은 PDF 각 면 하단에 **"AI 초안 · 사용자 확인 완료 {시각} · 최종 판단은 금융회사"** 를 찍습니다. **확인 단계가 없으면 이 표기가 사실이 아닙니다.**
- `prd.md` **FR-045 ②**의 근거 유형에 **`user_text`(사용자가 직접 입력한 서술)** 가 이미 정의돼 있습니다.
- **FR-045 ⑤**는 `intake` 또는 `user_text`가 근거인 문장에 **"본인 진술" 표기**를 붙이도록 이미 규정합니다.

즉 **사용자가 문장을 고치는 것은 FR-045 위반이 아니라 FR-045가 이미 정의해 둔 경로**입니다. 다만 그 경로를 열어주는 화면과 엔드포인트가 없을 뿐입니다.

## 2. 제안 — 미리보기는 HTML, 검증과 PDF는 서버

```
[미리보기]  프론트가 HTML로 렌더        ← PDF 아님
     ↓
[수정]      사용자가 값·문장 수정
     ↓
[검증]      POST /api/draft/revise      ← 서버가 F7-02 재실행
     ↓
[다운로드]  POST /api/package/text      ← 서버 PDF 생성 → pdf-lib 병합
```

**미리보기 단계에 PDF가 필요 없습니다.** 프론트는 이미 렌더에 필요한 데이터를 전부 갖고 있습니다.

| 미리보기 면 | 데이터 출처 |
| --- | --- |
| 1면 별지 제4호서식 | 프론트의 서식 폼 값 (필드 수는 `legal-form-and-package.md` 회신에 따름) |
| 2면 사실관계 진술서 | `POST /api/draft` 응답의 `draftText` / `sentences` |
| 3면 타임라인 | `GET /api/timeline` 응답의 `events` |
| 4면 증빙목록 | `POST /api/draft` 응답의 `checklist` |
| 5면 부족자료 체크리스트 | `POST /api/readiness` 응답의 `missingItems` |

### PDF 생성 주체는 그대로 백엔드입니다 (변경 없음)

미리보기·수정을 넣어도 **F7-06 분담은 바뀌지 않습니다.** 오히려 서버 생성이어야 하는 이유가 하나 늘었습니다 — **수정본도 F7-02 검증을 거쳐야 하는데, 프론트가 PDF를 만들면 검증을 우회하는 경로가 생깁니다.**

프론트가 새로 만드는 건 **미리보기 화면과 편집 UI**이지 PDF 생성이 아닙니다.

## 3. 신설할 계약 (회신 후 확정)

### `POST /api/draft/revise` — 수정 문장 검증

**Request**

```json
{
  "sentences": [
    { "sentenceId": "s1", "text": "2026년 9월 2일 물품대금 700,000원을 입금받았습니다." }
  ]
}
```

- 고친 문장만 보내도 되고 전체를 보내도 됩니다 (백엔드는 `sentenceId` 기준으로 덮어씁니다).
- 문장 **삭제**는 `text`를 빈 문자열로 보내는 대신 별도 필드를 쓸지 회신에서 정해주세요 (§4 회신 항목 3).

**Response**

```json
{
  "sentences": [
    {
      "sentenceId": "s1",
      "text": "...",
      "sourceType": "evidence | intake | user_text",
      "evidenceRefs": [ { "type": "evidence", "imageIndex": 2, "bbox": {} } ],
      "warning": null
    }
  ]
}
```

- `sourceType`이 `intake` 또는 `user_text`면 프론트는 문장에 **"본인 진술" 배지**를 붙입니다 (FR-045 ⑤).
- `warning`은 근거와 매칭되지 않을 때 채워집니다 (§4 회신 항목 1).

수정 결과는 세션에 반영되므로, 이후 `POST /api/package/text`는 **수정본으로 PDF를 만듭니다.**

## 4. 회신이 필요한 항목

### 4-1. 근거와 매칭되지 않는 수정 문장을 어떻게 할까요 (가장 중요)

사용자가 고친 문장이 어떤 근거와도 매칭되지 않을 때입니다.

| 안 | 동작 | 문제 |
| --- | --- | --- |
| A. 자동 삭제 (FR-045 ③ 그대로) | 문장을 지움 | **사용자가 방금 쓴 게 사라집니다.** 왜 사라졌는지 모르면 서비스를 불신하게 됩니다 |
| **B. 경고 + `user_text` 표기 후 유지 (백엔드 추천)** | 문장을 남기되 "이 문장은 올리신 자료에서 확인되지 않습니다. 본인 진술로 표기됩니다" 경고 + **"본인 진술" 배지** | 사용자가 경고를 무시할 수 있음 |

**백엔드는 B를 추천합니다.** 근거:
- FR-045 ⑤가 이미 `user_text` 근거 문장에 "본인 진술" 표기를 붙이도록 규정합니다 — B는 그 규정을 그대로 따르는 것이고, A는 사용자 입력을 `user_text`로 인정하지 않는 셈이라 오히려 FR-045와 어긋납니다.
- 허위 기재 책임 고지 화면이 이미 프론트에 있습니다(`privacy-and-safety.md` 체크리스트).
- **자동 삭제는 LLM 출력에 적용하는 규칙**입니다. 사람이 자기 사실을 적은 문장에 같은 규칙을 쓰면 성격이 다릅니다.

A/B 중 어느 쪽인지, 아니면 다른 안이 있는지 알려주세요.

### 4-2. 수정 범위를 어디까지 열까요

| 대상 | 백엔드 의견 |
| --- | --- |
| 서식 8필드 (1면) | **자유 입력** — 이미 그렇게 확정됨 |
| 소명서 본문 문장 (2면) | **문장 단위 편집 + 문장 제외** |
| 타임라인 (3면) | **편집 불가.** 값을 고치려면 Stage 2 카드 확인(`/api/evidence/confirm`)으로 돌아가는 게 맞습니다 — 타임라인만 고치면 소명서·증빙목록과 어긋납니다 |
| 증빙목록·부족자료 (4·5면) | **편집 불가.** 규칙 엔진 산출물이라 사람이 고치면 준비도와 불일치합니다 |

3·4·5면까지 편집을 원하시면 회신에 적어주세요 — 다만 위 이유로 백엔드는 반대합니다.

### 4-3. 문장 삭제를 어떻게 표현할까요

`text: ""`로 보낼지, `deleted: true` 필드를 둘지, 아니면 삭제를 아예 막고 "제외" 토글만 둘지. 프론트 UI 형태에 맞는 쪽으로 정해주세요.

### 4-4. 미리보기 화면을 어디에 둘까요

백엔드 제안은 **S04-2**(S04에서 `[제출 패키지 내보내기]` → 서식 입력 S04-1 → 미리보기 S04-2 → 다운로드)입니다. 화면 흐름은 프론트 판단이 우선이니 다르게 잡으셔도 됩니다. 정해지면 `spec.md` 화면 정의서에 반영하겠습니다.

### 4-5. 일정에 들어갈 수 있습니까

`roadmap.md` 기준 **8/29~8/31 "문서 생성"** 구간입니다. 프론트는 이 구간에 이미 서식 8필드 폼 + `pdf-lib` 병합 + 이미지 페이지 생성이 잡혀 있어, 미리보기·편집 UI까지 들어가면 부담이 큽니다.

**넣기 어려우면 그렇다고 회신해주세요.** 그 경우 백엔드는 아래로 축소 제안합니다.

- 미리보기는 **읽기 전용**으로만 (수정 없이 확인만)
- 틀린 내용을 발견하면 **Stage 2 카드 확인으로 돌아가 고치고 재생성**(F7-04, 이미 P1로 존재)
- `POST /api/draft/revise`는 만들지 않음

이 축소안도 "AI 초안 · 사용자 확인 완료" 표기를 사실로 만들기에는 충분합니다. **최소한 읽기 전용 미리보기는 넣어야 한다는 게 백엔드 의견입니다** — 지금은 사용자가 내용을 한 번도 못 본 채 PDF를 받습니다.

## 7. 참고 — 이 요청이 나온 경위

사용자(백엔드 담당)가 "PDF로 정리된 문장 대부분이 LLM 생성값인데, 실제와 다르게 작성된 부분이 있으면 다운로드 전에 이용자가 확인·수정하게 해주면 좋지 않겠나"라고 제기한 사안입니다. 검토 결과 **FR-045·F8-01이 이미 이 단계를 전제하고 있는데 화면과 엔드포인트만 없는 상태**로 확인되어 요청 문서로 올립니다.
