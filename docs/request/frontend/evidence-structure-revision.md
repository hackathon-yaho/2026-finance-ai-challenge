## 0. 왜 지금 이 요청을 보내나

`reason-type-rules.md`가 **"금감원 2026.5.3 기준 그대로 구현"** 이라고 선언하고 있는데, 실제 기준을 대조해보니 **우리 목록이 그 기준과 다릅니다.** 그리고 실제 피해 사례를 보니 **우리 규칙으로는 도와줄 수 없는 사용자**가 있습니다.

준비도 규칙 엔진을 아직 구현하지 않았으므로 **지금 고치면 비용이 거의 없습니다.** Phase 4에서 발견하면 다시 짜야 합니다.

> **근거의 한계를 먼저 밝힙니다.** 금감원 보도자료 **원문 PDF는 확보하지 못했습니다**(fss.or.kr 게시판이 스크립트 기반이라 접근 실패). 아래 목록은 **KB국민은행 공식 고객 안내**와 복수 매체가 **동일 문구**로 전한 내용을 근거로 합니다. KB 안내는 뉴스 요약이 아니라 은행이 자기 고객에게 하는 안내라 실무 적용의 방증입니다. 그래도 원문이 아니므로, **회신 시 이 점을 감안해 판단해주세요.**

## 1. 구매자–송금인 일치 여부 (가장 큼)

### 무엇이 빠졌나

금감원 물품 거래 공통 소명자료에 **"구매자와 송금인이 일치하는지 확인할 수 있는 자료"** 가 명시돼 있습니다. 그런데 우리 문서 어디에도 이 개념이 없습니다.

- `reason-type-rules.md` §1 사유유형 표 — 없음
- `reason-type-rules.md` §3 4대 신호 — 없음
- `spec.md` F7-03 서류 목록 — 없음
- 프론트 `data.ts`의 `CHECK_LABELS` — 없음
- `api-contract.md` 카드 스키마 — **이름을 담을 필드 자체가 없음** (`actor`는 `self`/`counterparty`/`system` 3값뿐)

### 왜 결정적인가

**통장협박·삼각사기의 판별 지점이 정확히 여기입니다.** 사기범이 피해자를 시켜 판매자 계좌로 송금하게 만들기 때문에 **대화 상대와 입금자 이름이 다릅니다.** 은행이 가장 먼저 보는 항목입니다.

실제 사례(서울경제 보도)에서도 구매자 B가 **전혀 모르는 제3자 C의 계좌에서** 송금하게 만든 구조였습니다.

### 좋은 소식 — 데이터는 이미 있습니다

대화 캡처에 상대 닉네임이 있고, 입금 내역 캡처에 입금자명이 있습니다. **판독한 두 값을 비교만 하면 됩니다.**

### 프론트에 필요한 것

1. **증거 카드에 이름 노출** — 지금 카드 항목은 `날짜 / 금액 / 상대방 / 거래 내용 / 배송 여부 / 썸네일`인데(F4-05), "상대방"이 대화 상대인지 입금자인지 구분되지 않습니다. **둘을 따로 보여줘야** 사용자가 확인·정정할 수 있습니다.
2. **불일치 시 안내 UI** — 불일치가 곧 문제는 아닙니다(삼각사기 피해자는 원래 불일치). **"이 차이를 소명서에 설명해야 한다"** 는 안내가 필요합니다.
3. **체크리스트 항목 추가**

> ⚠️ **불일치를 "위험 신호"로 표시하지 마세요.** 불일치는 오히려 **피해자임을 뒷받침하는 정황**일 수 있습니다. 서비스가 사용자를 의심하는 톤이 되면 안 됩니다.

**AI 담당에게도 별도 요청을 보냅니다** — 카드에 대화 상대명·입금자명을 담는 필드가 필요합니다.

## 2. 소명자료가 "한 덩어리"가 아니라 세 층입니다 (2026-08-25 전면 개정)

### 조사 결과 — 금감원 표준은 2유형뿐입니다

| 유형 | 금감원 표준 소명자료 |
| --- | --- |
| **물품 거래** | 사업자등록증 / 거래상대방 대화내역 / **계약서·세금계산서·거래명세서 중 택일** / 구매자–송금인 일치 여부 |
| **용역·급여** | **건강보험자격득실확인서·재직증명서 중 택일** / 급여 입금내역 |
| **채권 회수 · 기타/불명** | **표준 없음** (3회 검색해도 금감원 목록에 이 유형 자체가 없음) |

우리 `spec.md` F7-03은 4유형 모두에 목록을 두고 근거를 *"금감원 2026.5.3"* 으로 적어뒀는데, **뒤 두 유형은 사실과 다릅니다.** 근거 없이 우리가 만든 목록이었습니다.

### 그래서 성격을 세 층으로 나눴습니다

| 층 | 성격 | 근거 | 갖추지 못하면 |
| --- | --- | --- | --- |
| **① 법정 첨부서류** | **필수** | 시행령 제7조 (서식에 인쇄돼 있음) | 접수 요건 미충족 |
| **② 금감원 표준** | **기준선** (2유형만) | 금감원 2026.5 | 반려가 아니라, 은행이 추가 자료를 요구할 수 있음 |
| **③ 공통 최소 자료** | **참고 안내** (표준 없는 유형) | 없음 | 아무 일도 없어야 함 |
| **④ 보강 자료** | **선택 · 가점** | 실무 관행 | 불이익 없음 |

**②의 뉘앙스가 핵심입니다.** KB국민은행 안내가 *"…갖추면 **돼요**"* 입니다 — "이것만 있으면 충분하다"(부담 경감)이지 "이게 없으면 안 된다"가 아닙니다.

### ⚠️ 지금 구조가 만드는 실제 문제

프론트 `data.ts`를 보면 전부 AND입니다:

```ts
export const REQUIRED_EVIDENCE: Record<string, EvidenceId[]> = {
  "중고 물건 판매": ["chat", "bank", "shipping", "autopay"],
  ...
}
```

`lib/readiness.ts`가 `missing.length > 0`이면 곧바로 `SUPPLEMENT_NEEDED`를 냅니다. 결과적으로:

- **개인 중고거래자**는 사업자등록증이 없어서 물품 거래 표준을 못 채웁니다 → 영원히 "보완 필요"
- **차용증 없는 채권 회수**(P-05 페르소나)는 우리가 만든 "대여 사실 증빙"을 못 채웁니다 → 영원히 "보완 필요"

둘 다 **채울 방법이 없는 요구**입니다. 그런데 법정 요건인 ①의 "증명하는 자료"는 **자유 형식**이라 실제로는 이의제기가 막히지 않습니다. **우리 서비스만 막고 있는 셈입니다.**

### 프론트에 필요한 것

1. **OR 그룹 표현** — `EvidenceId[]` 평면 배열로는 택일을 표현할 수 없습니다. 자료구조 변경 필요 (예: `{ anyOf: [...] }`). 체크리스트 UI에 **"이 중 하나만 있으면 됩니다"** 표시
2. **층별 시각 구분** — ②만 "미보유 — 보완 요청 사유가 될 수 있습니다"를 붙이고, **③·④에는 붙이지 않습니다**
3. **③·④는 준비도를 깎지 않습니다** — 체크박스는 보여주되 미보유가 경고가 되면 안 됩니다

백엔드도 같은 구조로 `ReadinessService`를 짭니다. **자료구조 형태를 회신에서 정해주세요.**

> 단일 출처는 `../../01-product/reason-type-rules.md` §2로 정리했습니다. `spec.md` F7-03과 `phase-4-readiness.md`도 같은 구조로 이미 갱신했습니다.

## 3. 직거래(대면)에 증빙 경로가 없습니다

### 지금 무슨 일이 일어나나

`spec.md` F5-03 공백 탐지 규칙:

> ① `delivery_evidence == false` + 사유가 재화 거래 → **발송 증빙 없음**

그리고 `delivery` 판단 기준은 **"송장·발송 기록"**(F4-02)입니다.

**직거래는 송장이 원래 없습니다.** 지금 설계대로 구현하면 직거래 사용자에게 **영원히 "발송 증빙 없음" 공백을 띄우고 준비도를 깎습니다.** 사용자는 채울 방법이 없습니다.

F5-04 대체 증빙 제안도 *"택배사 조회 화면·수령 확인"* 이라 여전히 택배 전제입니다.

### 실제 사례

순금 팔찌 20돈(643만원)을 **직거래**로 판 A씨가 계좌 정지를 당하고, 증빙이 없어 *"거래 장소 인근의 CCTV라도 찾아다녀야 하는 상황"* 이 됐습니다.

**우리 서비스가 가장 도와야 할 사용자인데, 지금 규칙으로는 "보완 필요"만 띄웁니다.**

### 프론트에 필요한 것

거래 방식이 **택배인지 직거래인지 구분**해야 하고, 직거래면 다른 증빙을 물어야 합니다(물품 사진, 거래 장소·시각, 대면 인도 정황).

방법이 두 가지인데 **어느 쪽이 프론트에 나은지 회신에서 정해주세요.**

| 안 | 방법 | 영향 |
| --- | --- | --- |
| **A** | 문진에 거래 방식 문항 추가 (택배 / 직거래 / 해당 없음) | 문항이 6 → 7개. 서브스텝 구성 재조정 |
| **B** | 증거 유형에 "직거래 정황" 추가하고 문진은 그대로 | 문항 수 유지. 판정이 업로드 자료에 의존 |

백엔드는 **A**를 선호합니다 — 사유유형처럼 문진에서 확정되면 규칙이 결정적이 되고, 업로드 전에 "무엇을 준비해야 하는지" 안내할 수 있습니다. 다만 문진 UI를 방금 2서브스텝으로 재구성하신 직후라 부담이 클 수 있어 판단을 맡깁니다.

## 4. 플랫폼 거래 내역이 증거 유형에 없습니다

실무 안내가 **"중고 거래 플랫폼(당근마켓, 번개장터 등) 거래 내역"** 을 별도 자료로 듭니다. 대화 캡처와 다른 증거입니다 — **거래 성립 사실 + 물품 정보 + 상대 계정**이 한 화면에 있고, 플랫폼이 발행한 기록이라 신빙성이 다릅니다.

우리 증거 유형은 `chat / bank / shipping / autopay / threat` **5종 고정**이라, 플랫폼 거래 페이지를 올리면 `chat`으로 뭉뚱그려집니다.

**프론트에 필요한 것**: `EvidenceId`에 유형 추가 + 업로드 안내 문구.

## 5. 본인 신원·경제력 소명 트랙이 통째로 없습니다

### 근거

실무 자료와 후기에서 가장 반복되는 조언입니다.

> *"본인이 성실하게 경제생활(직업, 사업 등)을 하고 있고 예금이나 재산이 넉넉하여 굳이 이런 범죄를 저지르지 않아도 되는 사람이라는 점을 부각시킬 수 있는 증거자료를 첨부한다면 이의제기신청이 인용될 확률이 훨씬 높습니다."*

구체적으로 **재직증명서 · 소득금액증명원 · 예금거래내역서 · 건강보험자격득실확인서**입니다. 금감원 용역·급여 유형의 표준 서류와도 이어집니다.

### 우리는 이걸 "생계 흔적(자동이체)" 하나로 퉁치고 있습니다

그런데 이건 *계좌 사용 패턴*이지 *본인이 누구인가*가 아닙니다. 성격이 다릅니다.

### 구현이 쌉니다

이런 서류는 **사용자가 직접 발급받아 은행에 첨부**하는 것입니다. **이미지 업로드 대상이 아니고, 무저장 원칙과도 무관합니다.** 체크리스트에 "직접 첨부" 항목으로 넣기만 하면 됩니다 — **신분증 사본을 이미 그렇게 처리하고 있으니 같은 패턴**입니다.

**프론트에 필요한 것**: `ChecklistItem`에 "직접 첨부" 성격의 항목 추가. 지금 `ChecklistItem.id`가 `EvidenceId`로 묶여 있어(`types.ts`) 업로드 자료와 1:1인데, **업로드하지 않는 항목**을 표현할 수 있어야 합니다.

## 6. 수사 자료를 편입할 경로가 없습니다

> *"수사 결과 혐의 없음 처분이 나오면 이의제기의 강력한 소명자료가 됩니다."*

실제 사례에서 **구매자가 물건을 못 받아 판매자를 고소하는** 경우가 흔합니다. 그런데 우리 F9-02는 *"형사 절차 전환 시 전문가 상담 권고, 서비스 범위를 벗어남"* 으로 **밖으로 내보내기만 합니다.** 경찰 신고 접수증·수사 결과를 증빙으로 넣는 경로가 없습니다.

통장협박 케이스에서는 사용자가 **오히려 신고자**가 되는데도 마찬가지입니다.

**프론트에 필요한 것**: 증거 유형 또는 "직접 첨부" 체크리스트 항목 + F9-02 안내와의 연결.

> ⚠️ 여기서 **"고소당하셨나요?"** 같은 질문을 전면에 두지 마세요. 이미 불안한 사용자에게 공포를 더합니다. 해당하는 사람만 선택적으로 보게 배치해주세요.

## 7. 업로드 화면에서 "무엇을 올릴지" 먼저 보여줘야 합니다 (F3-07 신설)

### 지금 무슨 일이 일어나나

`UploadPanel.tsx`의 안내 문구가 이것뿐입니다.

> "대화·입금 내역·송장 캡처를 올리면 정리해드려요."

**사유유형과 무관한 고정 문구**라, 문진에서 "용역·알바 대가"를 고른 사용자에게도 **송장**을 안내합니다. 그리고 사유별 체크리스트(F7-03)는 **Stage 4(소명서)** 에 있습니다.

즉 사용자는:

1. Stage 2에서 **빈 업로드 박스**를 보고 "뭘 올리지?" 상태가 되고
2. Stage 4에 가서야 "아, 거래명세서가 필요했구나"를 알게 되고
3. Stage 2로 **되돌아가야** 합니다 — 이미 캡처를 지웠다면 되돌릴 수도 없습니다

실제 사례에서 A씨가 *"거래 이후 채팅 내역도 이미 지워서"* 곤란해진 것과 같은 구조입니다.

### 요청 — 업로드 패널 상단에 3단 안내

`spec.md`에 **F3-07**로 신설했습니다. 목록은 `reason-type-rules.md` §2를 **F7-03과 공유**하므로 데이터를 두 곳에 복사하지 않습니다.

```
[물품 거래를 선택한 경우]

은행이 바로 심사할 수 있는 자료
  · 거래 상대방과의 대화
  · 거래명세서            ← 계약서·세금계산서 중 하나만 있어도 됩니다
  · 구매자–송금인 확인
  · 사업자등록증          ← 해당 없으면 넘어가세요

함께 내면 도움이 되는 자료  (올리지 않아도 됩니다)
  · 재직증명서 · 소득금액증명원

따로 챙기실 것  (서비스에 올리지 않습니다)
  · 신분증 사본
  · 신청서 자필 서명
```

**지켜야 할 것 2가지**

- **해당 없는 항목을 붉은 경고로 표시하지 마세요.** 개인 중고거래자는 사업자등록증을 발급받을 수 없습니다. "해당 없으면 넘어가세요"로 안내해야 합니다
- **"이걸 내면 통과됩니다" 류의 표현 금지.** 허용 표현: **"이 자료를 갖추면 금융회사가 5영업일 내 심사합니다"**

### 왜 F3-05와 별개인가

`F3-05`(캡처 방법 안내)는 *"어떻게 캡처하나"*(기종별 키 조합)이고, F3-07은 *"무엇을 올려야 하나"*입니다. **둘 다 업로드 화면에 필요합니다.**

## 8. 회신이 필요한 항목 정리

| # | 항목 | 물어보는 것 |
| --- | --- | --- |
| 1 | 구매자–송금인 일치 | 카드에 두 이름을 어떻게 보여줄지 / 불일치 안내 배치 |
| 2 | **소명자료 3단 구조 + 택일(OR)** | **자료구조 형태를 정해주세요** (백엔드가 같은 구조로 맞춥니다). ③·④를 준비도에서 제외하는 것에 동의하시는지도 |
| 3 | 직거래 | **A안(문진 문항 추가) / B안(증거 유형 추가)** 중 선택 |
| 4 | 플랫폼 거래 내역 | 증거 유형 추가 가능 여부 |
| 5 | 신원·경제력 소명 | "직접 첨부" 항목을 체크리스트에 표현 가능한지 |
| 6 | 수사 자료 | 어디에 배치할지 |
| 7 | **사유별 업로드 안내 (F3-07)** | 업로드 패널 상단에 3단 안내를 넣을 수 있는지 / 레이아웃 부담 |
| 8 | **일정** | 7건 중 8/25~8/28 구간에 들어갈 수 있는 범위 |

### 일정이 부담되면

**우선순위는 7 > 3 > 1 > 5 > 2 > 4 > 6 입니다.**

- **7(업로드 안내)** 이 가장 먼저입니다. 나머지 6건은 "올린 자료를 어떻게 판정하나"인데, 7은 **애초에 올바른 자료를 올리게 만드는" 것**이라 앞단에서 문제를 줄입니다. 구현도 안내 문구 렌더라 가볍습니다.

- **3(직거래)** 은 안 고치면 특정 사용자군에게 **잘못된 안내**가 나갑니다. 버그에 가깝습니다.
- **1(송금인 일치)** 은 이 서비스의 판별력 자체를 좌우합니다.
- **5(신원·경제력)** 는 체크리스트 항목 추가라 가장 쌉니다.
- **4, 6**은 이번에 못 하면 다음으로 미뤄도 됩니다.
