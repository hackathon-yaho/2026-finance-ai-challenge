## 0. 먼저 — 확정된 좋은 소식 2가지

**은행별 자체 템플릿은 없습니다.** 카카오뱅크 배포본을 내려받아 국가법령정보센터 원본과 대조했더니 **수신처 한 줄(`○○○ 금융회사 귀하` → `한국카카오은행(주) 귀하`)만 다르고 나머지는 전부 동일**했습니다. 은행별 분기 처리가 필요 없습니다.

**서식 버전 대조도 끝났습니다.** 현행은 `<개정 2016. 7. 26.>` 입니다. 추가 확인 작업이 필요 없습니다.

## 1. 서식 필드가 8개가 아니라 11개입니다 (정정)

원본 서식의 기재란을 우리 계약과 대조한 결과입니다.

| 서식 기재란 | 현재 계약 키 | 상태 |
| --- | --- | --- |
| 신청인 — 성명 | `applicant.name` | ✅ |
| 신청인 — 생년월일 | `applicant.birthDate` | ✅ |
| 신청인 — 주소 | `applicant.address` | ✅ |
| 신청인 — **전화번호** | `applicant.phone` | ⚠️ 이름 모호 |
| 신청인 — **휴대전화번호** | — | ❌ **누락** |
| 신청인 — **전자우편주소** | — | ❌ **누락** |
| 계좌 — 금융회사 | `account.bank` | ✅ |
| 계좌 — 개설점포 | `account.branch` | ✅ |
| 계좌 — 예금종별 | `account.depositType` | ✅ |
| 계좌 — 계좌번호 | `account.accountNumber` | ✅ |
| 계좌 — **명의인** | — | ❌ **누락** |

**전자우편주소는 특히 중요합니다.** 지점이 없는 인터넷은행은 **이메일·팩스로 접수**하므로 회신 경로가 됩니다.

### 백엔드 제안 (다른 이름을 쓰셔도 계약에만 적히면 맞추겠습니다)

```json
{
  "applicant": {
    "name": "", "birthDate": "", "address": "",
    "phone": "",        // 전화번호 (유선)
    "mobile": "",       // 휴대전화번호  ← 신규
    "email": ""         // 전자우편주소  ← 신규
  },
  "account": {
    "bank": "", "branch": "", "depositType": "", "accountNumber": "",
    "holderName": ""    // 명의인       ← 신규
  }
}
```

**이전 회신에서 확정한 것은 그대로 유지됩니다** — 11개 **전부 선택**, 빈 값이면 공란 PDF, 폼에 필수 표시(`*`) 금지, 길이 100자·`birthDate` 형식만 검증.

> `holderName`(명의인)은 대개 신청인과 같습니다. **"신청인과 동일" 체크박스**를 두고 체크하면 `name`을 복사하는 방식이 사용자 입력을 줄입니다(PRD §4.4가 "신청인과 동일 여부 확인"으로 적어둔 항목입니다). 폼 구성은 프론트 판단에 맡깁니다.

## 2. PDF 1면은 법정 서식을 그대로 재현합니다 (백엔드 작업 · 통보)

**이건 프론트 작업이 아니라 통보입니다.** 다만 미리보기 화면을 만드신다면 1면 렌더링이 이 규칙을 따라야 하므로 공유합니다.

- **레이아웃을 재디자인하지 않습니다.** 은행 담당자가 눈으로 아는 양식입니다. 예쁘게 다시 그리면 오히려 반려 위험이 있습니다. A4(210×297mm) 규격과 표 구조를 원본대로 재현합니다.
- **접수번호·접수일자 란은 비웁니다.** 서식이 *"색상이 어두운 란은 신청인이 적지 않습니다"* 로 지정한 란입니다.
- **수신처**는 `account.bank` 값을 `○○○ 금융회사` 자리에 렌더합니다. 값이 없으면 원본대로 `○○○ 금융회사 귀하`를 둡니다(원본과 동일 상태이므로 문제없습니다).
- **작성일자**는 서버가 생성일로 채웁니다. 사용자 입력이 아닙니다.

### ⚠️ 서명란 — 화면 안내가 필요합니다 (프론트 요청)

서식에 **`신청인 성명 (서명 또는 인)`** 칸이 있습니다. 전자서명은 서비스 범위 밖이므로 **빈칸으로 출력**합니다.

그러면 사용자는 **출력 → 자필 서명 → (이메일 접수라면) 재스캔** 을 해야 합니다. 이걸 모르고 파일을 그대로 보내면 반려될 수 있습니다.

**요청**: 다운로드 완료 시점에 **"출력해서 서명란에 자필 서명한 뒤 제출하세요"** 안내를 노출해주세요. 신분증 사본 직접 첨부 안내(`DraftStage`에 이미 있는 문구)와 같은 자리에 묶으면 자연스럽습니다.

## 3. 5면 "부족자료 체크리스트"를 은행 제출본에서 빼야 합니다

### 문제

`spec.md` F7-06이 부족자료 체크리스트를 **은행 제출용 6종에 포함**시키고 있습니다.

> 구성 ① 신청서 작성 지원본 ② 사실관계 진술서 ③ 타임라인 ④ 증빙자료 목록 ⑤ 원본 이미지 **⑥ 부족한 자료 체크리스트**

**은행에 내는 서류에 "제가 이런 자료를 못 갖췄습니다" 목록을 붙이는 셈입니다.**

이의제기는 은행 담당자의 판단에 크게 좌우되고, 실무상 은행이 소극적으로 대응하는 경향이 보고됩니다. 그 담당자에게 **미보유 목록을 스스로 정리해서 건네는 것**은 불리하게 작용할 수 있습니다.

게다가 `spec.md` F7-03의 표시 문구가 **"미보유 — 보완 요청 사유가 될 수 있습니다"** 입니다. 이 문장이 그대로 은행에 갑니다.

### 백엔드 제안

부족자료 체크리스트는 **사용자 본인이 보는 것**입니다. 제출본에서 분리합니다.

| | 지금 | 제안 |
| --- | --- | --- |
| 은행 제출 PDF | 6종 (①~⑥) | **5종** (①~⑤) |
| 부족자료 체크리스트 | 6종에 포함 | **화면에만** 표시 (이미 `DraftStage`에 있음) |

⑥ 자리에는 대신 **"직접 첨부해야 하는 서류 안내"**(신분증 사본, 자필 서명)를 두는 것도 방법입니다. 이건 은행에 보여도 무해하고 사용자에게 유용합니다.

### 프론트에 필요한 것

- **`DraftStage`의 "제출 패키지 6종 내보내기" 버튼 문구** 변경 (현재 스텁 상태)
- 부족자료 체크리스트는 **화면에 그대로 유지** — 이미 구현돼 있으므로 오히려 지우지 마세요

### 회신 필요

이 판단에 동의하시는지, 아니면 6종을 유지할 다른 이유가 있는지 알려주세요. **PDF 구성이 바뀌면 F7-06 수용 기준("6종이 모두 포함된 단일 PDF")도 함께 고쳐야 합니다.**
