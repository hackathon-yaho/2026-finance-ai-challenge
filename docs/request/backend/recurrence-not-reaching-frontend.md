## 요약

AI가 `recurrence`를 구현해 내보내기 시작했는데(`50d4a58`), **백엔드에서 끊깁니다.**

| 위치 | `recurrence` | 확인 방법 |
| --- | --- | --- |
| AI-server 출력 | ✅ 있음 | `ai-server/app/schemas/card.py`의 `Card.recurrence` |
| 내부 계약 | ✅ 있음 | `internal-api-contract.md` "recurrence" 절 |
| **백엔드 `ExtractedEvent`** | ❌ **없음** | `grep -rn recurrence backend` → 0건 |
| **공개 계약 `api-contract.md`** | ❌ **없음** | `grep -n recurrence docs/02-architecture/api-contract.md` → 0건 |
| 프론트 | ❌ 못 받음 | 위 두 줄의 결과 |

`ExtractedEvent`는 record라 선언하지 않은 필드를 실을 수 없고, Jackson이 관대 모드라 **에러 없이 조용히 버려집니다.** 즉 지금 상태에서도 **500은 나지 않습니다** — 그래서 더 눈에 안 띕니다.

## 실측 (2026-08-26, 로컬 3서버 · 실제 OpenAI 호출)

같은 이미지(`04_자동이체_통신비.png`, 통신요금 12개월)를 두 경로로 넣어봤습니다.

**AI 서버 직접** — `POST :8000/internal/extract?image_index=0`

```json
{ "source_type": "autopay", "occurred_at": "2025-09-15T00:00:00+09:00", "amount": 65890,
  "recurrence": { "count": 12, "period": "monthly",
                  "first": "2025-09-15T00:00:00+09:00", "last": "2026-08-15T00:00:00+09:00" } }
```

**백엔드 경유** — `POST :8080/api/evidence` (같은 이미지, 8.2초, `200`)

```json
{ "source_type": "autopay", "occurred_at": "2025-09-15T00:00:00+09:00", "amount": 65890,
  "summary": "SK텔레콤 통신요금이 매월 같은 금액으로 자동 출금됨" }
```

`recurrence` **키 자체가 없습니다.** 카드 1장으로 묶이는 것(12장 → 1장)까지는 정상 동작하니, 손실 지점은 `ExtractedEvent` 하나로 좁혀집니다. 응답은 `200`이고 에러도 로그도 없습니다.

## 왜 그냥 두면 안 되는가 — 묶기 전보다 나빠집니다

이게 이 요청을 급하게 만드는 부분입니다. `recurrence`가 없으면 **묶기 이전 상태로 돌아가는 게 아니라, 정보가 사라진 상태**가 됩니다.

| | 묶기 전 | 지금 (묶었는데 `recurrence`가 안 옴) |
| --- | --- | --- |
| 카드 | 12장 | **1장** |
| `amount` | 각 65,890원 | 65,890원 (**1회분**) |
| `occurred_at` | 12개 날짜 | 첫 회차 하나 |
| 화면에 보이는 것 | 12번 있었다 | **"2026.01.15 · 통신비 자동이체 · 65,890원"** — 1번 있었던 것과 구분 불가 |

**사용자가 F4-06에서 이 카드를 확인합니다.** 12개월치를 대표하는 카드인데 화면에는 1회분 금액과 첫 날짜만 보이니, 사용자는 **"6만 원짜리 거래 한 건"으로 읽고 "맞아요"를 누릅니다.** 확인 절차의 의미가 깨집니다.

3면 타임라인도 같은 이유로 한 줄이 됩니다. 그런데 **소명서 문장은 정상입니다** — AI가 내부적으로 `recurrence`를 써서 "매월 12회, 2026.01.15부터 2026.12.15까지" 같은 문장을 만듭니다(`drafting.py`). 결과적으로 **소명서에는 "12회"라고 쓰여 있는데 같은 문서 3면 타임라인에는 1줄만 있는** 상태가 됩니다. 은행이 두 면을 대조하면 어긋나 보입니다.

## 요청

1. **`api-contract.md`에 `recurrence`를 반영해주세요.** 내부 계약과 같은 모양이면 됩니다 — `{ count, period, first, last }`, 반복이 아니면 `null`. `period`는 `monthly | weekly | daily | other`
2. **`ExtractedEvent`에 필드를 추가해 통과시켜주세요.** 백엔드가 값을 해석할 필요는 없고 그대로 흘려보내면 됩니다
3. **서버가 그리는 3면·4면에도 반영이 필요한지 판단해주세요** — 이건 저희가 정할 수 없는 부분입니다. 3면이 이 카드를 한 줄로 그리면서 "매월 12회"를 안 적으면 위에 쓴 소명서-타임라인 불일치가 **PDF 안에서** 그대로 남습니다. 4면은 원본 단위라 이미 한 줄이지만, "확인된 일시" 열에 첫 회차만 찍히면 같은 문제가 작게 반복됩니다

## 프론트는 카드 쪽을 먼저 붙여뒀습니다

**확인 카드(F4-06)는 구현을 마쳤습니다.** 필드가 오는 순간 그려집니다 — 값이 없으면 지금과 똑같이 동작하는 선택 필드로 받았습니다.

- 칩 줄에 **"매월 · 12회"** 배지 (접어도 보이는 자리)
- 금액 행 라벨을 **"금액 (1회분)"** 으로
- 아래 한 줄에 **"2025.09.15부터 2026.08.15까지 12회예요."**

카드부터 한 이유는, 이 화면이 **사용자가 "맞아요"를 누르는 자리**여서입니다. 1회분 금액만 보이는 카드를 확인하게 두면 확인 절차 자체가 의미를 잃습니다. 그리고 이 화면은 PDF에 대응하는 면이 없어 **서버와 문구를 맞출 필요가 없습니다.**

**3면·4면은 일부러 미뤘습니다.** 그쪽은 서버가 그리는 PDF와 같은 문구여야 하는데, 저희가 먼저 정해버리면 또 갈립니다. 서버가 쓰기로 한 문구를 알려주시면 그대로 맞추겠습니다.

## 참고 — 지금 프론트에 반영된 것

§7 `occurred_at == null` 게이팅은 **오늘 반영 완료**했습니다. `lib/cards.ts`의 `isBlocking`이 `low` 신뢰도 외에 `occurred_at == null`도 막고, `amount == null`은 그대로 예외입니다 — `hasBlockingUnconfirmedCards`와 같은 규칙입니다. 화면 문구는 이유를 구분해 적습니다(연도 없는 캡처에 "판독 신뢰도가 낮아요"라고 하면 사용자가 고칠 데를 못 찾습니다).
