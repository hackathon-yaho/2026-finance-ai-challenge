## §1. 같은 거래가 캡처 두 장에 겹쳐 찍히면 카드가 3장이 됩니다

사용자 피드백에서 시작했습니다 — *"같은 회사에서 같은 금액을 입금하는 내용에 대해 카드가 3개나 만들어졌다."*

용역 페르소나 자료 4장으로 재현했습니다. 원인은 **자동이체가 두 캡처에 함께 나오는 것**입니다. 실제 사용자도 똑같이 올립니다 — 입출금 내역에도 자동이체가 찍히고, 자동이체 내역을 따로 캡처하기도 합니다.

```
원본 2번 (입출금 내역)   건강보험료 128,640  ×2   ← 07.15 · 08.15 두 행
원본 4번 (자동이체 내역)  건강보험료 128,640  ×1   ← recurrence 4회로 묶임
                                        합계 3장
```

그런데 `GET /api/timeline` 실측은 이렇습니다.

```
events: 12 · gaps: 1 · mergeCandidates: 0
```

**F5-02 병합 후보가 하나도 안 잡힙니다.** `detectMergeCandidates`를 읽어보니 조건이 세 개 다 걸립니다.

| 조건 | 이 경우 |
| --- | --- |
| `parseInstant(occurredAt) != null` **양쪽 다** | 원본 2번 카드는 연도가 없어 `occurred_at`이 `null` → **후보에서 아예 제외** |
| 시각 차 ≤ `MERGE_WINDOW` | 같은 달 15일과 다음 달 15일이라 한참 벗어남 |
| `actor` 동일 | 이건 맞음 |

### 확인 부탁드리는 것

**규칙을 넓혀야 하는지, 아니면 이건 원래 범위 밖인지 판단해주세요.** 저희 쪽에서 답을 정하지 않겠습니다 — 병합은 잘못 묶으면 **서로 다른 거래를 하나로 합쳐 은행에 내는 것**이라 신중해야 할 자리입니다.

다만 판단에 도움이 될까 해서 저희가 본 것을 적습니다.

- 지금 규칙은 **"같은 사건이 몇 분 사이에 두 번 캡처된 경우"** 를 겨냥한 것으로 읽힙니다. 이번 건은 성격이 다릅니다 — **다른 캡처에 찍힌 같은 정기 거래**입니다
- 그래서 `MERGE_WINDOW`를 늘리는 건 위험해 보입니다. 창을 넓히면 **진짜로 다른 거래**(같은 금액을 두 번 보낸 경우)까지 후보가 됩니다
- 오히려 `recurrence`가 단서일 수 있습니다. 한쪽이 `recurrence`를 가진 자동이체 카드이고 다른 쪽이 그 기간 안의 같은 금액·같은 유형이면 **"이 반복에 포함된 회차"** 로 볼 여지가 있습니다. 이건 시각 차가 아니라 **포함 관계** 판정이라 창을 넓히지 않아도 됩니다
- 다만 §2가 풀리지 않으면 **연도 없는 카드는 어떤 규칙을 써도 후보에 못 들어갑니다**(`parseInstant`가 `null`). 두 건이 이어져 있는 이유입니다

**병합 UI는 이미 있습니다** — `mergeCandidates`가 오면 사용자에게 보여주고 `POST /api/timeline/merge`로 승인/거절을 보냅니다. 후보만 오면 화면 변경 없이 동작합니다.

## §2. `/internal/extract`에 기준 시점을 실어 보내주세요

**AI에게 보낸 `duplicate-cards-and-year-inference.md` §2의 전제입니다.** AI가 그 방향을 받아들이면 계약 변경이 필요하고, 계약 주체가 백엔드라 같이 요청드립니다.

### 왜 필요한가

국내 은행 앱 거래내역은 `08.19`처럼 **월·일만** 찍히는 것이 기본입니다. 지금 AI는 연도가 없으면 `occurred_at`을 `null`로 냅니다 — 8/26에 §7로 함께 정한 A안이고, 원칙 자체는 저희도 지지합니다.

그런데 실측해 보니 대가가 생각보다 큽니다. 같은 캡처를 **연도만 다르게** 넣은 결과입니다.

| | 연도 없음 | 연도 있음 |
| --- | --- | --- |
| 카드 수 | **8장** | 6장 |
| `occurred_at` | **8장 전부 `null`** | 전부 정상 |
| 반복 묶기 | **0건** | 2건 |
| F4-06 차단 | **8장 전부** | 0장 |
| `mergeCandidates` 후보 자격 | **없음**(`parseInstant`가 `null`) | 있음 |

**연도 하나가 없으면 날짜만 미상이 되는 게 아니라 반복 묶기도, 병합 후보 판정도 통째로 꺼집니다.**

그리고 결정적으로 — **지금 AI는 추론하고 싶어도 못 합니다.** `POST /internal/extract`에는 오늘 날짜도, 문진 지급정지일도 실려 있지 않습니다. `prompts.py` 7-1에 `연도가 화면에 없으면 추정하지 말고 null이다`만 있습니다.

### 요청

**`/internal/extract`에 기준 시점을 실어주세요.** 형태는 정해주시면 따르겠습니다 — 쿼리 파라미터든 헤더든 텍스트 경로 JSON 필드든, 저희 쪽 코드는 바뀌지 않습니다(프론트는 `/api/evidence`만 부릅니다).

무엇을 보낼지는 두 가지가 있어 보입니다.

1. **오늘 날짜** — 항상 있고 단순합니다
2. **문진 지급정지일**(`intake.when`) — 더 강한 기준입니다. 분쟁 대상 입금 전후로 거래가 몰려 있어서요. 다만 사용자가 모른다고 답하면 `null`입니다

저희 의견은 **둘 다 보내고 AI가 있는 것을 쓰게 하는 쪽**입니다. 다만 `intake.when`은 사용자가 입력한 값이라 **틀릴 수 있고**, 그걸 근거로 연도를 정하면 오류가 조용히 번집니다. 그래서 이건 백엔드·AI가 같이 정하실 문제로 남겨둡니다.

**AI가 A안 유지로 결론 내면 이 요청은 자동으로 닫힙니다.** 그 경우 회신에 그렇게 적어주시면 됩니다.

## 참고 — 프론트가 이미 고친 것

같은 세션에서 **소명서 생성이 실패해도 화면이 성공한 것처럼 넘어가던 것**을 고쳤습니다. `draft-timeout-needs-headroom.md`에 *"예산을 늘리면 그쪽 증상도 같이 없어질 걸로 봐 프론트에는 요청을 넣지 않기로 했다"* 고 적어주셨는데, 예산 상향은 **타임아웃이라는 원인 하나**를 없앨 뿐이고 `AI_CONFIG_ERROR`·네트워크 단절·`DRAFT_FAILED`에서는 같은 증상이 남습니다. 그래서 실패하면 소명서 화면으로 넘기지 않도록 바꿨습니다(`[초안 만들기]`가 남아 다시 시도할 수 있습니다). 배려 감사합니다 — 이건 저희 쪽에서 처리하는 게 맞았습니다.
