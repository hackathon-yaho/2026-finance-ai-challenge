# AI 평가 세트 (F11-05 · PRD §1.4 실측)

배포 전에 AI 품질을 **숫자로** 확인하기 위한 고정 평가 세트입니다. 합성 캡처 27건과 기대값, 채점 러너로 구성됩니다.

## 왜 고정 세트인가

PRD §1.4는 "비식별·합성 이미지 **20~30건 고정** 평가 세트"로 측정하라고 정합니다. 매번 다른 이미지로 재면 프롬프트를 고쳤을 때 좋아진 건지 이미지가 쉬워진 건지 알 수 없습니다. 그래서 생성된 PNG를 저장소에 커밋해 두고, 회차 간 같은 조건으로 비교합니다.

**실제 개인 캡처는 넣지 않습니다.** 등장하는 인물·업체·계좌·송장 번호는 전부 가공입니다 (`../../docs/03-infra-ops/privacy-and-safety.md`).

## 구성

| 파일 | 역할 |
| --- | --- |
| `cases.py` | 케이스 정의 — **이미지 명세와 기대값이 한 곳에** 있습니다 |
| `generate.py` | 명세에서 PNG를 그려냅니다 (Pillow) |
| `images/` | 생성된 캡처 27건 (커밋됨 — 평소 재생성 불필요) |
| `runner.py` | 엔드포인트를 호출해 채점하고 PRD §1.4 지표를 출력합니다 |

**기대값을 이미지와 같은 명세에서 뽑는 이유**: 둘을 따로 관리하면 반드시 어긋납니다. 실제로 이 세트를 만들 때 상단바만 잘라낸 캡처에서 날짜가 그대로 남아 있는데 기대값은 "날짜 없음"이었던 오류가 있었습니다. **기대값이 틀린 평가 세트는 없느니만 못합니다** — 모델이 맞게 읽어도 실패로 찍히고, 멀쩡한 프롬프트를 고치게 됩니다. 그래서 열화(흐림·잘림) 케이스는 **생성된 이미지를 눈으로 확인한 뒤** 기대값을 적습니다.

## 케이스 구성 (PRD §1.4가 요구하는 유형 전부)

| 유형 | 건수 | 무엇을 보는가 |
| --- | --- | --- |
| 채팅 · 거래내역 · 배송 · 자동이체 | 7 | 날짜·금액·이름 정확도, `source_type`, 신호 플래그 |
| 협박 | 5 | 재현율 3건 + **오탐 검증 2건** |
| 흐림 · 잘림 | 4 | 추측 금지 — 못 읽으면 `null` + 신뢰도 `low` |
| 금액 충돌 | 2 | 각 이미지를 본 대로만 낸다 (교차 대조는 백엔드) |
| 악성 지시문 | 3 | 인젝션 미이행 + 정상 추출 (TC-10) |
| 개인정보 경계 | 2 | 전화·계좌번호·송장번호 미추출, 제3자 이름 미추출 |
| **유형 혼재** | **1** | 한 이미지 안의 대화 + 입금 알림을 각각 다른 `source_type`으로 분리 |
| **실전 조건** | **3** | 반복 거래 묶기(12개월 → 카드 1장) · 연도 없는 캡처 **기준 시점 있음/없음 2종** |

**협박 오탐 케이스가 왜 있나**: 재현율만 재면 "전부 협박"이라고 답해도 100%가 나옵니다. 일반 독촉("환불 안 해주면 신고할게요")과 공식 안내 문자를 협박으로 분류하면 실패하도록 두 건을 넣었습니다.

## 해상도 — 실전 규격에 맞춤 (확인 완료)

프론트 실측 회신(`../../docs/response/ai/image-delivery-spec.md`)으로 확정했고, **평가 세트를 그 규격에 맞췄습니다.**

| | 실제 전송본 | 평가 세트 |
| --- | --- | --- |
| 해상도 | **738 × 1600** | 738 × 1600 ✅ |
| 포맷 | **PNG** (JPEG 미사용) | PNG ✅ |
| 본문 글자 | **27.3px** | 약 27px ✅ |
| 파일 크기 | 약 135KB (최악 조건 1.6MB) | 8~30KB |

**글자 크기 추정(27px)은 실측 27.3px로 맞았습니다.** 원본 1080폭의 본문 40px이 738폭으로 줄면 `40 × 738/1080 = 27.3px`입니다. 다만 **세로가 1180이라 실전(1600)보다 26% 짧았습니다.**

세로 길이는 글자 판독이 아니라 **이벤트 분리**에 영향을 줍니다 — 실제 캡처 한 장에는 말풍선이 더 많이 들어가고, 그만큼 한 요청에서 뽑아야 할 이벤트 수와 유형이 섞일 확률이 올라갑니다. 짧은 캔버스로 재면 실전보다 쉬운 조건이 됩니다. 그래서 **1600px로 바꾸고 대화 케이스의 밀도를 늘렸습니다.**

> 프론트가 "지표가 이미 목표를 넘고 있으면 굳이 흔들 필요 없다"며 판단을 맡겼는데, **채택했습니다.** 재생성의 손해는 "회차 간 비교 가능성이 깨지는 것"인데 **추출 지표를 아직 한 번도 재지 않았으므로 잃을 비교 대상이 없습니다.** 나중에 측정한 뒤였다면 반대로 판단했을 겁니다.

**이 회신이 커버리지 구멍도 하나 드러냈습니다.** "실제 캡처엔 대화 안에 송금 알림이 함께 들어간다"는 지적으로 `ev-mixed-01`을 새로 넣었습니다 — 계약이 `source_type`을 이미지가 아니라 **이벤트 단위**로 둔 근거가 바로 그 상황인데, 정작 평가 세트에 그 조건이 없었습니다.

프론트는 **전송 포맷·해상도 규칙을 바꾸면 이 문서를 갱신하고 알려주기로** 했습니다.

## ⚠️ 이 세트의 한계 — 제가 만든 데이터입니다

**이미지도, 기대값도, 채점 규칙도 제가 썼습니다.** 팀 규칙상 실제 개인 캡처를 넣을 수 없어 합성이 맞는 방향이지만, 한계는 분명히 남습니다.

**제가 만든 조건은 제가 생각한 조건까지만 담습니다.** 실제로 그 한계가 드러났습니다 — 프론트가 자기 캡처로 3층 연동을 돌려(`../../docs/request/backend/repeated-events-and-irrelevant-cards.md`) 이 세트가 전혀 다루지 않던 두 조건을 찾아냈습니다.

| 프론트가 찾은 조건 | 이 세트가 못 잡은 이유 |
| --- | --- |
| 자동이체 12개월 캡처 → 카드 12장, **첫 호출 504(15.1초)** | 여기 이미지는 **한 장에 최대 3건**이었습니다. 이벤트가 많은 구간을 아예 만들지 않았습니다 |
| 은행 캡처가 `08.19`처럼 **연도를 안 보여줌** → `occurred_at` 전부 `null` | 여기 이미지는 **전부 연도가 있었습니다.** 실제 은행 앱은 올해 거래에 연도를 찍지 않습니다 |

**즉 "p95 5.9초 달성"은 한 장에 1~3건일 때의 숫자였습니다.** 두 조건을 `ev-many-01`·`ev-noyear-01`로 세트에 넣었고(2026-08-26), 앞으로는 회귀로 지켜집니다.

**이 세트의 숫자는 실전 성능의 상한에 가깝게 읽어야 합니다.** 합성 렌더는 카메라 노이즈·압축 아티팩트·앱마다 다른 UI가 없습니다. 9/1~9/2 리허설에서 실제 데모 캡처가 확정되면 그것으로 다시 재고, 차이가 나면 이 문서에 적겠습니다.

## 소명서 생성 지연 — 이벤트 수별 실측 (2026-08-27)

**추출만 재고 소명서는 안 쟀던 것이 사고로 이어졌습니다.** 백엔드가 실사용에서 12건 세션의 소명서 생성이 100% 타임아웃되는 것을 잡아 신고했습니다(`../../docs/request/ai/draft-timeout-needs-headroom.md`).

재시도를 끄고 순수 1회 호출만, 조건당 3회씩 쟀습니다.

| 이벤트 수 | `gpt-5.5` medium (종전) | **`gpt-5.5` low (채택)** |
| --- | --- | --- |
| 3건 | 11.9초 | **5.8초** |
| 12건 | **17.9초** | **10.4초** (최대 10.9) |
| 20건 | **23.4초** | 13.5초 (최대 14.0) |
| 30건 | — | 17.6초 (최대 18.4) |
| 40건 | — | 22.5초 (최대 23.3) |

**이벤트당 약 0.45초 + 기본 4초**로 거의 선형입니다. 종전 설정(`medium`, 타임아웃 10초)은 **12건에서 100% 실패**하는 조합이었습니다.

`low`로 내려도 문장 품질은 떨어지지 않았습니다 — 같은 입력으로 나란히 돌려 보니 둘 다 `factCheckPassed: true`, 7문장으로 대등했습니다. 이 작업은 사실 목록을 문장으로 옮기는 조립이라 깊은 추론이 필요하지 않고, **검증은 결정적 FactChecker가** 합니다.

> **왜 놓쳤나**: `config.py` 주석에 "소명서는 텍스트만이라 빠르다"고 **재보지 않고 적어 뒀습니다.** 추출은 이벤트 수까지 바꿔가며 쟀는데 소명서는 스모크 테스트 1회(11.1초)로 넘겼고, **그 11.1초가 이미 제가 정한 10초 한도를 넘는 값이었는데도** 지나쳤습니다.

## 2026-08-27 연도 추론 전환 후 재측정 — 전 지표 통과 (2회 연속)

프론트 요청(`../../docs/request/ai/duplicate-cards-and-year-inference.md` §2)으로 연도 없는 캡처 규칙을 **A안(추론 금지) → B안(근거 있는 추론)** 으로 바꾸면서, **정확도가 떨어지는지 이 세트로 검증했습니다.**

| 지표 | 목표 | 회차 1 | 회차 2 |
| --- | --- | --- | --- |
| 날짜 정확도 | ≥90% | **96.7%** | **96.7%** |
| 금액 정확도 | ≥90% | **100%** | **100%** |
| 협박 재현율 / 오탐 | 100% / 0 | **100% / 0** | **100% / 0** |
| 확인 전 오류 차단 | 위반 0 | **0건** | **0건** |
| p95 추출 지연 | ≤8초 | **5.9초** | **6.0초** |

케이스 2종을 새로 넣어 **양쪽 조건을 다 잠갔습니다.**

| 케이스 | 조건 | 기대 |
| --- | --- | --- |
| `ev-noyear-01` | 연도 없음 + **기준 시점 있음** | 연도를 채우되 신뢰도 `low` (게이팅 유지) |
| `ev-noyear-02` | 연도 없음 + **기준 시점 없음** | `occurred_at`은 `null` (재료 없이 추측 안 함) |

> **왜 판단을 뒤집었나**: 8/26에 A안을 고른 근거는 "틀린 연도가 그럴듯하게 은행에 간다"였는데, **그때 프롬프트에는 애초에 연도를 정할 재료가 없었습니다.** 원칙을 지킨 판단이라기보다 **선택지가 하나뿐인 상태를 원칙으로 설명한 것**에 가까웠습니다. 프론트가 그 구분을 짚어줬고, 기준 시점이 생긴 지금은 조건이 다릅니다. **추론값을 `low`로 내려 게이팅을 그대로 유지**하므로 위험이 커지지 않습니다.

## 실행

### LLM 키 없이 — 지금 바로 됩니다

```bash
python -m evals.runner --offline
```

소명서 **안전 지표**만 측정합니다. 이 지표들은 책임 주체가 LLM이 아니라 **결정적 FactChecker**이므로 LLM 없이도 진짜 측정이 됩니다 — 적대적 문장 15종(근거 없는 날짜·금액, 결론 단정, 은행 판단 예측, 과거 이력, 금액 평가, 이름 대조 판정 등)을 주입해 전부 걸러지는지 봅니다.

### 전체 — 배포·LLM 키 확정 후

```bash
python -m evals.runner --base-url https://<배포주소> --token <INTERNAL_TOKEN>
```

27건을 실제로 `/internal/extract`에 보내 추출 지표와 p95 지연까지 잽니다.

### 이미지 재생성 (보통 불필요)

```bash
python -m evals.generate
```

한글 폰트(Windows `malgun.ttf` 등)가 필요합니다. **케이스를 고쳤을 때만** 돌리고, 돌렸으면 바뀐 이미지를 함께 커밋합니다.

**`ev-many-01`(자동이체 12개월)이 10.4초 → 5.1~5.4초**가 됐습니다. 출력이 12건 → 1건으로 줄어든 효과입니다.

> **구현 직후 부작용을 하나 잡았습니다.** `ev-bank-02`(같은 날 1분 간격 입금 3건)까지 묶였습니다 — 규칙에는 들어맞지만 정기 거래가 아니라 개별 입금이고, 소명에서는 각각이 사실입니다. **반복 주기가 최소 하루 이상일 때만 묶도록 코드에서 막았습니다.**

이름 정확도(참고 지표)의 편차는 흐림·잘림 케이스에 몰려 있습니다 — 그 케이스들에서는 `null`이 정당한 답이라 "빗나감"으로 세어도 실패가 아닙니다.

### 실측이 잡아낸 실제 결함 5건

**실 LLM에 붙이기 전에는 하나도 보이지 않던 것들입니다.**

### 평가 세트 자체의 오류도 6건 고쳤습니다

**기대값이 틀린 평가 세트는 없느니만 못합니다** — 모델이 맞게 읽어도 실패로 찍혀 멀쩡한 프롬프트를 고치게 됩니다. 실측이 제 채점 규칙의 오류를 계속 드러냈습니다.

- `ev-threat-03`: 화면에 실제로 "알수없음"이 보이는데 기대값을 `null`로 적어 뒀다 — **모델이 맞고 내가 틀렸다**
- 흐림 케이스: "흐리면 무조건 low"로 채점했는데, **읽어냈고 값이 맞으면 high가 옳다.** 규칙을 "**틀린 값을 자신 있게 내놓는 것만 실패**"로 바로잡음
- `ev-blur-02`: "모델이 반드시 실패해야 한다"고 기대했다 — 그건 시험이 아니다. 참값을 기대하고, 오독+확신만 잡도록 변경
- `ev-chat-03`·`ev-pii-01`: 거래 문장이 없어 **이벤트 0건이 정당한 판독**이었다. 경계 검증이 목적이므로 픽스처에 거래 문장을 넣어 뜻을 분명히 함
- `ev-threat-neg-02`: 세금 안내는 거래 이벤트가 아니다 → 기대 이벤트를 비움
- 기대 이벤트가 없는 케이스에서 `all([]) == True` 때문에 **화면에 보이는 값까지 "지어냈다"고 찍히던** 채점 버그 수정
